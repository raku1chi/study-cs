## なぜ学ぶのか

- **ML のコードは氷山の一角**: Google の Sculley ほかは 2015 年の論文 "Hidden Technical Debt in Machine Learning Systems"（NeurIPS 2015）で、実際の ML システムでは ML のコードはごく一部にすぎず、データの収集・検証、特徴量の抽出、設定、配信の基盤、監視といった周辺のシステムが大半を占めること、そしてそこに通常のソフトウェアにはない種類の技術的負債がたまることを示しました。
- **世界が変わるとモデルは壊れる**: 2020 年、新型コロナウイルスの流行で人々の購買行動が急変し、需要予測や不正検知などで使われていた多くのモデルが想定外の振る舞いをしたと報じられました（MIT Technology Review, 2020）。学習データの世界と本番の世界がずれることは、例外ではなく日常です。
- **LLM は提供元の都合で変わる**: Chen・Zaharia・Zou（2023）は、同じ名前で提供されていた LLM の 2023 年 3 月版と 6 月版で、一部のタスクの正答率が大きく変化したことを報告しました。自社のコードを 1 行も変えていなくても、品質は変わりうるのです。
- **運用しなければ価値は続かない**: モデルの価値は、本番で使われ続けて初めて生まれます。監視・再学習・ロールバックの仕組みがないモデルは、導入した日から少しずつ負債に変わっていきます。

## 1. ML システムの隠れた技術的負債

Sculley ほかの論文の有名な図では、ML のコードは中央の小さな箱として描かれ、その周りを、設定、データの収集、特徴量の抽出、データの検証、計算資源の管理、分析のツール、プロセス管理、配信の基盤、監視という、はるかに大きな箱が取り囲んでいます。モデルの精度を上げる作業は、システム全体から見ればごく一部だということです。

論文が挙げる負債の典型を、実務の言葉に直すと次のようになります。

| 負債 | 何が起きるか | 対策の方向 |
|---|---|---|
| **CACE**（Changing Anything Changes Everything） | 特徴量を 1 つ加えるだけで、他の特徴量の重みや、しきい値の最適値まで変わる | 変更のたびに全体を再評価する。評価の自動化 |
| 宣言されていない利用者 | モデルの出力を、知らないうちに別のチームが特徴量として使っている。改善したつもりが他で障害になる | 出力の利用をアクセス制御とカタログで管理する |
| 不安定なデータ依存 | 上流のテーブルの定義が変わり、特徴量の意味が静かに変わる | データ契約とデータ品質のテスト（[12.1](../01-data-engineering/README.md)） |
| フィードバックループ | モデルの判断が、次の学習データを作る（4.4 節） | 探索のための対照群、影響の監視 |
| グルーコードとパイプラインの迷路 | 学習と推論のために書き足された変換処理が絡み合い、誰も全体を把握していない | 特徴量の定義の一元化（特徴量ストア）、パイプラインの整理 |
| 使われない実験コード | 条件分岐で残った古い実験の経路が、ある日有効になる | 実験が終わったら消す（[8.5 リファクタリングと技術的負債](../../08-software-engineering/05-refactoring-and-tech-debt/README.md)） |
| 設定の負債 | 学習の設定・特徴量の選択・しきい値が、コード以上に複雑でレビューされない | 設定もバージョン管理し、レビューとテストの対象にする |

Google の Breck ほかは、この問題への処方箋として、データ・モデル・基盤・監視についてのテストの一覧を「ML Test Score」（2017）という採点表にまとめています。自社の ML システムの成熟度を点検するチェックリストとして使えます。

## 2. ライフサイクルと基盤

### 2.1 ML のライフサイクル

```mermaid
flowchart LR
  D["データ<br>収集・検証・特徴量"] --> T["学習<br>実験管理"]
  T --> E["評価<br>オフライン指標・公平性"]
  E --> R["登録<br>モデルレジストリ"]
  R --> Dep["デプロイ<br>シャドー・カナリア・A/B"]
  Dep --> M["監視<br>ドリフト・性能・コスト"]
  M -->|"劣化・データの変化"| D
  M -->|"障害"| RB["ロールバック"]
  RB --> R
```

このループを人手で回している状態から、パイプラインとして自動化し、さらにパイプライン自体の変更も CI/CD で扱う状態へと、段階的に成熟させていきます（Google Cloud のドキュメント "MLOps: Continuous delivery and automation pipelines in machine learning" は、これをレベル 0〜2 として整理しています）。大切なのは、いきなり全部を自動化することではなく、**再現できること・安全に戻せること・劣化に気づけること** を先に確保することです。

### 2.2 実験管理と再現性

モデルを再現するには、次の 4 つがそろっている必要があります。

- **データ**: 学習・検証に使ったデータの版（スナップショットの ID、クエリと時点）
- **コード**: 学習と前処理のコードのコミット
- **設定**: ハイパーパラメータ、特徴量の一覧、乱数のシード
- **環境**: ライブラリの版、ハードウェア（GPU の演算は完全には決定的でないことがある）

実験管理のツール（MLflow、Weights & Biases など。2026 年時点）は、実験ごとにこれらと評価指標・成果物を記録し、比較できるようにします。「先月の良かったモデルをもう一度作りたいが、どのデータで学習したか分からない」という状況は、記録の仕組みがあれば起きません。演習 2 のモデルレジストリも、データとコードの版がない登録を拒否します。

### 2.3 特徴量ストア

学習では DWH のバッチ処理で特徴量を作り、推論ではアプリケーションのコードで同じ特徴量を計算し直す——この二重実装は、**学習と推論の不一致**（3.3 節）の最大の原因です。**特徴量ストア** は、特徴量の定義を 1 か所にまとめ、次の 2 つの経路に同じ値を提供します。

- **オフラインストア**: 学習用。過去の各時点で「その時点で見えていた値」を取り出せる（point-in-time の正しさ。[12.1 の SCD Type 2](../01-data-engineering/README.md) や [12.2 のデータリーク](../02-machine-learning/README.md) と同じ問題）。
- **オンラインストア**: 推論用。最新の値を低遅延で返す。

Uber が 2017 年に社内の ML 基盤 Michelangelo を紹介して広く知られるようになり、オープンソースの Feast などがあります。ただし、特徴量ストアは運用の重い基盤です。モデルが少なく、特徴量がバッチで十分な段階では、DWH の中で特徴量の定義を 1 か所にまとめるだけでも、効果の大半が得られます。

### 2.4 モデルレジストリ

**モデルレジストリ** は、学習したモデルの版を管理し、どの版が本番で使われているかを明確にする仕組みです（演習 2 で実装します）。

- 版ごとに、成果物・評価指標・データとコードの版・作成者を記録する（系譜、リネージ）。
- 「検証中（Staging）」「本番（Production）」「退役（Archived）」のような状態を管理し、本番への昇格に条件（指標の閾値、承認、現行モデルとの比較）を課す。作成者本人の承認を数えないのは、職務の分離の原則です。
- 障害時に、1 つ前の本番の版へすぐに戻せる（ロールバック）。

演習 2 の実装で、昇格の拒否とロールバックの流れを見てみます（演習を解いた後に `exercises/` で実行。出力は解答例のもの）。

```python
import datetime as dt
from model_registry import (PRODUCTION, STAGING, ChampionCheck, GateError, MetricGate,
                            ModelRegistry, PromotionPolicy)

t = [dt.datetime(2026, 4, 1, 9, 0, tzinfo=dt.timezone.utc)]
def clock():
    t[0] += dt.timedelta(minutes=5)
    return t[0]

reg = ModelRegistry(clock=clock)
reg.set_policy("fraud", PromotionPolicy(gates=(MetricGate("pr_auc", ">=", 0.60),), required_approvals=1,
                                        champion_checks=(ChampionCheck("pr_auc", tolerance=0.01),)))

def ship(pr_auc):
    mv = reg.register("fraud", f"s3://models/fraud/{pr_auc}", metrics={"pr_auc": pr_auc},
                      data_version="txn@2026-03-31", code_version="git:9f8e7d", created_by="alice")
    reg.transition("fraud", mv.version, STAGING, actor="alice")
    reg.approve("fraud", mv.version, approver="bob")
    try:
        reg.transition("fraud", mv.version, PRODUCTION, actor="alice")
        print(f"v{mv.version}（PR-AUC {pr_auc}）を本番へ")
    except GateError as e:
        print(f"v{mv.version}（PR-AUC {pr_auc}）は昇格不可: {e.reasons}")

ship(0.66)
ship(0.64)          # 現行の本番より 0.02 悪い
ship(0.68)
print("本番:", f"v{reg.production('fraud').version}")
print("障害 → ロールバック:", f"v{reg.rollback('fraud', actor='oncall').version}")
for e in reg.audit_log[-4:]:
    print(e.at.strftime("%H:%M"), e.actor, e.action, f"v{e.version}", e.detail or "-")
```

```text
v1（PR-AUC 0.66）を本番へ
v2（PR-AUC 0.64）は昇格不可: ['pr_auc が現行の本番（v1: 0.66）より悪化しています（0.64）']
v3（PR-AUC 0.68）を本番へ
本番: v3
障害 → ロールバック: v1
10:10 bob approve v3 -
10:15 alice archive v1 v3 の昇格に伴う
10:20 alice transition v3 Staging → Production
10:25 oncall rollback v1 v3 → v1
```

ロールバックでは昇格の条件を再確認しません。障害対応では速さが最優先で、戻す先は以前に本番で動いていた版だからです。その代わり、**ロールバック先の版が今も動く状態にあること**（成果物が残っている、依存する特徴量が今も提供されている）を日頃から確かめておく必要があります。MLflow などの製品では、ステージの代わりに別名（エイリアス）やタグで本番の版を指す方式も使われています（2026 年時点。製品のドキュメントを確認してください）。

## 3. デプロイのパターン

### 3.1 バッチ推論とオンライン推論

| | バッチ推論 | オンライン推論 |
|---|---|---|
| 仕組み | 定期的に全件（または対象）を予測し、結果を DB に保存する | 要求のたびに、その場で予測する |
| 例 | 毎晩の解約スコア、週次の需要予測、推薦の候補の事前計算 | 決済の不正検知、検索の並べ替え、チャットの応答 |
| 鮮度 | 前回の実行時点のデータ | 要求の時点のデータ |
| 遅延の要件 | 緩い（数時間で終わればよい） | 厳しい（数十〜数百ミリ秒） |
| 運用の難しさ | 低い。失敗したら再実行 | 高い。可用性・遅延・スケーリングの設計が必要 |

「リアルタイムの予測が必要か」は、12.1 のストリーミングと同じく、**その鮮度で誰のどの判断が変わるのか** で決めます。バッチで事前計算した結果を低遅延で引くだけで足りる場合は、意外に多くあります。

### 3.2 安全な切り替え

新しいモデルは、オフラインの評価が良くても本番で期待通りに動くとは限りません（データの分布の違い、遅延、依存するシステムの挙動）。段階的に切り替えます（[8.4 CI/CDとリリースエンジニアリング](../../08-software-engineering/04-ci-cd-and-release/README.md)）。

```mermaid
flowchart LR
  S["シャドー<br>本番の入力を複製して<br>新モデルにも流す<br>利用者には影響なし"] --> C["カナリア<br>一部（例: 1〜5%）の<br>要求だけ新モデルへ<br>異常があれば即停止"]
  C --> AB["A/B テスト<br>無作為に分けて<br>事業の指標を比較"]
  AB --> F["全面切り替え<br>旧モデルは<br>ロールバック用に保持"]
```

- **シャドー**: 新旧の予測の分布や差、遅延、エラーを、利用者に影響を与えずに比べられます。ただし、新モデルの判断が実際に使われないので、「その判断の結果、利用者がどう行動したか」は分かりません。
- **カナリア**: 実際の利用者の一部に新モデルを使い、技術的な異常（エラー率・遅延・予測の偏り）を早く検出します。
- **A/B テスト**: 事業上の効果（売上、解約率、不正の損失）を統計的に比較します（[2.2 確率・統計と定量的思考](../../02-math-and-algorithms/02-probability-statistics/README.md)）。オフラインの指標の改善が事業の改善につながるとは限らないので、最終判断はここで行います。

### 3.3 学習と推論の不一致（training-serving skew）

学習時と推論時で、同じはずの特徴量の値が違ってしまう現象です。典型的な原因は次の通りです。

- 学習用（SQL）と推論用（アプリケーションのコード）で、特徴量を別々に実装している
- 欠損値・外れ値・タイムゾーンの扱いが、2 つの実装で違う
- 学習時は日次のバッチで集計した値、推論時はリアルタイムの値を使っている（鮮度の違い）
- 推論時に使えない情報（未来の情報）を、学習時に使ってしまっている（リーク）

対策の基本は、**推論時に実際に使った特徴量の値を記録し、それを学習データとして再利用する**（あるいは学習時の値と突き合わせる）ことです。推論時の特徴量の分布を学習時の分布と比べる監視（4 節）も、不一致の検出に役立ちます。

## 4. 監視 — モデルは静かに劣化する

### 4.1 何が変わるのか

| 種類 | 変わるもの | 例 |
|---|---|---|
| データドリフト（共変量シフト） | 入力の分布 P(X) | 新しい販路の開始で、利用者の年齢層が変わる |
| コンセプトドリフト | 入力と正解の関係 P(Y\|X) | 不正の手口が変わり、同じ特徴を持つ取引でも不正の確率が変わる |
| ラベルシフト | 正解の割合 P(Y) | 景気の悪化で、延滞の割合が全体に増える |
| 上流のデータの障害 | 特徴量そのものが壊れる | 列の単位が変わる、欠損が急増する、既定値ばかりになる |

実務で最も頻繁に起きるのは、最後の **上流のデータの障害** です。モデルの側で気づくより、[12.1](../01-data-engineering/README.md) のデータ品質のテストで止める方が安く確実です。

もう 1 つの難しさは、**正解が遅れて届く** ことです。不正の確定は数週間後のチャージバック、解約は数か月後、融資の返済の成否は数年後に分かります。性能そのものを測れるまで待てないので、入力の分布・予測の分布・代わりの指標（早期の兆候）を監視して、劣化を推測します。

### 4.2 ドリフトの検出

演習 1 では、次の 3 つの手法を実装します。

- **PSI（Population Stability Index）**: 基準データの分位点でビンを作り、基準と現在の割合から PSI = Σ (a − e) ln(a / e) を計算します。与信モデルの監視で使われてきた経験則として、0.1 未満は安定、0.1〜0.25 はやや変化、0.25 以上は大きな変化とされます。割合が 0 のビンは log(0) になるので、小さな値（eps）で置き換えます。
- **KS 検定（2 標本）**: 2 つの累積分布関数の最大の差 D を統計量とし、「同じ分布から来た」という仮説の p 値を求めます。同じ値（同点）の扱いを誤ると D を大きく見積もってしまうので、実装に注意が必要です。
- **カイ二乗検定**: カテゴリの特徴量について、基準と現在の割合が同じかを 2 × k の分割表で検定します。新しいカテゴリの出現も検出できます。

演習 1 の `evaluate_drift` で、よくある 3 種類の変化を検出してみます。

```python
import random
from drift import evaluate_drift

rng = random.Random(0)
n = 5000
reference = {   # 学習時のデータ
    "amount": [rng.lognormvariate(8.0, 0.6) for _ in range(n)],
    "age": [rng.gauss(40, 12) for _ in range(n)],
    "device": [rng.choice(["pc", "ios", "android"]) for _ in range(n)],
}
current = {     # 本番の直近 1 週間のデータ
    "amount": [rng.lognormvariate(8.3, 0.6) for _ in range(n)],             # 高額の注文が増えた
    "age": [None if rng.random() < 0.2 else rng.gauss(40, 12) for _ in range(n)],  # 上流の変更で欠損が急増
    "device": [rng.choice(["pc", "ios", "android", "android"]) for _ in range(n)],
}
for r in evaluate_drift(reference, current, categorical={"device"}):
    print(f"{r.feature:7s} {r.status:6s} PSI={r.psi:.3f} p={r.p_value:.1e} 欠損 {r.missing_rate_current:.0%}  {' / '.join(r.reasons)}")
```

```text
age     alert  PSI=0.003 p=8.5e-01 欠損 20%  欠損率が 0.0% → 20.1% に増加
amount  warn   PSI=0.223 p=2.6e-92 欠損 0%  PSI=0.223 ≥ 0.1（p=2.6e-92）
device  warn   PSI=0.103 p=6.1e-56 欠損 0%  PSI=0.103 ≥ 0.1（p=6.1e-56）
```

`age` は、値がある部分の分布は変わっていない（PSI ≈ 0）のに、欠損が 20% に急増しています。分布の指標だけを見ていると見逃す、上流の障害の典型です。

ドリフトの監視を運用するときの注意点は 3 つあります。

1. **p 値だけで判断しない**。標本が大きいと、実務上意味のない小さな差でも p 値は極端に小さくなります（上の例でも p はすべて天文学的に小さい）。逆に標本が小さいと、PSI は偶然大きくなります。演習では「効果の大きさ（PSI）と有意さ（p 値）の両方」を条件にしています。
2. **多重検定に注意する**。多くの特徴量を毎日検定すれば、ドリフトがなくても偶然の警告が出ます。

```python
import random
from drift import ks_p_value, ks_statistic

rng = random.Random(1)
false_alarms = 0
for feature in range(200):          # ドリフトのない 200 個の特徴量
    ref = [rng.gauss(0, 1) for _ in range(500)]
    cur = [rng.gauss(0, 1) for _ in range(500)]
    if ks_p_value(ks_statistic(ref, cur), 500, 500) < 0.01:
        false_alarms += 1
print(f"ドリフトのない 200 特徴量のうち p < 0.01 になったもの: {false_alarms} 個（期待値は約 2 個）")
```

```text
ドリフトのない 200 特徴量のうち p < 0.01 になったもの: 3 個（期待値は約 2 個）
```

3. **ドリフト ≠ 性能の劣化**。モデルが重視していない特徴量のドリフトは、性能に影響しないことがあります。重要な特徴量に絞る、予測の分布そのものも監視する、正解が届いたら性能で確かめる、という組み合わせで、警告の数を「人が対応できる量」に保ちます。季節性（曜日・月末・セール）も、比較する基準の選び方で扱います（[12.1 のボリュームの監視](../01-data-engineering/README.md) と同じ問題です）。

### 4.3 性能の監視とアラート

- **区分ごとに見る**: 全体の精度は変わらなくても、新しい地域・新しい端末・特定の顧客層だけで大きく劣化していることがあります。公平性の観点からも、集団別の指標を監視します（[12.2](../02-machine-learning/README.md)）。
- **ML システムの SLO**: 推論の遅延とエラー率に加えて、「モデルの鮮度（最後に再学習した日）」「特徴量の鮮度」「予測の分布が基準から外れていないこと」を SLO に含めます（[10.3 信頼性設計とSLO](../../10-cloud-and-sre/03-reliability-engineering/README.md)）。
- **アラート疲れを避ける**: 対応が必要なものだけをページ（呼び出し）にし、それ以外はダッシュボードと定期的なレビューで扱います。

### 4.4 フィードバックループとラベル付け

モデルの判断が、次の学習データを作ることがあります。

- **不正検知**: 不正と判定して止めた取引は、本当に不正だったかどうかの正解が得られません。止めた取引が学習データから抜け落ちると、モデルは自分の判断の正しさを学べなくなります。対策として、ごく一部の取引をモデルの判断によらず通して結果を観察する（探索）、あるいは人が確認して正解を付ける、といった方法があります。
- **推薦**: 推薦したものだけがクリックされ、クリックされたものが「好まれた」と学習されて、さらに推薦される。多様性が失われ、人気のあるものが一層人気になります。
- **予測に基づく資源配分**: 犯罪予測に基づいて警察の巡回を配置すると、巡回した地域ほど犯罪の記録が増え、その記録がさらに予測を強化する「暴走するフィードバックループ」が起きうることが、研究で示されています（Ensign ほか, 2018）。

正解のラベルを人手で付ける場合は、判断基準の文書、判定者どうしの一致率の測定、難しい事例の再確認、そしてラベル付けのコストの管理が必要です。モデルが迷っている事例を優先してラベルを付ける（能動学習）と、少ない費用で効果的にデータを増やせます。

### 4.5 再学習の方針

| 方針 | 仕組み | 向いている場面 |
|---|---|---|
| 定期的 | 毎週・毎月など決まった間隔で再学習する | 変化が緩やかで予測しやすい |
| きっかけ型 | ドリフトや性能の劣化を検知したら再学習する | 変化が不規則 |
| 継続的 | 新しいデータが届くたびに少しずつ更新する | 変化が速く、データが大量 |

どの方針でも、再学習したモデルを **自動で本番に出す前に、昇格の条件で検証する** ことが重要です。上流のデータが壊れた状態で自動再学習すると、壊れたデータを学習したモデルが自動で本番に出てしまいます。演習 2 のレジストリの昇格の条件（指標の閾値と現行モデルとの比較）は、この安全装置です。

## 5. LLMOps

### 5.1 ML の運用と何が違うのか

| 観点 | 従来の ML | LLM を使うシステム |
|---|---|---|
| モデル | 自社で学習し、自社で持つ | 多くは提供元のモデルを API で使う。提供元が更新・廃止する |
| 変更の単位 | モデルの再学習 | プロンプト・モデルの版・検索の設定・ツールの定義の変更 |
| 評価 | 正解ラベルとの比較（精度・AUC） | 自由記述の出力の評価（自動採点・LLM による採点・人の評価。[12.4](../04-llm-applications/README.md)） |
| コスト | 学習と推論の計算資源 | 主にトークン数に比例する従量課金 |
| 固有のリスク | ドリフト、偏り | 幻覚、プロンプトインジェクション、情報漏えい、提供元の障害 |

### 5.2 プロンプトと設定の版管理

LLM のシステムでは、プロンプト・モデルの識別子・生成のパラメータ・検索の設定・ツールの定義のすべてが、振る舞いを決める「コード」です。

- **すべてをバージョン管理する**: プロンプトは Git で管理し、レビューを経て変更する。本番で使っている組み合わせ（どのプロンプトの版を、どのモデルの版で使っているか）をいつでも答えられるようにする。
- **モデルの版を固定する**: 提供元が「最新版」を指す別名を用意している場合でも、本番では日付などで固定された版の識別子を使い（提供されている場合）、新しい版への移行は評価を経て行う。提供元のモデルの廃止予定を追跡し、移行の期限を管理する。
- **変更は評価を経て出す**: [12.4 の評価ハーネス](../04-llm-applications/README.md) のような回帰テストを CI に組み込み、評価データでの結果が悪化したらリリースを止める。

### 5.3 トレースとオブザーバビリティ

LLM のシステムの障害調査には、**1 回の要求の中で何が起きたか** の記録（トレース）が欠かせません（[10.4 オブザーバビリティ](../../10-cloud-and-sre/04-observability/README.md)）。

- 記録するもの: 要求ごとに、使ったプロンプトの版、モデル、入出力のトークン数、遅延、費用、検索したチャンクの ID、ツールの呼び出しと結果、エラー、ガードレールの判定。
- 分散トレースと同じく、LLM の呼び出し・検索・ツールの実行を「スパン」として親子関係でつなぐと、どこで時間とお金を使ったかが分かります。OpenTelemetry でも生成 AI 向けの属性の標準化が進められています（2026 年時点。仕様の成熟度を確認してください）。
- 注意: トレースにはプロンプトと出力、つまり **個人情報や機密がそのまま入ります**。保存期間・閲覧権限・マスキングを最初から設計します。

### 5.4 AI ゲートウェイ

組織内の多くのアプリケーションが LLM を使い始めると、提供元の API キーの管理、コストの把握、障害時の切り替えがアプリケーションごとにばらばらになります。**AI ゲートウェイ** は、すべての LLM の呼び出しを 1 か所に集める関所です（演習 3 で実装します）。

| 機能 | 目的 |
|---|---|
| ルーティング | 要求の品質・遅延・文脈の長さに合う、最も安いモデルを選ぶ |
| フォールバック | タイムアウトや一時的な障害なら、別の提供元のモデルに切り替える |
| 予算とレート制限 | チームごとのトークンの予算と、要求の頻度の上限 |
| キャッシュ | 同じ要求に保存済みの応答を返し、費用と遅延を減らす |
| 利用量の記録 | チーム・用途ごとの費用の把握と配賦 |
| 認証と監査 | API キーを各アプリケーションに配らず、誰が何を呼んだかを記録する |
| 無害化 | 個人情報のマスキング、出力の検査（[12.4](../04-llm-applications/README.md)） |

```python
from decimal import Decimal
from ai_gateway import (AIGateway, BudgetExceeded, FakeProvider, ManualClock, ModelSpec,
                        ProviderTimeout, Request)

models = [  # 価格は架空（100 万トークンあたりの円）
    ModelSpec("small", "vendor-a", 1, Decimal("15"), Decimal("60"), 400, 16_000),
    ModelSpec("medium", "vendor-b", 2, Decimal("75"), Decimal("300"), 900, 128_000),
    ModelSpec("medium-b", "vendor-a", 2, Decimal("90"), Decimal("360"), 700, 128_000),
    ModelSpec("large", "vendor-c", 3, Decimal("450"), Decimal("1800"), 2500, 200_000),
]
providers = {"vendor-a": FakeProvider("vendor-a"),
             "vendor-b": FakeProvider("vendor-b", failures=[ProviderTimeout()]),   # 1 回目だけタイムアウト
             "vendor-c": FakeProvider("vendor-c")}
gw = AIGateway(models, providers, clock=ManualClock(), team_token_budgets={"marketing": 520})

for req in [Request("support", "有給休暇の申請方法は？"),                 # standard → medium（が落ちて medium-b）
            Request("support", "有給休暇の申請方法は？"),                 # 同じ要求 → キャッシュ
            Request("support", "この文を分類して: …", quality="low"),     # low → 最安の small
            Request("marketing", "新商品のキャッチコピー", max_output_tokens=500),
            Request("marketing", "もう一案", max_output_tokens=500)]:     # 予算を超える
    try:
        r = gw.handle(req)
        print(f"{req.team:9s} → {r.model:8s} cached={r.cached!s:5s} cost={r.cost:.6f}円 attempts={list(r.attempts)}")
    except BudgetExceeded as e:
        print(f"{req.team:9s} → 拒否: {e}")
for team, u in gw.usage_report().items():
    print(team, u)
```

```text
support   → medium-b cached=False cost=0.006210円 attempts=[('medium', 'timeout'), ('medium-b', 'ok')]
support   → medium-b cached=True  cost=0.000000円 attempts=[]
support   → small    cached=False cost=0.000900円 attempts=[('small', 'ok')]
marketing → medium   cached=False cost=0.004875円 attempts=[('medium', 'ok')]
marketing → 拒否: チーム marketing の予算の残り 497 トークン < 見積もり 503
marketing Usage(requests=1, cache_hits=0, input_tokens=9, output_tokens=14, cost=Decimal('0.004875'), provider_failures=0)
support Usage(requests=3, cache_hits=1, input_tokens=17, output_tokens=28, cost=Decimal('0.00711'), provider_failures=1)
```

設計の要点:

- **予算は呼ぶ前に確かめる**: 出力が上限まで出た場合の最悪値で見積もり、超えるなら提供元に送らない。請求が届いてから気づくのでは遅い。
- **フォールバックするのは一時的な障害だけ**: タイムアウトやサーバー側の障害なら別のモデルに切り替えるが、要求そのものが不正（入力が長すぎる、形式が違う）なら、別のモデルに回しても直らず、費用だけがかかる。
- **フォールバック先の品質を評価しておく**: 切り替え先のモデルでも自社の評価データで基準を満たすことを確かめておかないと、障害時に品質の事故が起きる。
- **キャッシュは安全な範囲で**: 温度 0 の決定的な要求だけを保存し、テナント（チーム・顧客）をまたいで共有しない。権限や時点によって答えが変わる要求は保存しない。
- **ゲートウェイ自体が単一障害点になる**: 冗長化し、ゲートウェイの障害時の振る舞い（全停止か、直接呼び出しへの切り替えか）を決めておく。オープンソースやクラウドの製品もあるので（2026 年時点）、自作するか使うかは、必要な機能と運用体制で判断します。

### 5.5 ガードレールとフォールバックの設計

提供元の障害は必ず起きます。LLM の機能が止まったときの **縮退運転** を、機能ごとに決めておきます。

- 検索結果だけを表示し、生成による要約を省く
- 定型の回答やルールベースの応答に切り替える
- 「現在混み合っています」と表示し、人の担当者への問い合わせ窓口を案内する

これに加えて、タイムアウト（最初のトークンまでの時間と全体の時間）、再試行の上限、サーキットブレーカー（失敗が続く提供元への送信を一時的に止める。[9.5 スケーラビリティとパフォーマンス](../../09-architecture/05-scalability-and-performance/README.md)）を組み合わせます。

## 6. 推論基盤

### 6.1 GPU でのモデルの配信

自社で LLM を動かす場合、推論のエンジンの選択と設定が、性能とコストを大きく左右します。

- **continuous batching**: 複数のリクエストをまとめて処理するとき、全員の生成が終わるのを待たず、1 トークンの生成ごとに終わったリクエストを抜き、新しいリクエストを加える方式です（Orca, Yu ほか, OSDI 2022 の iteration-level scheduling）。GPU の遊び時間が減り、スループットが大きく上がります。
- **KV キャッシュのメモリ管理**: vLLM（Kwon ほか, SOSP 2023）は、KV キャッシュを OS の仮想メモリのページのように固定長のブロックで管理する PagedAttention により、メモリの断片化を減らして同時に処理できるリクエスト数を増やしました（[4.2 仮想メモリ](../../04-operating-systems/02-virtual-memory/README.md) の考え方の応用です）。
- 推論エンジンには vLLM のほか、Hugging Face の Text Generation Inference、NVIDIA の TensorRT-LLM などがあります。開発の状況や対応するモデルは変化が速いので、2026 年時点の状況を確認して選んでください。

### 6.2 容量計画とコスト

必要な GPU の台数は、[12.3](../03-deep-learning/README.md) のメモリの見積もり（重み ＋ KV キャッシュ）と、負荷試験で測ったスループットから計算します。次は、すべて仮定の値を使った概算です。

```python
import math

# 社内アシスタントの推論基盤の概算（すべて仮定の値。実際は負荷試験で測る）
peak_rps = 20                 # ピーク時のリクエスト数/秒
output_tokens = 400           # 1 リクエストの平均出力トークン数
gpu_tokens_per_sec = 2_500    # GPU 1 枚が連続バッチ処理で出せる出力トークン/秒（モデル・GPU・設定で大きく変わる）
headroom = 0.3                # 障害・急増に備えた余裕

need = peak_rps * output_tokens
gpus = math.ceil(need * (1 + headroom) / gpu_tokens_per_sec)
print(f"必要な生成速度: {need:,} トークン/秒 → GPU {gpus} 枚")

gpu_cost_per_hour = 600       # 円/時（仮の値）
for utilization in (0.8, 0.3):
    tokens_per_hour = gpus * gpu_tokens_per_sec * 3600 * utilization
    print(f"平均稼働率 {utilization:.0%}: 100 万トークンあたり {gpus * gpu_cost_per_hour / tokens_per_hour * 1e6:,.0f} 円")
```

```text
必要な生成速度: 8,000 トークン/秒 → GPU 5 枚
平均稼働率 80%: 100 万トークンあたり 83 円
平均稼働率 30%: 100 万トークンあたり 222 円
```

GPU はピークに合わせて確保しますが、費用は時間単位でかかり続けます。**平均稼働率が下がれば、トークンあたりの費用はそのまま上がります**。夜間に利用がない社内システムでは、稼働率 30% も珍しくありません。自社運用の損益分岐は、API のトークン単価との比較で、この稼働率を含めて判断します。

自動スケーリングにも GPU 特有の難しさがあります。数十 GB の重みを読み込んで起動するまでに数分かかることがあり、急な負荷の増加に間に合いません。GPU そのものの調達が難しい時期もあります。最低台数の確保、夜間の縮小、バッチ処理の時間帯の分離、量子化によるメモリの削減（[12.3](../03-deep-learning/README.md)）を組み合わせます。

### 6.3 自社運用か、API か

| 観点 | API を使う | 自社で動かす |
|---|---|---|
| 初期費用と速さ | ほぼゼロ。すぐ使える | GPU・推論エンジン・運用体制の準備が必要 |
| 利用量が多いときの費用 | トークン数に比例して増え続ける | 稼働率が高ければ安くなりうる |
| 品質 | 最先端の大きなモデルを使える | 自社で動かせる大きさのモデルに限られる |
| データの所在 | 提供元の契約と設定に依存する | 自社の管理下に置ける |
| 運用の負荷 | 提供元の障害・変更への追従 | GPU の障害、モデルの更新、セキュリティ対応 |

多くの組織では、まず API で始めて評価データとゲートウェイを整え、利用量とデータの要件が明確になってから、一部の用途（大量の定型処理、機密性の高いデータ）を自社運用に移す、という順序が現実的です。

## 7. 責任ある運用

- **モデルカードとデータシート**: モデルの用途と用途外、学習データ、評価の結果（集団別を含む）、既知の限界、倫理的な配慮を記したモデルカード（Mitchell ほか, 2019）と、データセットの由来・収集方法・前提を記したデータシート（Gebru ほか）は、利用者と監査に対する説明の土台になります。演習 2 のレジストリに記録する情報を、人が読める形にまとめたものと考えてください。
- **人による監督**: 影響の大きい判断では、人が AI の出力を確認・修正・却下できる経路と、そのための情報（根拠・確信度）を用意します。緊急時に AI の機能だけを止めるスイッチ（キルスイッチ）も用意しておきます。
- **AI インシデントへの対応**: 誤った回答が顧客に出た、偏った判定が見つかった、情報が漏えいした——こうした事象を、通常の障害と同じ枠組み（検知 → 影響範囲の特定 → 封じ込め → 復旧 → ポストモーテム）で扱います（[10.5 インシデント対応とポストモーテム](../../10-cloud-and-sre/05-incident-management/README.md)）。封じ込めの手段（ロールバック、機能の停止、ルールへの切り替え、人の確認の必須化）を事前に用意し、利用者からの報告の窓口を設けます。
- **規制と標準**: EU の AI 法（2024 年 8 月に発効し、義務は段階的に適用）、米国 NIST の AI リスクマネジメントフレームワーク（AI RMF 1.0, 2023 年）、AI マネジメントシステムの国際規格 ISO/IEC 42001（2023 年）、日本の「AI事業者ガイドライン」など、AI の運用に関する規制や指針が整備されつつあります。適用の範囲や時期は変化しているので、2026 年時点の最新の情報を確認し、具体的な判断は法務の専門家に確認してください（[14.5](../../14-cto/05-governance-risk-compliance/README.md)、[14.8](../../14-cto/08-ai-strategy/README.md)）。

## 8. コストの統制

AI の費用は、利用が広がるほど急に増えます。クラウドのコスト管理（[10.6 クラウドコスト管理（FinOps）](../../10-cloud-and-sre/06-finops/README.md)）と同じ考え方で統制します。

- **見える化と配賦**: ゲートウェイで、チーム・機能・顧客ごとのトークン数と費用を記録し、各チームに見せる（ショーバック）か、予算として割り当てる（チャージバック）。
- **単位あたりの経済性**: 「月の請求額」ではなく、「解決した問い合わせ 1 件あたりの費用」「生成した見積書 1 件あたりの費用」のように、事業の単位で費用を測る。単位あたりの費用が、その機能が生む価値を上回っていないかを確かめる。
- **予算と異常検知**: チームごとの予算（演習 3）、1 リクエストあたりのトークン数の急増や、特定の利用者による大量の利用の検知。エージェントの暴走（無限ループ）は、ここで止める最後の防衛線になります。
- **設計によるコスト削減**: モデルの振り分け、プロンプトキャッシュ、コンテキストの削減、バッチ処理（[12.4 の 8 節](../04-llm-applications/README.md)）。

## よくある落とし穴

1. **モデルを出して終わりにする**。監視・再学習・ロールバックの仕組みがないまま本番に出すと、劣化に気づくのは利用者の苦情になる。リリースの条件に監視とロールバックの手順を含める。
2. **学習と推論で特徴量を別々に実装する**。欠損値やタイムゾーンの扱いのわずかな違いが、本番の精度を静かに下げる。特徴量の定義を 1 か所にまとめ、推論時の値を記録して突き合わせる。
3. **ドリフトの警告を p 値だけで出す**。大量のデータでは意味のない差でも警告が鳴り続け、誰も見なくなる。効果の大きさと組み合わせ、重要な特徴量に絞る。
4. **上流のデータの障害をモデルの監視で見つけようとする**。欠損の急増や単位の変更は、データ品質のテストで取り込みの時点で止める方が早く確実。
5. **自動再学習をそのまま本番に出す**。壊れたデータで学習したモデルが自動で本番に出る。昇格の条件（指標の閾値・現行モデルとの比較）を必ず通す。
6. **LLM のモデルの版を固定しない**。提供元の更新で振る舞いが変わり、原因の特定に時間がかかる。版を固定し、移行は評価を経て行う。
7. **トレースにプロンプトと出力をそのまま無期限に保存する**。個人情報と機密の新たな保管場所になる。保存期間・権限・マスキングを設計する。
8. **GPU をピークに合わせて確保し、稼働率を見ない**。稼働率 30% なら、トークンあたりの費用は 80% のときの約 2.7 倍。稼働率を監視し、API との比較を定期的に見直す。
9. **フォールバック先のモデルを評価していない**。障害時に品質の低いモデルへ切り替わり、別の事故になる。切り替え先も評価データで基準を満たすことを確認する。

## CTOの視点

1. **ML・AI 機能のリリース基準を定める**。「オフラインの精度が良い」だけでは本番に出さない、という基準を組織として明文化します。例: ①データとコードの版が記録され再現できる、②シャドーまたはカナリアで本番のデータに対する振る舞いを確認した、③監視（入力の分布・予測の分布・遅延・費用）とアラートの担当が決まっている、④ロールバックの手順を試した、⑤モデルカードがある。これは [8.4](../../08-software-engineering/04-ci-cd-and-release/README.md) のリリース基準の ML 版です。
2. **障害対応で投げるべき質問**: 「いつから、どの区分で劣化したか（ドリフトか、上流のデータの障害か、モデルの変更か）」「直近で変わったものは何か（データ・コード・プロンプト・提供元のモデルの版）」「ロールバックできるか。すぐに戻せないなら、縮退運転に切り替えられるか」「影響を受けた顧客や判断は何件か」。これに即答できるだけの記録（トレース・レジストリの監査ログ）を、平時から残しておくことが CTO の責任です。
3. **ML の技術的負債を予算に組み込む**。ML システムは、通常のソフトウェアより保守の費用が大きくなりがちです（データへの依存、再学習、監視、ラベル付け）。新しいモデルを提案されたら、構築の費用だけでなく、年間の運用の費用（人・計算資源・ラベル付け）と、モデルをやめるときの手順まで見積もらせます。価値が運用の費用を下回ったモデルを退役させる判断も必要です。
4. **LLM の利用を AI ゲートウェイに集約する**。各チームが個別に提供元の API キーを持ち、それぞれ直接呼ぶ状態は、コストの不透明さ・キーの漏えい・障害時の混乱・監査の困難を生みます。早い段階でゲートウェイを整え、予算・利用量の見える化・フォールバック・監査を組織の標準にすると、提供元の切り替えやモデルの価格交渉も容易になります。
5. **体制と役割**: 小さな組織では、データサイエンティストが運用まで担うと、監視や再学習が後回しになりがちです。ML エンジニアや基盤チームが、実験管理・レジストリ・ゲートウェイ・監視の「舗装された道」を提供し、各チームがその上でモデルや AI 機能を作る体制を目指します（[13.6 チームと組織の設計](../../13-technical-leadership/06-team-and-org-design/README.md)）。採用では、モデルを作った経験だけでなく「本番で劣化したモデルをどう見つけ、どう直したか」を語れる人を重視します。

### 演習 4（記述）: 劣化した不正検知モデルのポストモーテム

EC サイトの不正検知モデル（オンライン推論、勾配ブースティング）について、次の事象が起きました。

> 3 月 1 日、決済の画面を刷新し、新しく「後払い」の支払い方法を追加した。3 月 20 日、経理から「3 月のチャージバック（不正による返金）が前月の 3 倍になっている」と連絡があった。調査すると、後払いの取引の特徴量 `payment_method` は、学習時に存在しない値だったため、推論時には「その他」として扱われていた。また、決済の刷新で `device_id` の取得方法が変わり、3 月 1 日以降、約 40% の取引で空になっていた。モデルは毎週日曜に自動で再学習され、そのまま本番に出る設定だった。

[10.5 インシデント対応とポストモーテム](../../10-cloud-and-sre/05-incident-management/README.md) の形式にならって、①検知が遅れた理由、②根本原因（技術と組織の両面）、③再発防止策（この章の技術を使って）をまとめてください。

<details>
<summary>解答例と採点の観点</summary>

**① 検知が遅れた理由**

- 不正の確定（チャージバック）は数週間遅れて届くため、性能の指標だけでは劣化に気づけなかった。
- 入力の分布（新しいカテゴリの出現、`device_id` の欠損率の急増）と、予測の分布（不正スコアの分布の変化）を監視していなかった。
- 決済の刷新という大きな上流の変更が、ML の担当者に共有されていなかった。

**② 根本原因**

- 技術: 未知のカテゴリを黙って「その他」に寄せる前処理、`device_id` の欠損を検知しないパイプライン、そして **壊れたデータを学習して自動で本番に出る再学習**（3 月の 3 回の日曜に、欠損した `device_id` を含むデータで学習したモデルが検証なしで本番に出た可能性がある）。
- 組織: プロダクトの変更（新しい支払い方法、決済画面の刷新）を、データや ML に影響する変更として扱う手続き（データ契約、変更の事前共有）がなかった。モデルの監視の担当者が決まっていなかった。

**③ 再発防止策**

- データ品質: 取り込みの時点で、`device_id` の欠損率・`payment_method` の許可された値をテストし、違反したら学習と推論のパイプラインを止めて通知する（[12.1](../01-data-engineering/README.md)）。
- ドリフトの監視: 重要な特徴量について PSI・カテゴリの変化・欠損率を日次で監視し、予測の分布も監視する（演習 1）。
- 再学習の安全装置: 自動で再学習したモデルは、評価データでの指標の閾値と現行モデルとの比較を満たさない限り昇格させない（演習 2）。昇格の前にシャドーで予測の分布を確認する。
- 未知の値の扱い: 学習時にない値を検知して記録し、一定量を超えたら通知する。新しい支払い方法のように不正の傾向が違うかもしれない値は、当面は人の確認や保守的なルールを併用する。
- 組織: 決済やアカウントなど、モデルの入力に関わるプロダクトの変更は、データ・ML の担当者のレビューを必須にする。モデルごとにオーナーと監視の担当を決める。
- 影響への対応: 3 月の被害額の集計、後払いの取引を対象にした暫定的なルール、経理・カスタマーサポートとの連携。

採点の観点:

- 正解の遅れ（チャージバック）のために、入力と予測の分布の監視が必要だったことを指摘できれば合格ライン。
- 自動再学習に検証がなかったこと、未知のカテゴリと欠損の扱い、プロダクトの変更をデータに影響する変更として扱う組織の仕組みまで踏み込めていれば、再発防止を主導できる水準です。

</details>

## 理解度チェック

**Q1. Sculley ほかの "Hidden Technical Debt in Machine Learning Systems" が指摘する「CACE」とは何ですか。それが運用に与える影響と対策を説明してください。**

<details>
<summary>解答</summary>

CACE は "Changing Anything Changes Everything"（何かを変えるとすべてが変わる）の略で、ML モデルでは入力の特徴量や設定が互いに絡み合っているため、1 つの特徴量の追加・削除・分布の変化が、他の特徴量の寄与やしきい値の最適値など、モデル全体の振る舞いを変えてしまうことを指します。通常のソフトウェアのように「この部分だけを変えたので、影響はここだけ」と局所化できません。

そのため、どんな小さな変更でも、評価データでの全体の再評価、区分ごとの性能の確認、シャドーやカナリアでの段階的な導入が必要です。評価と昇格の条件を自動化しておくことが、変更の速さと安全性を両立させる鍵になります。

</details>

**Q2. データドリフトとコンセプトドリフトの違いを、クレジットカードの不正検知を例に説明してください。どちらが検出しにくいですか。**

<details>
<summary>解答</summary>

- **データドリフト**: 入力の分布 P(X) が変わること。例: 新しい国での販売開始で、海外からの取引の割合が増える。入力のデータだけを見れば検出できる。
- **コンセプトドリフト**: 入力と正解の関係 P(Y|X) が変わること。例: 不正の手口が変わり、以前は安全だった特徴（少額の取引を繰り返す、など）を持つ取引が不正に使われるようになる。入力の分布は変わらないこともある。

コンセプトドリフトの方が検出しにくい。入力の分布を見ても変化が現れないことがあり、確かめるには正解（不正の確定）が必要ですが、それは数週間後にしか届きません。予測の分布の変化、人が確認した取引での正解率、利用者からの報告などの早期の兆候を組み合わせて監視します。

</details>

**Q3. PSI の計算で、ビンの境界を基準データの分位点で決め、現在のデータにも同じ境界を使うのはなぜですか。また、割合が 0 のビンに eps を使うのはなぜですか。**

<details>
<summary>解答</summary>

PSI は「同じビンに入る割合が、基準と現在でどれだけ違うか」を測る指標なので、両方に同じ境界を使わなければ比較になりません。基準データの分位点で境界を決めると、基準の各ビンにほぼ同じ数のデータが入り、どのビンの変化も同じくらいの感度で測れます（等間隔の境界では、データの少ない裾のビンが不安定になります）。

PSI の式には ln(a / e) が含まれるので、どちらかの割合が 0 だと 0 での割り算や log(0) になり、値が無限大になります。現在のデータに一度も現れないビンがあるのは珍しくないので、割合を小さな値 eps で下から抑えて、有限の値にします。eps の選び方で値が変わるので、組織内で固定して比較可能にしておきます。

</details>

**Q4. 1 日 100 万件の推論データで、200 個の特徴量のドリフトを KS 検定（有意水準 0.01）で監視したところ、毎日数十件の警告が出て、誰も見なくなりました。何が問題で、どう改善しますか。**

<details>
<summary>解答</summary>

問題は 2 つです。①標本が非常に大きいため、実務上は無視できるほど小さな分布の差でも p 値が 0.01 を下回る（統計的な有意さは、差の大きさを意味しない）。②200 個の特徴量を毎日検定しているので、ドリフトがなくても偶然の警告が出る（多重検定）。

改善策:

- 効果の大きさ（PSI、KS の D）に閾値を設け、有意さと両方を満たしたときだけ警告する。
- モデルにとって重要な特徴量に絞る（重要度の高い上位の特徴量、事業上重要な特徴量）。
- 予測の分布そのものと、正解が届いた分の性能を主な指標にし、特徴量のドリフトは原因調査の手がかりとして使う。
- 季節性を考慮した基準（同じ曜日・前年同期）を使う。
- 警告の段階を分け、即時対応が必要なものだけを呼び出しにする。

</details>

**Q5. シャドー、カナリア、A/B テストは、それぞれ何を確かめるための方法ですか。**

<details>
<summary>解答</summary>

- **シャドー**: 本番の入力を複製して新しいモデルにも流し、結果は使わない。利用者に影響を与えずに、本番のデータでの予測の分布、旧モデルとの差、遅延、エラーを確かめる。ただし、新モデルの判断が実際に使われた場合の利用者の反応は分からない。
- **カナリア**: 一部の利用者（例: 1〜5%）に新モデルを実際に使い、技術的な異常（エラー率・遅延・予測の偏り）を小さな影響範囲で早く検出する。異常があればすぐに戻す。
- **A/B テスト**: 利用者を無作為に分けて新旧のモデルを使い、事業上の効果（売上・解約率・不正の損失など）を統計的に比較する。オフラインの指標の改善が事業の改善につながるかは、ここで確かめる。

</details>

**Q6. 自動再学習のパイプラインで、再学習したモデルを検証なしに本番へ出すと、どんな事故が起こりえますか。どんな安全装置を置くべきですか。**

<details>
<summary>解答</summary>

上流のデータの障害（欠損の急増、単位の変更、重複、ラベルの遅延による欠落）があると、壊れたデータで学習したモデルが自動で本番に出て、予測の品質が大きく下がります。フィードバックループがあると、劣化したモデルの判断が次の学習データをさらに歪めます。誰も変更していないのに品質が落ちるので、原因の特定にも時間がかかります。

安全装置: ①学習データの品質のテスト（件数・欠損・値の範囲）で、異常なら学習を止める、②評価データでの指標の閾値と、現行の本番モデルとの比較を昇格の条件にする（演習 2）、③昇格の前にシャドーで予測の分布を確認する、④問題が起きたらすぐに前の版に戻せるようにする（ロールバック）、⑤すべての版の系譜を記録する。

</details>

**Q7. LLM を使うシステムで、プロンプトの変更と提供元のモデルの版の更新を、どのように管理すべきですか。**

<details>
<summary>解答</summary>

- プロンプト・生成のパラメータ・検索の設定・ツールの定義を、コードと同じくバージョン管理し、レビューを経て変更する。
- 本番では、提供元のモデルを日付などで固定された版の識別子で指定し（提供されている場合）、「最新版」を指す別名に任せない。
- 変更（プロンプトの修正、モデルの版の移行）は、評価データを使った回帰テストを CI で実行し、悪化していればリリースを止める。平均だけでなく、個別に悪化した事例を確認する（[12.4](../04-llm-applications/README.md)）。
- 本番では、どのプロンプトの版とモデルの版の組み合わせで応答したかをトレースに記録し、問題が起きたときに追跡できるようにする。
- 提供元のモデルの廃止予定を追跡し、期限までに評価と移行を終える計画を立てる。

</details>

**Q8. 自社で LLM を動かす GPU を 5 枚、ピークに合わせて確保しました。夜間と週末は利用がほとんどなく、平均稼働率は 30% です。トークンあたりの費用はどうなり、どんな対策が考えられますか。**

<details>
<summary>解答</summary>

GPU の費用は稼働率に関係なく時間単位でかかるので、トークンあたりの費用は稼働率に反比例します。平均稼働率 30% では、80% の場合の約 2.7 倍（80 / 30）になります（本文の仮定では 100 万トークンあたり 83 円に対して 222 円）。

対策:

- 需要の少ない時間帯に台数を減らす（ただし、重みの読み込みに時間がかかるので最低台数と起動時間を考慮する）。
- 即時性の不要な処理（要約・分類・データの加工）を夜間に回し、遊んでいる時間帯の稼働率を上げる。
- 量子化や小さなモデルへの置き換えで、1 枚あたりの処理量を増やす。
- 利用量の少ない用途や、ピークだけを API に回す（ゲートウェイでのルーティング）。
- 自社運用と API の費用を、稼働率を含めて定期的に比較し直す。

</details>

## まとめ

- ML のコードは ML システムのごく一部で、データ依存・フィードバックループ・設定・グルーコードといった隠れた技術的負債が周辺にたまる。変更のたびの再評価と、依存関係の管理が欠かせない。
- 再現性は「データ・コード・設定・環境」の記録から生まれる。特徴量の定義の一元化で学習と推論の不一致を防ぎ、モデルレジストリで版・昇格の条件・承認・ロールバック・監査を管理する。
- デプロイはバッチかオンラインかを鮮度の必要性で選び、シャドー → カナリア → A/B テストの段階を踏んで安全に切り替える。
- モデルは入力の分布・入力と正解の関係・上流のデータの変化によって静かに劣化する。PSI・KS 検定・カイ二乗検定で分布を監視し、効果の大きさと有意さ・多重検定・季節性に注意して警告を設計する。正解の遅れとフィードバックループを前提にする。
- 自動再学習は必ず昇格の条件を通す。壊れたデータで学習したモデルを自動で本番に出さない。
- LLMOps では、プロンプト・モデルの版・設定をコードとして管理し、評価を CI に組み込み、トレースで要求ごとの振る舞いと費用を記録する。AI ゲートウェイでルーティング・フォールバック・予算・キャッシュ・監査を集約する。
- 自社運用の推論は、continuous batching と KV キャッシュの管理で効率が決まり、費用は稼働率に反比例する。モデルカード・人の監督・AI インシデントの手順・単位あたりの費用の管理で、責任を持って運用し続ける。
