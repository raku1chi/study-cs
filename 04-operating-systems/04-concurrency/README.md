## なぜ学ぶのか

並行処理のバグは、条件がそろったときにだけ現れ、再現が難しく、ときに深刻な結果を招きます。

- **Therac-25（1985〜1987 年）**: 放射線治療装置 Therac-25 は、ソフトウェアの欠陥によって 6 件の大量過剰照射事故を起こし、死者も出ました。Leveson と Turner の調査報告（IEEE Computer、1993 年）は、オペレーターが素早く入力を修正すると、装置の実際の設定と画面の表示が食い違ってしまう競合状態などを原因として挙げています。ハードウェアの安全装置をソフトウェアの制御に置き換えたことも被害を大きくしました。
- **北米大停電（2003 年）**: 米国とカナダの約 5,000 万人に影響した大停電では、電力会社の監視システムの警報機能が停止していたために、運用者が状況の悪化に気づくのが遅れました。米加合同の調査委員会の報告書などによれば、警報ソフトウェアの停止には競合状態のバグが関わっていたとされています。
- **Mars Pathfinder（1997 年）**: 火星に着陸した探査機が、原因不明のシステムリセットを繰り返しました。原因は、優先度の低いタスクがロックを持ったまま、中程度の優先度のタスクに割り込まれ続け、同じロックを待つ最高優先度のタスクが動けなくなる **優先度逆転** でした。地上から設定を変更して修正されたこの事例は、4.5 節で詳しく見ます。

これらは特殊な分野の話ではありません。在庫の二重引き当て、残高の不整合、キャッシュの破損、深夜の謎のハングといった日常的な障害も、同じ原理から生まれます。

## 1. 並行と並列

### 1.1 並行（concurrency）と並列（parallelism）

2 つの言葉は混同されがちですが、意味が違います。

- **並行（concurrency）**: 複数の仕事を、重なり合った期間に進める **構造** のこと。1 つの CPU でも、仕事を細かく切り替えれば並行に進められる（4.1 の時分割）。
- **並列（parallelism）**: 複数の仕事を、**物理的に同時に** 実行すること。複数の CPU コアが必要。

Go 言語の設計者の 1 人である Rob Pike の講演のタイトル "Concurrency is not Parallelism"（2012 年）のとおり、並行は「多くのことを扱う方法」、並列は「多くのことを同時に行うこと」です。例えば Python の asyncio は、1 つのスレッドで多数の接続を並行に扱いますが、並列には実行しません。

### 1.2 なぜ並行・並列にするのか

- **待ち時間を隠す**: ネットワークやディスクの応答を待つ間に、他の仕事を進める（Web サーバーの大半の時間は待ち時間）。
- **応答性**: 重い処理の最中でも、画面の操作や他の利用者の要求に応える。
- **計算を速くする**: 複数のコアで計算を分担する。

ただし、並列化で速くなるのは並列化できる部分だけです。プログラムのうち並列化できる割合を p、コア数を n とすると、速度向上の上限は **アムダールの法則（Amdahl's law）** で `1 / ((1 − p) + p / n)` と表されます。

| 並列化できる割合 p | 2 コア | 4 コア | 16 コア | 64 コア | 1024 コア |
|---|---|---|---|---|---|
| 50% | 1.3 倍 | 1.6 倍 | 1.9 倍 | 2.0 倍 | 2.0 倍 |
| 90% | 1.8 倍 | 3.1 倍 | 6.4 倍 | 8.8 倍 | 9.9 倍 |
| 99% | 2.0 倍 | 3.9 倍 | 13.9 倍 | 39.3 倍 | 91.2 倍 |

90% を並列化できても、コアを 1,024 個に増やして 10 倍にもなりません。ロックで守られた部分（クリティカルセクション）は並列化できない部分そのものなので、**ロックの中で過ごす時間を短くすることが、スケールするプログラムの鍵** になります。

## 2. 競合状態

### 2.1 read-modify-write と更新の喪失

複数のスレッドが同じデータを読み書きし、結果が実行のタイミングによって変わってしまう状況を **競合状態（race condition）** と呼びます。最も典型的なのが、「読んで、計算して、書く」という **read-modify-write** の途中に、他のスレッドが割り込む場合です。

```python
import threading
import time

balance = 0

def deposit_many(n):
    global balance
    for _ in range(n):
        current = balance        # (1) 読む
        time.sleep(0)            # ここで他のスレッドに切り替わりうる（I/O や関数呼び出しの代わり）
        balance = current + 1    # (2) 書く

threads = [threading.Thread(target=deposit_many, args=(10_000,)) for _ in range(4)]
for t in threads:
    t.start()
for t in threads:
    t.join()
print("期待値 40000, 実際:", balance)
```

```text
期待値 40000, 実際: 10000
```

4 つのスレッドがそれぞれ 1 万回入金したのに、残高は 1 万しかありません。あるスレッドが (1) で読んだ後、(2) で書くまでの間に、他のスレッドが同じ古い値を読んで書くため、更新が次々に上書きされて消えたのです（**更新の喪失、lost update**）。実行するたびに結果は変わります。

### 2.2 GIL があっても安全ではない

CPython には **GIL（Global Interpreter Lock）** があり、一度に 1 つのスレッドしか Python のバイトコードを実行しません。そのため「Python ではスレッドの競合は起きない」と誤解されがちですが、GIL が守るのはインタプリタ自身の内部構造であって、**あなたのプログラムの複数の手順をまとめて守るわけではありません**。上の例のように、手順の間でスレッドが切り替われば、更新は失われます。

興味深いことに、この環境の Python 3.10・3.11 で、単純なループの `counter += 1` を 4 スレッドで 100 万回ずつ実行すると、何度試しても 4,000,000 になりました。CPython がスレッドを切り替えるのは実装上の限られたタイミングだけなので、この単純な形ではたまたま分割されないのです。しかしこれは **言語の保証ではありません**。Python のバージョンや、関数呼び出しを挟むかどうか、GIL のない free-threaded ビルド（7.3 節）で結果は変わります。**テストで再現しないことは、正しいことの証明にはならない** という、並行処理の最も重要な教訓の 1 つです。

### 2.3 check-then-act

もう 1 つの典型が、「確認してから行動する（**check-then-act**）」の間に状況が変わる競合です。

```python
if key not in cache:            # 確認
    cache[key] = compute(key)   # 行動: 他のスレッドも同時に「ない」と判断して、二重に計算しうる
```

- **在庫の引き当て**: 「在庫が 1 以上あるか確認 → 1 減らす」を 2 人が同時に行うと、在庫 1 個に 2 件の注文が入る。
- **一意性の確認**: 「このメールアドレスは未登録か確認 → 登録」では、同時の 2 件の登録が両方通る。データベースの一意制約（[6.3](../../06-databases/03-transactions/README.md)）で守るのが正解。
- **ファイル**: 「ファイルが存在しないことを確認 → 作成」の間に、攻撃者がシンボリックリンクを作ると、意図しないファイルを上書きさせられる（**TOCTOU**、Time Of Check to Time Of Use の脆弱性）。`O_CREAT | O_EXCL` のように、確認と行動を 1 つの原子的な操作にするのが正解。

どれも対策は同じで、**確認と行動を 1 つの原子的な操作にする**（ロックで囲む、DB の条件付き更新や制約を使う、OS の原子的なフラグを使う）ことです。

### 2.4 データ競合と競合状態

似た言葉に **データ競合（data race）** があります。これは「複数のスレッドが同じメモリ位置に同期なしでアクセスし、少なくとも 1 つが書き込み」という、より低いレベルの定義で、C・C++・Go などでは **未定義の動作**（何が起きても文句を言えない）になります。

- データ競合があっても、アプリの結果としては問題にならない場合もある（統計用のカウンタの多少のずれなど。ただし C・C++ では未定義動作なので、それでも避けるべき）。
- データ競合がなくても、競合状態は起きる。2.1 の例で、読みと書きをそれぞれ個別にロックで守っても、その間に割り込まれれば更新は失われる。

**ロックで守るべき単位は「メモリへのアクセス」ではなく「不変条件（invariant）が壊れている期間」** です。「残高の読みと書き」「在庫の確認と減算」をひとまとまりで守らなければなりません。

### 2.5 すべてのインターリーブを数える

2.1 の `x += 1` は、read・inc・write の 3 つの手順に分かれます。2 つのスレッドがこれを実行するとき、各スレッドの中の順序を保ったまま手順を 1 列に並べる方法（**インターリーブ**）は、6 個の手順から 3 個の位置を選ぶ組み合わせで 20 通りあります。演習5で作る探索器で、20 通りすべてを実行してみます（解答例による実際の出力）。

```python
from interleave import explore, increment_program

print(explore([increment_program("x"), increment_program("x")], {"x": 0}))
print(explore([increment_program("x", lock="L")] * 2, {"x": 0}))
```

```text
ExploreResult(outcomes=Counter({(('x', 1),): 18, (('x', 2),): 2}), deadlocks=0, schedules=20)
ExploreResult(outcomes=Counter({(('x', 2),): 2}), deadlocks=0, schedules=2)
```

20 通りのうち、正しく 2 になるのは「一方がもう一方の完了後に読む」2 通りだけで、残りの 18 通りでは更新が失われます。ロックで囲むと、実行可能な並びは 2 通りに減り、結果は常に 2 になります。実際のスレッドのテストでは、この 18 通りに当たるかどうかが運次第ですが、網羅的に探索すれば確実に見つかります（8 節）。ただし、3 スレッドがそれぞれ 10 手順を実行するだけでインターリーブは 5 兆通りを超えるので、実用的なツールは、結果に影響しない並べ替えを省く工夫をしています。

## 3. 同期プリミティブ

### 3.1 クリティカルセクションとミューテックス

共有データにアクセスし、同時に 1 つのスレッドしか実行してはいけない区間を **クリティカルセクション（critical section）** と呼びます。これを守る最も基本的な道具が **ミューテックス（mutex、相互排他ロック）** です。

```python
lock = threading.Lock()

def deposit(amount):
    global balance
    with lock:                  # 入るときに取得、出るときに必ず解放（例外が起きても）
        balance = balance + amount
```

ロックの設計では **粒度** がトレードオフになります。1 つの大きなロック（粗い粒度）は正しく書きやすいが、同時に 1 つしか進めないので並列度が出ません。データごとの細かいロック（細かい粒度）は並列度が上がりますが、複数のロックを取る場面でデッドロック（4 節）の危険が生まれます。まずは粗い粒度で正しく作り、測定して、競合が本当にボトルネックになっている箇所だけを細かくするのが定石です。

Linux のミューテックス（glibc の pthread_mutex）は **futex** という仕組みで実装されています。競合がなければユーザー空間のアトミック操作だけでロックを取り、競合したときだけシステムコールでカーネルに眠らせてもらいます。そのため、競合のないロックの取得は非常に安く、**高価なのは「競合したロック」** です。

### 3.2 アトミック操作と CAS

CPU は、いくつかの操作を分割されない 1 つの操作（**アトミック操作**）として実行する命令を持っています。中でも重要なのが **CAS（Compare-And-Swap）** です。

```text
CAS(アドレス, 期待する値, 新しい値):
    原子的に: 現在の値 == 期待する値 なら、新しい値を書いて成功を返す。違えば何もせず失敗を返す。
```

x86 の `lock cmpxchg` 命令や、ARM の排他的ロード／ストア命令がこれにあたります。CAS を使うと、ロックなしでカウンタを増やせます。

```python
# 擬似コード（Python には、ユーザーが直接使える CAS はありません）
while True:
    old = counter.load()
    if counter.compare_and_swap(old, old + 1):   # 他のスレッドに先を越されていなければ成功
        break                                    # 失敗したら、読み直してやり直す（CAS ループ）
```

Java の `AtomicLong`、Go の `sync/atomic`、C++ の `std::atomic` は、この命令を言語から使えるようにしたものです。単純なカウンタやフラグにはロックよりアトミック操作が適していますが、複数の値をまとめて一貫して更新するには向きません。

ロックを取れないときに、CPU を回しながら待つ **スピンロック** と、眠って待つ **ブロッキングなロック** の選択もあります。待ち時間がコンテキストスイッチ（4.1 で測った約 1 マイクロ秒）より十分短いと分かっている場合だけ、スピンが有利です。

### 3.3 セマフォ

**セマフォ（semaphore）** は、「残りの許可の数」を持つカウンタで、取得（P、acquire）で 1 減らし（0 なら待つ）、解放（V、release）で 1 増やします。Dijkstra が 1960 年代に考案した、最も古い同期プリミティブの 1 つです。**同時に実行してよい数を N 個に制限する** ときに使います（DB の接続プール、外部 API への同時リクエスト数、演習4の並行数制限）。許可が 1 つのセマフォはミューテックスに似ていますが、ミューテックスには「取ったスレッドが解放する」という所有者の概念がある点が違います。

### 3.4 条件変数

「キューが空でなくなるまで待つ」のように、**ある条件が成り立つまで待つ** には **条件変数（condition variable）** を使います。条件変数は必ずミューテックスと組み合わせて使い、`wait()` は「ロックを手放して眠り、起こされたらロックを取り直してから戻る」を原子的に行います。演習1の有界ブロッキングキューの骨格は次の形です。

```python
def get(self):
    with self._not_empty:              # 条件変数に対応するロックを取る
        while not self._items:         # if ではなく while で確かめる
            self._not_empty.wait()     # ロックを手放して眠る → 起きたらロックを取り直す
        item = self._items.popleft()
        self._not_full.notify()        # put で待っている誰かを起こす
        return item
```

**条件は必ず `while` で確かめ直します**。起こされたときに条件が成り立っているとは限らないからです。他の消費者に先を越されたかもしれませんし、多くの実装では、誰も notify していないのに起きる **見せかけの起床（spurious wakeup）** も規格上許されています。`if` で書いたコードは、テストではまず失敗せず、負荷の高い本番でだけ壊れます。

`notify()`（1 人だけ起こす）と `notify_all()`（全員起こす）の選択も重要です。待っている全員が同じ条件を待っているなら `notify()` で十分ですが、異なる条件を 1 つの条件変数で待たせていると、`notify()` で「その条件とは関係のないスレッド」だけが起きて、本来起きるべきスレッドが眠り続けることがあります。迷ったら `notify_all()` の方が安全です（その代わり、無駄な起床が増えます）。

### 3.5 読み書きロック

読み取りだけなら同時に行っても問題ないので、「読み手は何人でも同時に、書き手は 1 人だけで、その間は誰も入れない」という **読み書きロック（read-write lock）** が使われます。読み取りが大半を占めるデータ（設定、キャッシュ）で並列度を上げられます。

ここで、読み手と書き手のどちらを優先するかという問題が生じます。読み手を優先すると、読み手が途切れない限り書き手は永遠に入れません（**飢餓、starvation**）。書き手を優先すると（演習2）、書き手が待っている間は新しい読み手が待たされます。また、クリティカルセクションが短い場合は、読み書きロックの管理のコストの方が高くつき、普通のミューテックスより遅くなることもあります。**測定してから** 採用しましょう。

### 3.6 使い分け

| 道具 | 用途 | 注意点 |
|---|---|---|
| ミューテックス | 共有データをひとまとまりで守る | 粒度、ロック中の I/O、デッドロック |
| アトミック操作（CAS） | 単純なカウンタ・フラグ・ポインタ | 複数の値の整合は守れない |
| セマフォ | 同時実行数の制限 | 解放し忘れで許可が減っていく |
| 条件変数 | 条件が成り立つまで待つ | 必ず while で確かめる。notify の選択 |
| 読み書きロック | 読み取りが大半のデータ | 飢餓。短い区間ではかえって遅い |
| キュー・チャネル | スレッド間でデータを受け渡す | 有界にして背圧をかける（無制限のキューはメモリを食い尽くす） |

## 4. デッドロック・ライブロック・スタベーション

### 4.1 デッドロックの 4 条件

**デッドロック（deadlock）** は、複数のスレッドが互いに相手の持つ資源を待ち、永遠に進めなくなる状態です。Coffman らは 1971 年に、デッドロックが起きるのは次の 4 条件が **すべて** 成り立つときだと整理しました。

1. **相互排他**: 資源は同時に 1 つのスレッドしか使えない。
2. **保持と待機**: 資源を持ったまま、別の資源を待つ。
3. **横取り不可**: 他のスレッドが持つ資源を強制的に奪えない。
4. **循環待ち**: 待ちの関係が輪になっている（T1 が T2 を待ち、T2 が T1 を待つ）。

逆に言えば、どれか 1 つを崩せばデッドロックは起きません。実務で最もよく使われるのは 4 を崩す方法です。

### 4.2 防ぐ: ロックの順序付けとタイムアウト

2 つのスレッドが、2 つのロックを逆の順序で取ろうとすると、デッドロックします。

```python
import threading
import time

lock_a, lock_b = threading.Lock(), threading.Lock()

def worker(name, first, second, first_name, second_name):
    with first:
        time.sleep(0.1)                       # 相手が自分の 1 つ目のロックを取る時間を与える
        if second.acquire(timeout=1):         # タイムアウトなしなら、ここで永遠に止まる
            second.release()
            print(f"{name}: 両方のロックを取れた")
        else:
            print(f"{name}: {first_name} を持ったまま {second_name} を 1 秒待ったが取れない")

t1 = threading.Thread(target=worker, args=("T1", lock_a, lock_b, "A", "B"))
t2 = threading.Thread(target=worker, args=("T2", lock_b, lock_a, "B", "A"))
t1.start(); t2.start(); t1.join(); t2.join()
```

```text
T1: A を持ったまま B を 1 秒待ったが取れない
T2: 両方のロックを取れた
```

T1 は A を持って B を、T2 は B を持って A を待ち、循環待ちになりました。タイムアウトがあったので、先に諦めた T1 が A を手放し、T2 が進めました（どちらが諦めるかはタイミング次第です）。タイムアウトは「横取り不可」を実質的に崩す方法ですが、諦めた側の処理は失敗するので、やり直しの設計が必要です。

根本的な対策は **ロックの順序付け（lock ordering）** です。すべてのコードで「ロックは必ず決められた順序（例えば口座 ID の小さい順）で取る」と決めれば、循環待ちは起こりえません。演習3の送金関数はこの方法で実装します。ほかにも、次の方法があります。

- **一度に全部取る、または 1 つも取らない**: 必要なロックを最初にまとめて取り、取れなければすべて手放してやり直す（「保持と待機」を崩す）。
- **ロックを持ったまま、正体の分からないコードを呼ばない**: コールバックやプラグイン、ログ出力のフックの中で別のロックが取られると、順序の規則が破られる。
- **そもそも共有しない**: データを 1 つのスレッドだけに持たせ、他のスレッドはメッセージで依頼する（7 節）。

### 4.3 見つける: 待ちグラフ

防ぐのが難しい場合は、デッドロックを **検出して回復** します。「どのスレッドがどのスレッドを待っているか」を辺にした **待ちグラフ（wait-for graph）** に循環があれば、デッドロックです。

```mermaid
flowchart LR
  T1["トランザクション T1"] -->|"行 B のロックを待つ"| T2["トランザクション T2"]
  T2 -->|"行 C のロックを待つ"| T3["トランザクション T3"]
  T3 -->|"行 A のロックを待つ"| T1
```

データベースはこれを実際に行っています。PostgreSQL は、ロックを一定時間（`deadlock_timeout`、既定 1 秒）待ったトランザクションについて待ちグラフを調べ、循環があればその 1 つを中断して `deadlock detected` のエラーを返します。MySQL の InnoDB も既定でデッドロックを検出し、一方のトランザクションをロールバックします。つまり、**データベースを使うアプリは、デッドロックによるトランザクションの失敗を、再試行すべき正常なエラーとして扱う必要がある** のです（[6.3](../../06-databases/03-transactions/README.md)）。演習3では、ロックの保持と待ちの表から待ちグラフを作り、循環を見つける関数を実装します。

### 4.4 ライブロックと飢餓

- **ライブロック（livelock）**: スレッドは動き続けているのに、互いに譲り合って（あるいは同じタイミングでやり直して）誰も先に進まない状態。廊下で向かい合った 2 人が同じ側に避け続けるようなものです。タイムアウト後の再試行を全員が同じ間隔で行うと起きやすく、**ランダムな待ち時間（ジッター）付きの指数バックオフ** で解消します。Ethernet の衝突時の再送や、分散システムの再試行（[7.1](../../07-distributed-systems/01-fundamentals/README.md)）でも同じ考え方を使います。
- **飢餓（starvation）**: 特定のスレッドだけが、いつまでも資源をもらえない状態。読み手優先の読み書きロックの書き手や、4.1 のスケジューリングの低優先度のタスクがその例です。公平なキュー（到着順）やエージングで防ぎます。

### 4.5 優先度逆転と Mars Pathfinder

優先度付きのスケジューリングとロックが組み合わさると、**優先度逆転（priority inversion）** が起きることがあります。Mars Pathfinder で起きたことを簡略化して示します。

```text
優先度
  高  H: ............[ロック待ち ─────────────── 期限までに実行されず、ウォッチドッグがリセット]
  中  M: ..................[██████████ 長い処理（ロックは使わない）██████████]
  低  L: [██ ロック取得 ██][ M に横取りされて進めない …………………………… ][解放]
         時刻 →
```

1. 低優先度のタスク L が、共有データ（Pathfinder では「情報バス」）を守るミューテックスを取った。
2. 高優先度のタスク H が同じミューテックスを待つ。ここまでは想定内で、L がすぐに解放すれば問題ない。
3. ところが、ロックと無関係な中優先度のタスク M が動き出し、L より優先度が高いので L を横取りし続けた。L はロックを解放できず、結果として **H が M に待たされる**（優先度が逆転する）。
4. H が期限内に動かないことをウォッチドッグが検出し、システム全体をリセットした。

対策は **優先度継承（priority inheritance）** です。高優先度のタスクが待っているロックを持つタスクは、一時的にその高い優先度を受け継ぐので、M に横取りされずにすぐロックを解放できます。Pathfinder が使っていたリアルタイム OS（VxWorks）にはこの機能がありましたが、該当のミューテックスでは無効になっていました。JPL の技術者は、地上のテスト機で問題を再現して原因を突き止め、探査機に設定の変更を送って修正しました。Linux も、リアルタイム用途向けに優先度継承付きのロック（PI futex）を備えています。

## 5. メモリモデルと可視性

ここまでは「手順がどの順で実行されるか」を考えてきましたが、実はもっと厄介な問題があります。**あるスレッドの書き込みが、他のスレッドからいつ・どの順で見えるか** です。

CPU は性能のために、書き込みをいったんコアごとの書き込みバッファに溜めたり、命令の順序を入れ替えたりします。コンパイラも、1 つのスレッドの結果が変わらない範囲で、読み書きの順序を入れ替えたり、値をレジスタに置きっぱなしにしたりします。1 つのスレッドから見ると何も変わりませんが、他のスレッドからは次のようなことが起こりえます（擬似コード）。

```text
初期値: data = 0, ready = false

スレッド 1:                スレッド 2:
  data = 42                  while not ready: pass
  ready = true               print(data)      # 0 が表示されうる！
```

スレッド 2 が `ready` の更新を見たのに、`data` の更新がまだ見えないことがあります（ARM のように順序の保証が弱い CPU や、コンパイラの最適化による）。x86 は比較的強い順序を保証しますが、それでも「書き込みの後の、別の場所からの読み込み」が先に行われることがあります（[1.3](../../01-computer-systems/03-memory-hierarchy/README.md) のキャッシュの一貫性は「同じアドレス」の話で、「異なるアドレスの間の順序」は保証しません）。

このため、各言語は **メモリモデル** を定め、「どの操作の後なら、どの書き込みが見えることを保証するか」を **happens-before（先行発生）** という関係で規定しています（この言葉は Lamport の 1978 年の論文に由来します）。

- ロックの解放は、同じロックの次の取得に happens-before する（ロックの中で書いたものは、次にロックを取った人から見える）。
- スレッドの開始（start）と終了の待ち合わせ（join）も happens-before を作る。
- **Java** は `volatile` 変数（JSR-133、Java 5 で規定し直された）、**C++** は `std::atomic` とメモリオーダー、**Go** は `sync` パッケージとチャネル（「チャネルへの送信は、対応する受信の完了より前に起きる」）で、この関係を作る。

実務上の結論は単純です。**スレッド間で共有するデータは、ロック・アトミック変数・チャネル・スレッドセーフなキューのいずれかを通して受け渡す**。「ただのフラグだから」と普通の変数で済ませると、あるスレッドがいつまでも古い値を見続ける（ループが終わらない）といった、再現しにくい不具合になります。Java で有名な「ダブルチェックロッキング」による遅延初期化は、`volatile` なしでは正しく動かないことが知られています。

## 6. ロックフリーと ABA 問題

CAS を使って、ロックを使わずにキューやスタックを実装する技法を **ロックフリー（lock-free）** プログラミングと呼びます。どのスレッドが止まっても（ロックを持ったまま眠ることがないので）システム全体としては必ず誰かが前に進める、という性質を持ちます。JVM や Go のランタイム、高性能なキューの内部で使われています。

ただし、正しく書くのは非常に難しいことで知られています。代表的な落とし穴が **ABA 問題** です。スレッド 1 がポインタの値 A を読み、CAS で置き換えようとする間に、他のスレッドが A → B → A と変更すると、スレッド 1 の CAS は「変わっていない」と判断して成功してしまいます。その A が一度解放されて再利用された別のノードだったら、データ構造は壊れます。バージョン番号を組み合わせる、使い終わったメモリの再利用を遅らせる（ハザードポインタ、エポックに基づく回収）といった対策が必要です。**ロックフリーのデータ構造は、自分で書かずに実績のあるライブラリを使う** のが原則です。

## 7. 並行処理のモデル

### 7.1 スレッドプールとサイズの見積もり

スレッドを仕事のたびに作ると生成のコストがかかり、数が際限なく増えるとメモリとコンテキストスイッチで破綻します。そこで、決まった数のスレッドを用意して仕事のキューから取り出させる **スレッドプール** を使います。何本にすべきかは、仕事の性質で決まります。

- **CPU を使う仕事**: コア数程度（それ以上増やしても切り替えが増えるだけ）。
- **I/O を待つ仕事**: Goetz らの "Java Concurrency in Practice" の目安では、`スレッド数 ≒ コア数 × 目標 CPU 使用率 × (1 + 待ち時間 / 計算時間)`。

より直接的な見積もりには、[2.2](../../02-math-and-algorithms/02-probability-statistics/README.md) の **リトルの法則** `L = λW`（系の中にある平均の数 = 到着率 × 滞在時間）が使えます。毎秒 400 件のリクエストが来て、1 件の処理に平均 50 ミリ秒（計算 10 ミリ秒 ＋ 外部 API の待ち 40 ミリ秒）かかるなら、同時に処理中のリクエストは平均 400 × 0.05 = 20 件です。スレッドプールや DB の接続プールがこれより小さければキューが伸び続け、ばらつきを考えるとピーク時にはこの数倍の余裕が要ります。逆に、下流（DB や外部 API）が同時に捌ける数より大きくしても、下流で待たされるだけです。**並行数は「上流からの到着」と「下流の処理能力」の両方から決める** ものであり、上限を超えた分はキューで待たせるか、早めに断る（背圧、[9.5](../../09-architecture/05-scalability-and-performance/README.md)）必要があります。

### 7.2 async/await とイベントループ

[4.3](../03-filesystems-and-io/README.md) のイベントループを、言語の構文で書きやすくしたのが **async/await** です。`await` は「ここで待つ間、イベントループに制御を返してよい」という印で、タスクは `await` の地点でだけ切り替わります（**協調的マルチタスク**）。スレッドと違って切り替わる場所が明示されるので、`await` を挟まない一連の処理は他のタスクに割り込まれません。

その代わり、**イベントループの中でブロックする処理を 1 つでも呼ぶと、すべてのタスクが止まります**。

```python
import asyncio
import time

async def handler_blocking(i):
    time.sleep(0.1)              # ブロックする呼び出し: イベントループごと止まる
    return i

async def handler_async(i):
    await asyncio.sleep(0.1)     # await: 待っている間、ループは他のタスクを進める
    return i

async def main():
    for handler in (handler_blocking, handler_async):
        t0 = time.perf_counter()
        await asyncio.gather(*(handler(i) for i in range(10)))
        print(f"{handler.__name__:16}: 10 件で {time.perf_counter() - t0:.2f} 秒")

asyncio.run(main())
```

```text
handler_blocking: 10 件で 1.00 秒
handler_async   : 10 件で 0.10 秒
```

`time.sleep` の代わりに、同期的な HTTP クライアント（requests など）、同期的なデータベースドライバ、重い計算（JSON の巨大なパース、画像処理）を呼んでも同じことが起きます。対策は、非同期版のライブラリを使うこと、避けられないブロッキング処理は `asyncio.to_thread()` や `loop.run_in_executor()` でスレッドプールに逃がすこと、CPU を使う処理はプロセスプールに逃がすことです。また、`asyncio.gather` は渡した仕事をすべて同時に始めるので、1 万件の API 呼び出しをそのまま渡すと、相手のサーバーや接続プールを溢れさせます。演習4では、並行数を制限しつつ結果の順序を保つ関数を実装します。

### 7.3 Python の GIL と free-threaded ビルド

GIL のため、CPython のスレッドは、Python のコードを複数のコアで同時に実行できません。ただし、I/O を待つ間や、NumPy などの C 拡張が重い計算をする間は GIL が解放されるので、I/O 中心の処理や、そうしたライブラリを使う処理ではスレッドも有効です。純粋な Python の CPU 計算を並列化するには、複数のプロセス（`multiprocessing`、`concurrent.futures.ProcessPoolExecutor`）を使うのが従来の定石でした。

この状況は変わりつつあります。PEP 703（2023 年に受理）に基づき、Python 3.13 では GIL を持たない **free-threaded ビルド** が実験的に提供され、3.14 では正式にサポートされる段階に進みました。ただし 2026 年時点でも既定のビルドは GIL ありで、C 拡張の対応状況にもばらつきがあります（最新の状況は公式ドキュメントで確認してください）。free-threaded ビルドでは、2.2 節で「たまたま」動いていたコードが本当に壊れうるので、共有データを正しく同期することの重要性はむしろ増します。

### 7.4 Go の goroutine とチャネル

Go は、ランタイムが多数の **goroutine** を少数の OS スレッドに割り当てる M:N スケジューリングを採用しています（4.1）。goroutine は数 KB 程度の小さなスタックから始まって必要に応じて伸びるので、数十万個を作ることも珍しくありません。I/O で待つ goroutine は OS スレッドを占有せず、ランタイムが内部でイベントループ（epoll など）を使って待ちます。つまり、**スレッドの書きやすさと、イベントループの効率を両立** しています。

Go は共有メモリとロック（`sync.Mutex`）も使えますが、推奨されるのは **チャネル** によるメッセージの受け渡しです。「メモリを共有することで通信するのではなく、通信することでメモリを共有せよ」という Go のことわざのとおり、データの所有権をチャネルで受け渡し、同時に 1 つの goroutine だけがデータに触れるようにします。この考え方は、Hoare の CSP（Communicating Sequential Processes、1978 年）に由来します。

### 7.5 アクターモデル

**アクターモデル** では、各アクターが自分だけの状態とメールボックスを持ち、他のアクターとはメッセージでのみやり取りします。アクターは 1 通ずつメッセージを処理するので、自分の状態にロックは要りません。Erlang/OTP は、軽量なプロセスをアクターとして大量に動かし、「失敗したプロセスは素直に落とし（let it crash）、監視役（スーパーバイザ）が再起動する」という設計で、高い可用性を実現してきました。JVM では Akka が代表的な実装です（2022 年にライセンスが変更され、Apache Pekko としてフォークされました）。アクターモデルは、メッセージが届かない・遅れる・重複するといった分散システムの性質と相性がよく、第7部への橋渡しになります。

### 7.6 構造化並行性

`threading.Thread(...).start()` や `asyncio.create_task()` で「投げっぱなし」にしたタスクは、誰がその完了を待ち、誰がその例外を受け取り、呼び出し元がキャンセルされたら誰が止めるのかが曖昧になります。例外が握りつぶされ、終了処理の後もタスクが動き続け、リソースが漏れる原因になります。

**構造化並行性（structured concurrency）** は、「タスクは、それを起動したコードのブロック（スコープ）の中で必ず終わる」という規律です。ブロックを抜けるときには子タスクがすべて完了しており、1 つが失敗したら残りをキャンセルして、例外を呼び出し元に伝えます。Nathaniel J. Smith のエッセイ "Notes on structured concurrency, or: Go statement considered harmful"（2018 年）で広まった考え方で、Python の Trio のナーサリ、asyncio の `TaskGroup`（Python 3.11 以降）、Kotlin のコルーチンスコープなどに取り入れられ、Java でもプレビュー機能として導入が進んでいます（2026 年時点）。演習4の「1 つが失敗したら残りをキャンセルする」振る舞いも、この考え方に沿っています。

## 8. 並行処理のバグを見つける

並行処理のバグは、特定のタイミングでしか現れないので、「1,000 回テストして通った」ことは正しさの証明になりません。いくつかの方法を組み合わせます。

| 方法 | 内容 | 例 |
|---|---|---|
| 設計で避ける | 共有する可変データを減らす（不変データ、メッセージの受け渡し、DB の制約や原子的な操作に任せる） | 7.4、7.5 |
| 網羅的な探索 | あり得る実行順序を系統的に試す | 演習5、Java の jcstress、Rust の loom、Microsoft Research の CHESS、設計レベルなら TLA+（[7.4](../../07-distributed-systems/04-consensus-and-coordination/README.md)） |
| ストレステスト | 多数のスレッドで長時間、ランダムな待ちを挟んで実行し、不変条件を検査する | 演習1〜3 のテスト |
| レース検出器 | 実行時にメモリアクセスを監視し、同期のない同時アクセス（データ競合）を報告する | ThreadSanitizer（C/C++）、Go の `go test -race`（ThreadSanitizer に基づく） |
| 本番での診断 | ハングしたプロセスの全スレッドのスタックを取得する | Java の `jstack`、Python の `py-spy dump`、Go の pprof の goroutine ダンプ |

そして、どの方法でも役立つのが **タイムアウト** です。ロックの取得、キューの待ち、外部呼び出しのすべてにタイムアウトを付けておけば、デッドロックは「永遠のハング」ではなく「エラーとログ」として現れ、調査の手がかりが残ります。

ここまで扱ったことは、1 台のマシンの中の話でした。複数のマシンにまたがると、共有メモリもロックも使えず、メッセージは遅れ、失われ、順序が入れ替わります。それでも「在庫を二重に引き当てない」「同じ処理を 2 回実行しない」を守るための、分散ロック、フェンシングトークン、合意アルゴリズム、冪等性といった道具は、第7部で扱います。

## よくある落とし穴

1. **「GIL があるから Python ではロックは要らない」と考える**。GIL は複数の手順をまとめて守りません。read-modify-write や check-then-act はロックで囲みます。free-threaded ビルドでは、たまたま動いていたコードも壊れます。
2. **条件変数を `if` で待つ**。見せかけの起床や、他のスレッドに先を越された場合に、条件が成り立っていないまま処理を進めてしまいます。必ず `while` で確かめ直します。
3. **ロックを持ったまま I/O や外部のコードを呼ぶ**。ロックの保持時間が I/O の待ち時間まで伸びて並列度が落ち、コールバックの中で別のロックが取られるとデッドロックの原因になります。ロックの中では、共有データの読み書きだけをします。
4. **場所によってロックの取得順序が違う**。まれにしか重ならない 2 つのコードパスが、本番の負荷で初めてデッドロックします。取得順序の規則を決め、コードレビューで確認します。
5. **async 関数の中でブロックする処理を呼ぶ**。`time.sleep`、同期的な HTTP・DB クライアント、重い計算は、イベントループのすべてのタスクを止めます。非同期版を使うか、スレッドプールやプロセスプールに逃がします。
6. **スレッド数や接続プールを「多いほど速い」と考えて設定する**。CPU を使う処理ではコア数を超えると遅くなり、下流の DB の処理能力を超えた接続は、下流で待たされるだけです。リトルの法則と下流の上限から決め、超えた分は待たせるか断ります。
7. **`time.sleep` でタイミングを合わせるテストを書く**。遅い CI 環境で不安定に失敗するテスト（flaky test）になります。イベントやバリアで待ち合わせ、タイムアウトは「失敗を検出するため」に長めに設定します。網羅的な探索で確かめられる部分は、そうします。
8. **アプリケーションの check-then-act で一意性や在庫を守ろうとする**。複数のサーバーで動かした瞬間に、アプリのロックは効かなくなります。DB の一意制約、条件付きの UPDATE、トランザクションの分離レベル（[6.3](../../06-databases/03-transactions/README.md)）に任せます。
9. **「ただのフラグ」を同期なしで共有する**。Java・C++・Go などでは、他のスレッドがいつまでも古い値を見続けることがあります。`volatile`・atomic・`threading.Event` など、可視性を保証する道具を使います。

## CTOの視点

1. **「同じリクエストが同時に 2 回来たらどうなるか」を設計レビューの定番の質問にする**。二重クリック、クライアントの再試行、複数のサーバーでの同時処理は、必ず起きます。在庫・残高・一意性のような不変条件は、アプリのコードではなく、データベースの制約や原子的な操作、冪等キー（[9.4](../../09-architecture/04-api-design/README.md)）で守る設計になっているかを確認します。並行処理のバグは再現に何週間もかかることがあり、設計の段階で潰すのが最も安上がりです。
2. **並行処理のモデルは、言語・ランタイムの選択と一体で決まる**。Go の goroutine、Java の仮想スレッド、Node.js や Python の asyncio、Erlang のアクターは、それぞれ書きやすさ・性能・落とし穴が違い、採用できるエンジニアの層も違います。「CPU を使う処理をどこで実行するか」「ブロッキングなライブラリが混ざったら誰が気づくか」まで含めて、組織として標準を決めます。
3. **並行数の上限と背圧を、容量計画の一部にする**。スレッドプール、接続プール、非同期処理の同時実行数、キューの長さは、すべて障害時の振る舞いを決める設定値です。既定値のまま運用され、負荷の急増時にキューが伸び続けてメモリを食い尽くしたり、下流の DB に接続が殺到したりする障害は典型的です。「この処理の同時実行数を制限しているのはどこか、超えたらどうなるか」を問いましょう。
4. **ハングしたときの調査手段を、平時に用意する**。デッドロックやイベントループの停止は、ログに何も残らないことが多い障害です。スレッドダンプや goroutine ダンプを本番で取得できるか（権限、手順、ツールのインストール）、ロックの待ち時間やイベントループの遅延をメトリクスとして監視しているかを確認します（[10.4](../../10-cloud-and-sre/04-observability/README.md)）。
5. **採用・育成では「直したことをどう確かめたか」を聞く**。並行処理のバグを直した経験を尋ね、「なぜそれで直ったと言えるのか」「テストでどう確かめたか」を掘り下げると、原理の理解と検証の姿勢が分かります。「1,000 回テストが通ったから大丈夫」と答える人より、不変条件と実行順序で説明できる人に、並行処理の設計を任せましょう。

### 演習6（記述）: タイムセールの在庫引き当て

EC サイトで、在庫 100 個の商品のタイムセールを行ったところ、注文が 112 件入ってしまいました。注文処理は、複数のアプリケーションサーバーで次のように実装されています（擬似コード）。

```python
def place_order(user_id, item_id):
    stock = db.query_one("SELECT stock FROM items WHERE id = %s", item_id)
    if stock > 0:
        db.execute("UPDATE items SET stock = %s WHERE id = %s", stock - 1, item_id)
        db.execute("INSERT INTO orders (user_id, item_id) VALUES (%s, %s)", user_id, item_id)
        return "ok"
    return "sold out"
```

(1) 在庫を超えて注文が入った理由を、2 つのリクエストの実行順序を示して説明してください。(2) 修正案を 3 つ挙げ、それぞれの長所と短所を比べてください。(3) セール開始直後に 1 秒あたり数千件のリクエストが集中することを考えると、どの案をどう組み合わせますか。二重クリックやリクエストの再試行への対策にも触れてください。

<details>
<summary>解答例</summary>

**(1) 原因**: check-then-act と read-modify-write の競合状態です。例えば在庫が 1 のとき、リクエスト A が `SELECT` で 1 を読み、B も `SELECT` で 1 を読みます。両方とも `stock > 0` なので、A が `stock = 0` を書き、B も `stock = 0` を書き、注文は 2 件入ります。複数のサーバーで動いているので、アプリの中のロックでは防げません。

**(2) 修正案**

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| 条件付きの原子的な UPDATE | `UPDATE items SET stock = stock - 1 WHERE id = %s AND stock > 0` を実行し、更新された行数が 1 なら注文を作る（同じトランザクションで） | 確認と更新が DB の中で 1 つの操作になる。単純で速い | 同じ行への更新が集中すると、行ロックの待ちが直列化のボトルネックになる |
| 行ロック（悲観的ロック） | トランザクションの中で `SELECT ... FOR UPDATE` で行をロックしてから確認・更新する | 複雑な確認（ユーザーごとの購入上限など）もまとめて守れる | ロックの保持時間が長くなりやすく、待ちが増える。デッドロックや待ちのタイムアウトへの対処が要る |
| 楽観的ロック | バージョン列を持ち、`UPDATE ... WHERE id = %s AND version = 読んだ値` が 0 行なら読み直して再試行 | ロックを持ち続けない | 競合が激しいと再試行が大量に失敗し、かえって遅い（セールには不向き） |
| 在庫を別の仕組みで先に引き当てる | Redis の原子的な減算（DECR）や、在庫数分の「引換券」をキューに入れておき、取れた人だけが注文処理に進む | 高いスループット | DB との二重管理になり、注文作成の失敗時に在庫を戻す処理（補償）が必要 |

**(3) 組み合わせの例**

- 基本は条件付きの原子的な UPDATE と注文の INSERT を 1 つのトランザクションで行い、「DB が最後の砦」として超過販売を不可能にする。
- 開始直後の集中には、前段に在庫の引換券（Redis の減算やキュー）を置き、在庫がなくなったら DB に到達する前に「売り切れ」を返して、DB の負荷と行ロックの競合を減らす。人気商品では、在庫を複数の行に分割して（シャーディングしたカウンタ）競合を分散する方法もある。
- 二重クリックや再試行で同じユーザーの注文が重複しないよう、クライアントが生成した冪等キーを注文テーブルの一意制約で守る（[9.4](../../09-architecture/04-api-design/README.md)）。
- 在庫を減らした後に注文の作成や決済が失敗した場合に、在庫を戻す処理（トランザクションのロールバック、または補償処理）を設計する。

採点の観点: 競合する実行順序を具体的に示せていること、「アプリのロックは複数サーバーでは効かない」ことを理解していること、条件付き UPDATE の「更新行数の確認」まで書けていることが合格の目安です。負荷の集中への対策と冪等性まで扱えていれば、設計レビューをリードできる水準です。

</details>

## 理解度チェック

**Q1. 並行（concurrency）と並列（parallelism）の違いを説明し、「並行だが並列ではない」例を挙げてください。**

<details>
<summary>解答</summary>

並行は、複数の仕事を重なり合った期間に進める構造のことで、1 つの CPU でも切り替えながら実現できます。並列は、複数の仕事を物理的に同時に実行することで、複数の実行ユニット（コア）が必要です。

「並行だが並列ではない」例: Python の asyncio のイベントループは、1 つのスレッドで多数の接続の処理を切り替えながら進めますが、同時に実行しているのは常に 1 つです。1 コアのマシンで複数のスレッドを時分割で動かすのも同様です。

</details>

**Q2. `if key not in cache: cache[key] = compute(key)` は、CPython の GIL があっても競合状態になりえます。なぜですか。また、どう直しますか。**

<details>
<summary>解答</summary>

GIL が保証するのは、1 つ 1 つのバイトコードの実行が他のスレッドと混ざらないことだけで、「確認」と「代入」の 2 つの手順をまとめて守るわけではありません。あるスレッドが `key not in cache` を確認してから代入するまでの間（特に `compute` の実行中）に、他のスレッドも同じ確認をして「ない」と判断し、`compute` が二重に実行されます。`compute` が外部 API の呼び出しや課金を伴う処理なら、実害になります。

直し方: 確認と代入を 1 つのロックで囲む（計算が重いなら、キーごとのロックや「計算中」の印を置く方法も検討する）。単に「最初の 1 回だけ登録したい」なら `cache.setdefault(key, value)` のような原子的な操作を使う方法もありますが、その場合も `compute` の二重実行は防げない点に注意します。

</details>

**Q3. 条件変数を待つコードは、なぜ `if` ではなく `while` で条件を確かめる必要があるのですか。**

<details>
<summary>解答</summary>

`wait()` から戻ったときに、待っていた条件が成り立っているとは限らないからです。

- 起こされてからロックを取り直すまでの間に、他のスレッド（別の消費者など）が先にロックを取り、条件を再び偽にしている可能性がある。
- 多くの実装や規格では、誰も notify していないのに起きる「見せかけの起床（spurious wakeup）」が許されている。
- `notify_all()` で全員が起こされた場合、条件を満たせるのは一部だけのことがある。

`while` で確かめ直せば、条件が偽ならもう一度待つだけなので、これらすべてに正しく対処できます。

</details>

**Q4. デッドロックの 4 条件（Coffman の条件）を挙げ、「ロックを常に ID の小さい順に取る」ことがどの条件を崩すのかを説明してください。**

<details>
<summary>解答</summary>

1. 相互排他（資源は同時に 1 つのスレッドしか使えない）
2. 保持と待機（資源を持ったまま別の資源を待つ）
3. 横取り不可（他のスレッドの資源を奪えない）
4. 循環待ち（待ちの関係が輪になる）

ロックを常に ID の小さい順に取ると、「ID の大きいロックを持ったスレッドが、ID の小さいロックを待つ」ことが起こらなくなります。待ちの関係は常に「小さい ID のロックを持つ者 → 大きい ID のロックを持つ者」の向きにしか生じないので、輪（循環待ち）が作れません。つまり 4 番目の条件を崩しています。

</details>

**Q5. 優先度逆転とは何ですか。Mars Pathfinder の事例に沿って説明し、優先度継承がどう解決するのかを答えてください。**

<details>
<summary>解答</summary>

優先度逆転は、高優先度のタスクが、それより低い優先度のタスクに実質的に待たされてしまう現象です。Pathfinder では、低優先度のタスクが共有データ（情報バス）を守るミューテックスを持っている間に、高優先度のタスクが同じミューテックスを待ちました。そこへ、ミューテックスとは無関係な中優先度のタスクが動き出して低優先度のタスクを横取りし続けたため、低優先度のタスクはロックを解放できず、高優先度のタスクは中優先度のタスクが終わるまで待たされました。高優先度のタスクが期限内に動かないことをウォッチドッグが検出し、システムがリセットされました。

優先度継承では、高優先度のタスクが待っているロックを持つタスクが、一時的にその高い優先度を受け継ぎます。低優先度のタスクは中優先度のタスクに横取りされなくなり、すぐにロックを解放できるので、高優先度のタスクの待ちが短くなります。Pathfinder では、この機能が無効になっていたミューテックスの設定を、地上から変更して修正しました。

</details>

**Q6. 8 コアのサーバーで、1 リクエストあたり CPU で 10 ミリ秒計算し、外部 API の応答を 190 ミリ秒待つ処理があります。毎秒 300 件を処理するには、同時にいくつのリクエストを処理できる必要がありますか。また、スレッドプールの大きさの目安と、注意すべき点を答えてください。**

<details>
<summary>解答</summary>

リトルの法則 `L = λW` より、1 件の処理時間は 10 + 190 = 200 ミリ秒 = 0.2 秒なので、同時に処理中のリクエストは平均で 300 × 0.2 = **60 件** です。ばらつきやピークを考えると、この数倍の余裕が必要です。

Goetz の目安では、CPU 使用率 100% を目標にすると 8 × (1 + 190 / 10) = 160 スレッドまでは CPU を遊ばせずに使えます。一方、CPU の上限から見た処理能力は 8 コア ÷ 0.01 秒 = 毎秒 800 件なので、毎秒 300 件なら CPU には余裕があり、ボトルネックは待ち時間の方です。

注意点:

- 外部 API が同時に受け付けられる数（相手のレート制限や接続数の上限）を超えないこと。超えた分は、相手側で待たされるか拒否されるだけ。
- 外部 API が遅くなると、滞在時間 W が伸びて必要な同時数 L も比例して増える。プールが溢れたときにキューで待たせるのか、早めに断るのか（背圧）を決め、外部呼び出しにはタイムアウトを付ける。
- 待ちが中心の処理なので、スレッドを増やす代わりに、非同期 I/O や軽量スレッドで同時数を確保する選択肢もある。

</details>

**Q7. asyncio のハンドラの中で、同期的な HTTP クライアントを使って外部 API を呼ぶと何が起きますか。対策も答えてください。**

<details>
<summary>解答</summary>

同期的な呼び出しは、応答が返るまでスレッドをブロックします。asyncio のイベントループは 1 つのスレッドで全タスクを動かしているので、その間、**すべてのリクエストの処理が止まります**。1 件の API 呼び出しが 1 秒かかれば、サーバー全体が 1 秒間応答しなくなり、同時に多数のリクエストがあれば待ち時間は積み重なります。CPU 使用率は低いのに応答が遅い、という症状になりやすく、原因に気づきにくいのも厄介な点です。

対策:

- 非同期の HTTP クライアント（aiohttp、httpx の非同期 API など）を使い、`await` する。
- どうしても同期的なライブラリを使う必要があるなら、`asyncio.to_thread()` や `loop.run_in_executor()` でスレッドプールに逃がす。
- イベントループの遅延（予定した処理がどれだけ遅れて実行されたか）を監視し、ブロックしているコードを検出する（asyncio のデバッグモードは、遅いコールバックを警告してくれる）。

</details>

**Q8. 並行処理のコードで、ストレステストが 1,000 回連続で成功しても、競合状態がないとは言えないのはなぜですか。バグを見つけるために、ほかにどんな方法がありますか。**

<details>
<summary>解答</summary>

競合状態は、特定の実行順序（インターリーブ）でだけ現れます。実行順序はスケジューラや CPU の負荷、コア数、キャッシュの状態によって決まり、テスト環境ではほとんど現れない順序が、本番の負荷や別のハードウェアでは頻繁に現れることがあります。2 スレッドが 3 手順ずつ実行するだけで 20 通り、3 スレッドが 10 手順ずつなら 5 兆通りを超える順序があり、ランダムに試すだけでは、まれな順序を踏めません。

ほかの方法:

- **網羅的な探索（モデル検査）**: 小さなモデルで、すべての実行順序を系統的に試す（演習5、jcstress、loom、TLA+ など）。
- **レース検出器**: ThreadSanitizer や Go の `-race` で、同期のない同時アクセスを実行時に検出する。実際に競合が起きなくても、同期の欠如を見つけられる。
- **設計による回避**: 共有する可変データを減らす、不変条件を DB の制約や原子的な操作に任せる。
- **コードレビューで不変条件と取得順序を確認する**、タイムアウトとスレッドダンプで本番の問題を診断できるようにする。

</details>

## まとめ

- **並行** は多くの仕事を扱う構造、**並列** は物理的に同時に実行すること。並列化の効果は、並列化できない部分（ロックの中を含む）で頭打ちになる（アムダールの法則）。
- **競合状態** の典型は read-modify-write と check-then-act。GIL は複数の手順を守らない。ロックで守る単位は「不変条件が壊れている期間」であり、テストで再現しないことは正しさの証明ではない。
- ミューテックス・アトミック操作（CAS）・セマフォ・条件変数（**必ず while で待つ**）・読み書きロックを、用途に応じて使い分ける。高価なのは競合したロック。
- デッドロックは 4 条件がそろうと起きる。**ロックの順序付け** で循環待ちを崩し、タイムアウトと待ちグラフで検出・回復する。優先度逆転は優先度継承で防ぐ。
- 共有データの可視性は、各言語の **メモリモデル** が定める happens-before の関係（ロック、atomic、チャネル）を通じてのみ保証される。
- スレッドプールや並行数は、リトルの法則と下流の処理能力から決め、背圧をかける。async/await では **ループを止めない**。goroutine、アクター、構造化並行性は、共有を減らし、タスクの寿命を明確にするための道具。
- 並行処理のバグは、網羅的な探索・レース検出器・ストレステスト・設計による回避を組み合わせて見つける。その先には、共有メモリのない分散システムの並行性（第7部）がある。
