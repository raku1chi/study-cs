## なぜ学ぶのか

ストレージの I/O は、「成功した」と返ってきても、それが何を保証しているのかが直感と大きく異なる分野です。

- **fsyncgate（2018 年）**: PostgreSQL の開発者は、Linux で `fsync()` が失敗したとき、カーネルが書き込めなかったページを「書き込み済み」扱いにしてエラーを消してしまう場合があり、`fsync()` を再試行すると、データがディスクに届いていないのに成功が返りうることに気づきました。PostgreSQL は長年「失敗したら後で再試行すればよい」と考えていたため、データを失う可能性がありました。議論の結果、PostgreSQL は fsync の失敗時にはプロセスを異常終了（PANIC）させ、WAL から回復する方針に変更しました（2019 年初めのマイナーリリースから）。20 年以上使われてきた成熟したデータベースでも、OS の I/O の保証を誤解していたのです。
- **GitLab.com のデータ消失（2017 年）**: GitLab の公開ポストモーテムによれば、レプリケーションの不調に対応していた担当者が、誤ってプライマリのデータベースのデータディレクトリを削除しました。用意されていたはずの複数のバックアップと複製の仕組みは、設定の不備や気づかれない失敗によってどれも期待通りに機能せず、約 6 時間分のデータベースの更新が失われました。レプリケーションやスナップショットは、定期的に「復元できること」を確かめて初めてバックアップになります。
- **C10K 問題**: 1999 年、Dan Kegel は「1 台のサーバーで 1 万のクライアントを同時に扱う」ことの難しさを C10K 問題としてまとめました。接続ごとにスレッドを作る設計の限界と、epoll・kqueue によるイベント駆動の設計は、今日の nginx・Node.js・Go のランタイムの土台になっています。

## 1. ファイルという抽象

### 1.1 ファイル・ディレクトリ・inode

ディスクは、固定長の **ブロック**（多くの場合 4 KiB）を番号で読み書きするだけの装置です。ファイルシステムは、その上に「名前の付いた、伸び縮みするバイト列」というファイルの抽象を作ります。Unix 系のファイルシステムでは、ファイルは 2 つの部分から成ります。

- **inode**: ファイルの実体の管理情報。大きさ、所有者、パーミッション、タイムスタンプ、データが置かれたブロックの位置、リンク数などを持つ。**名前は持たない**。
- **ディレクトリ**: 「名前 → inode 番号」の対応表を中身とする、特別なファイル。

`stat` コマンドや Python の `os.stat()` で見える情報の大半は inode の内容です。名前と実体が分かれていることから、次のような性質が生まれます。

### 1.2 ハードリンクとシンボリックリンク

```python
import os
with open("a.txt", "w") as f:
    f.write("hello\n")
os.link("a.txt", "hard.txt")         # ハードリンク: 同じ inode に別の名前を付ける
os.symlink("a.txt", "sym.txt")       # シンボリックリンク: 「a.txt という名前」を指す小さなファイル
for name in ("a.txt", "hard.txt", "sym.txt"):
    st = os.lstat(name)              # lstat はリンク自体の情報（stat はリンク先をたどる）
    print(f"{name:9} inode={st.st_ino} links={st.st_nlink} size={st.st_size}")
os.remove("a.txt")                   # 元の名前を消す
print("hard.txt:", open("hard.txt").read().strip())      # 中身（inode）は残っている
try:
    open("sym.txt")
except FileNotFoundError as e:
    print("sym.txt :", e)                                  # 名前の参照先が消えたのでたどれない
```

```text
a.txt     inode=1983036 links=2 size=6
hard.txt  inode=1983036 links=2 size=6
sym.txt   inode=1983044 links=1 size=5
hard.txt: hello
sym.txt : [Errno 2] No such file or directory: 'sym.txt'
```

`a.txt` と `hard.txt` は同じ inode を指す 2 つの名前で、リンク数が 2 になっています。`rm` が行うのは「名前を消してリンク数を減らす」ことで（システムコール名が `unlink` なのはこのため）、リンク数が 0 になり、**かつ開いているプロセスがいなくなった** とき、初めてデータが解放されます。シンボリックリンクは「名前」を中身に持つ別のファイルなので、指す先の名前が消えるとたどれなくなります（中身の 5 バイトは `a.txt` という文字列です）。ハードリンクは同じファイルシステムの中でしか作れず、シンボリックリンクはファイルシステムをまたげます。

### 1.3 開いているファイルの 3 つの表

4.1 で見たファイルディスクリプタは、次の 3 段の構造でファイルを指しています。

```text
プロセスの fd 表      オープンファイル記述（カーネル全体）    inode
  fd 3 ───────┬────▶ [ 読み書きの位置=3、フラグ ] ──┐
  fd 4（dup）─┘                                    ├──▶ [ inode（大きさ、ブロックの位置…） ]
  fd 5 ────────────▶ [ 読み書きの位置=0、フラグ ] ──┘
（fork した子の fd も、親と同じオープンファイル記述を指す）
```

```python
import os
fd1 = os.open("f.txt", os.O_RDONLY)
fd2 = os.open("f.txt", os.O_RDONLY)   # もう一度 open → 別のオープンファイル記述
fd3 = os.dup(fd1)                     # dup → fd1 と同じオープンファイル記述を指す
os.read(fd1, 3)                       # fd1 から 3 バイト読む
print([os.lseek(fd, 0, os.SEEK_CUR) for fd in (fd1, fd2, fd3)])   # [3, 0, 3]
```

読み書きの位置（オフセット）はオープンファイル記述に属するので、`dup` した fd や fork した子とは共有され、別々に `open` した fd とは独立です。複数のプロセスが同じログファイルに追記するときは `O_APPEND` で開きます。すると、各 `write` の直前にカーネルが位置をファイルの末尾に移すので、ローカルのファイルシステムでは互いの書き込みが上書きし合いません。

「削除したのにディスクが空かない」という定番の障害も、この構造で説明できます。

```python
import os
import shutil

f = open("big.log", "wb")
f.write(b"x" * (200 * 1024 * 1024))           # 200 MiB のログを書く
f.flush()
print("削除前の空き:", shutil.disk_usage(".").free // 2**20, "MiB")
os.remove("big.log")                            # 名前を消す（rm と同じ）
print("削除後の空き:", shutil.disk_usage(".").free // 2**20, "MiB   ← 増えない")
print("リンク数:", os.fstat(f.fileno()).st_nlink, "（名前はもうないが、開いている fd がある）")
f.close()                                       # 最後の参照がなくなって初めて領域が解放される
print("close後の空き:", shutil.disk_usage(".").free // 2**20, "MiB")
```

```text
削除前の空き: 28879 MiB
削除後の空き: 28879 MiB   ← 増えない
リンク数: 0 （名前はもうないが、開いている fd がある）
close後の空き: 29079 MiB
```

ファイルを `os.remove()` しても、開いている fd がある限り空きは増えず、`close` して初めて 200 MiB が解放されました。巨大なログを `rm` してもディスクの使用率が下がらないときは、ログを書き続けているプロセスが fd を持ったままです。`lsof +L1`（リンク数 0 の開いているファイルを表示）で見つけ、プロセスにログを開き直させる（logrotate の `postrotate` でシグナルを送るなど）必要があります。

## 2. データはいつディスクに届くのか

### 2.1 バッファリングの層

アプリケーションの `write` から、データが電源を切っても消えない媒体に届くまでには、いくつものバッファがあります。

```text
アプリの変数
   │  f.write()          … 言語のライブラリのバッファ（Python の open() や C の stdio）
   ▼
ユーザー空間のバッファ
   │  flush() → write(2) … システムコール。ここで「成功」が返る
   ▼
カーネルのページキャッシュ（dirty ページ）
   │  バックグラウンドの書き戻し、または fsync(2)
   ▼
ブロック層・I/O スケジューラ → デバイスドライバ
   │
   ▼
ストレージ装置の揮発性の書き込みキャッシュ
   │  キャッシュのフラッシュ命令（fsync の中で発行される）
   ▼
不揮発の媒体（磁気ディスク、NAND フラッシュ）
```

層ごとに、何を失いうるかが違います。

| クラッシュの種類 | 失われうるもの |
|---|---|
| プロセスのクラッシュ（例外、SIGKILL） | ユーザー空間のバッファ（flush していないデータ） |
| OS のクラッシュ・電源断 | 上に加えて、ページキャッシュ上の dirty ページ（fsync していないデータ） |
| 装置の故障 | 媒体上のデータそのもの（→ RAID・レプリケーション・バックアップで守る） |

### 2.2 write はページキャッシュへのコピーにすぎない

`write()` が成功した時点では、データはカーネルのページキャッシュ（[4.2](../02-virtual-memory/README.md) で見た buff/cache）にコピーされ、「dirty（未書き戻し）」の印が付いただけです。書き戻しはカーネルのスレッドが後でまとめて行います。この環境の設定を見てみます。

```text
vm.dirty_background_ratio = 10
vm.dirty_ratio = 20
vm.dirty_expire_centisecs = 3000
vm.dirty_writeback_centisecs = 500
```

約 5 秒（500 センチ秒）ごとに書き戻しのスレッドが起き、dirty になってから 30 秒を過ぎたページを書き出します。dirty ページが使用可能なメモリの 10% を超えるとバックグラウンドの書き戻しが始まり、20% を超えると、書き込んでいるプロセス自身が書き戻しを待たされます。つまり、**fsync しなければ、電源断で最大 30 秒程度の書き込みが失われうる** のが既定の設定です。大量に書き込むバッチ処理で、ときどき write が突然遅くなるのは、この上限に当たって待たされているためです。

### 2.3 fsync・fdatasync・O_DIRECT

| 方法 | 保証すること | 典型的な用途 |
|---|---|---|
| `write` のみ | ページキャッシュへのコピー（他のプロセスからは読める） | 失っても再生成できるデータ |
| `fsync(fd)` | ファイルのデータとメタデータ（大きさなど）が媒体に届くまで待つ。装置のキャッシュのフラッシュも含む | コミットの完了、原子的な置き換え |
| `fdatasync(fd)` | データと、それを読むのに必要なメタデータだけ（更新時刻などは省く） | WAL の追記（メタデータの更新を省いて速くする） |
| `O_SYNC` / `O_DSYNC` で開く | 各 write が fsync / fdatasync 相当になる | 書き込みごとに永続化が必要なとき |
| `O_DIRECT` で開く | ページキャッシュを経由しない（永続化は保証しないので fsync は別に必要） | 自前のバッファプールを持つ DB（二重キャッシュを避ける） |

fsync は高価です。4 KiB の追記を 500 回、fsync ありとなしで比べました（この環境の仮想ディスクでの値。装置や設定で大きく変わります）。

```python
import os
import time

def bench(sync: bool, n: int = 500) -> float:
    fd = os.open("bench.dat", os.O_WRONLY | os.O_CREAT | os.O_TRUNC, 0o644)
    block = b"x" * 4096
    t0 = time.perf_counter()
    for _ in range(n):
        os.write(fd, block)             # 4 KiB を追記する
        if sync:
            os.fsync(fd)                # 毎回ディスクに届くまで待つ
    elapsed = time.perf_counter() - t0
    os.close(fd)
    os.remove("bench.dat")
    return elapsed / n * 1e6            # 1 回あたりのマイクロ秒

print(f"write のみ       : {bench(False):8.1f} µs/回")
print(f"write + fsync    : {bench(True):8.1f} µs/回")
```

```text
write のみ       :      2.5 µs/回
write + fsync    :    211.7 µs/回
```

fsync を毎回呼ぶと 80 倍以上遅くなりました。HDD なら 1 回の fsync にミリ秒単位かかります。データベースが複数のトランザクションのコミットをまとめて 1 回の fsync で永続化する **グループコミット** を行うのは、このコストを分け合うためです。逆に、ベンチマークで異常に速いストレージは、fsync を省略している（設定で無効化されている、または装置がフラッシュ命令を無視している）可能性を疑うべきです。

### 2.4 原子的なファイルの置き換え

設定ファイルや状態ファイルを「上書き保存」する素朴な方法は、`open(path, "w")` で開いて書くことです。しかし `"w"` は開いた瞬間にファイルを空にするので、書いている途中でクラッシュすると、**空か書きかけのファイル** が残ります。

正しい手順は次の通りで、これは多くのデータベースやパッケージマネージャが使っている定石です。

1. 同じディレクトリに一時ファイルを作り、新しい内容をすべて書く
2. 一時ファイルを **fsync** する
3. `rename`（Python では `os.replace`）で本来の名前に付け替える
4. ディレクトリを **fsync** する

POSIX は、同じファイルシステム内の `rename` が **原子的** であること、つまり他のプロセスからは古いファイルか新しいファイルのどちらかしか見えないことを保証しています。手順 2 を省くと、rename（ディレクトリの更新）が中身より先にディスクに届き、クラッシュ後に「新しい名前で、中身が空のファイル」が残りえます。2009 年ごろ、ext4 ファイルシステムの遅延割り当て（書き込むブロックの決定を遅らせる最適化）が広まった際に、クラッシュ後にアプリの設定ファイルが空になるという報告が相次ぎ、アプリ側が手順 2 を省いていたことが原因として議論されました（ext4 側も、このような置き換えのときにデータを先に書き出す対策を入れました）。手順 4 は、rename 自体（ディレクトリの内容の変更）を永続化するためのものです。演習1でこの手順を実装し、テストで呼び出しの順序を確かめます。

### 2.5 fsync の失敗は取り返せない

冒頭の fsyncgate の教訓を整理します。

- ページキャッシュの書き戻しが I/O エラーで失敗したとき、Linux はそのエラーを後続の fsync で報告しますが、報告は基本的に **一度きり** で、もう一度 fsync したときに再び報告される保証はありません。書き込めなかったページがどうなるか（dirty のまま残るか、clean として扱われるか）もファイルシステムやバージョンによって異なり、少なくとも「再試行すれば書ける」とは限りません。
- したがって、**fsync が失敗したら、そのファイルの未永続化の内容は失われたとみなす** 必要があります。PostgreSQL が選んだのは、プロセスを異常終了させて、確実にディスクにある WAL から回復することでした。
- アプリケーションの設計では、「fsync のエラーをログに出して続行する」のではなく、「そのデータを確実に持っている場所（WAL、上流のキュー、クライアント）からやり直す」経路を用意します。

## 3. ファイルシステムはどうやって壊れずにいるか

### 3.1 クラッシュ一貫性の問題

ファイルに 1 ブロック追記するだけでも、ファイルシステムは複数の場所を更新します。空きブロックの管理表（ビットマップ）、inode（大きさとブロックの位置）、データのブロック本体です。この途中で電源が落ちると、「ビットマップでは使用中なのに、どの inode からも指されていないブロック」や、「inode が指しているのに、中身がゴミのブロック」が残ります。

昔のファイルシステムは、起動時に **fsck** で全体を走査して矛盾を直していましたが、ディスクが大きくなると何時間もかかるようになりました。

### 3.2 ジャーナリング

**ジャーナリング（journaling）** は、データベースの WAL（先行書き込みログ、[6.4](../../06-databases/04-storage-and-recovery/README.md)）と同じ考え方です。本来の場所を更新する前に、「これからこう更新する」という記録をジャーナル（ログ）に書いて永続化し、それから本来の場所を更新します。クラッシュしたら、ジャーナルの完了した記録だけをやり直せば、全体を走査せずに一貫した状態に戻れます。

Linux の ext4 には 3 つのモードがあります。

| モード | ジャーナルに書くもの | 特徴 |
|---|---|---|
| `data=journal` | メタデータとデータの両方 | 最も安全だが、データを 2 回書くので遅い |
| `data=ordered`（既定） | メタデータのみ。ただしデータを先に書いてからメタデータをコミットする | クラッシュ後に「古い他人のデータが見える」ことはない |
| `data=writeback` | メタデータのみ。順序の保証なし | 速いが、クラッシュ後にファイルの中身がゴミになりうる |

XFS もメタデータのジャーナリングを行います。重要なのは、**ジャーナリングが守るのはファイルシステム自身の一貫性であって、アプリケーションのデータの一貫性ではない** ことです。「複数のファイルをまとめて更新する」「書きかけのレコードを捨てる」といった整合性は、アプリケーション（またはデータベース）が fsync と自前のログで守る必要があります。

### 3.3 コピーオンライト型ファイルシステム

**ZFS** や **btrfs** は、既存のブロックを上書きせず、変更したブロックを常に新しい場所に書き、最後にルートのポインタを原子的に切り替えます（[4.2](../02-virtual-memory/README.md) のコピーオンライトと同じ発想）。

- 古い版がそのまま残るので、**スナップショット** がほぼ一瞬で作れる。
- データにも **チェックサム** を持つので、ディスクのビット化け（サイレントなデータ破損）を検出でき、冗長構成なら正しいコピーから自動で修復できる。
- 一方、データベースのファイルのように小さなランダムな上書きが多いと、断片化や書き込み量の増加で性能が落ちることがあり、用途に応じた設定の調整が必要になる。

### 3.4 アプリケーションの責任: レコードの境界とチェックサム

ファイルシステムが一貫していても、アプリケーションのファイルの中身が一貫しているとは限りません。追記型のログに書いている最中にクラッシュすると、ファイルの末尾には **途中で切れたレコード**（torn write）が残ります。また、媒体やコントローラの不具合で、ビットが化けることもあります。

そこで、ログやデータファイルは、各レコードに **長さ** と **チェックサム** を付けて書くのが定石です。演習4では、次の形式のログを実装します。

```text
+----------------+-----------------+--------------------+
| 長さ（4 バイト）  | CRC32（4 バイト） | ペイロード（長さ分）  |  ← これを隙間なく並べる
+----------------+-----------------+--------------------+
```

開くときに先頭から読み、「ヘッダが途中で切れている」「長さの分だけデータがない」「CRC が一致しない」レコードに当たったら、そこから後ろは信用せずに切り詰めます。これが **回復（recovery）** の最小の形です。データベースの WAL（6.4）も、Kafka のような分散ログ（[7.5](../../07-distributed-systems/05-messaging-and-events/README.md)）も、基本は同じ構造をしています。CRC32 は偶然の破損を検出するためのもので、悪意ある改ざんの検出には暗号学的なハッシュや MAC が必要です（[11.2](../../11-security/02-cryptography/README.md)）。

## 4. ストレージデバイス

### 4.1 HDD と SSD

[1.3](../../01-computer-systems/03-memory-hierarchy/README.md) で見たように、ストレージの速度は種類によって桁違いです。目安を示します（製品や世代で大きく変わります）。

| 装置 | ランダムな読み込みの遅延 | ランダムアクセスの性能（IOPS） | 特徴 |
|---|---|---|---|
| HDD | 数ミリ秒〜10 ミリ秒程度（ヘッドの移動と回転待ち） | 100〜200 程度 | 順次アクセスは速く、ランダムアクセスは遅い |
| SATA SSD | 100 マイクロ秒程度 | 数万〜10 万程度 | インターフェースが上限になる |
| NVMe SSD | 数十〜100 マイクロ秒程度 | 数十万〜それ以上 | 多数のキューで並列に処理できる |

SSD（NAND フラッシュ）には、HDD にない独特の性質があります。

- **上書きできない**: フラッシュは「消去してから書く」必要があり、消去の単位（ブロック。製品によるが数 MB 程度）は書き込みの単位（ページ、数 KB〜十数 KB）よりずっと大きい。そこで SSD の中の **FTL（Flash Translation Layer）** が、論理アドレスを物理位置に対応付け直しながら、常に空いた場所に書く（ここでもコピーオンライト）。
- **ガベージコレクション**: 古いデータが残ったブロックを整理するため、SSD の内部で読み直しと書き直しが起きる。空き容量が少ないと頻繁になり、**書き込みの遅延が突発的に悪化** したり、実際に媒体に書く量が増えたり（**書き込み増幅**）する。OS が削除したブロックを SSD に伝える **TRIM** は、これを軽くする。
- **寿命**: セルには書き換え回数の上限があり、製品は総書き込み量（TBW）や 1 日に全容量を何回書けるか（DWPD）で耐久性を示す。
- **電源断への備え**: SSD 内部の揮発性キャッシュを電源断時に書き出すためのコンデンサ（電源喪失保護、PLP）を持つ製品と持たない製品があり、fsync の速さと安全性に影響する。

### 4.2 ブロック層と I/O スケジューラ

カーネルのブロック層は、ファイルシステムからの I/O 要求をまとめたり並べ替えたりしてから装置に渡します。どう並べるかを決めるのが **I/O スケジューラ** です。

```text
$ cat /sys/block/vda/queue/scheduler
none [mq-deadline] kyber bfq
```

`mq-deadline`（要求に締め切りを設けて飢餓を防ぐ）、`bfq`（プロセス間の公平性を重視）、`kyber`（遅延の目標を持つ）、`none`（並べ替えない）が選べ、`[ ]` が現在の設定です。HDD ではヘッドの移動を減らす並べ替えが効きましたが、内部で並列に処理できる NVMe SSD では、並べ替えの手間の方が高くつくことが多く、`none` がよく選ばれます。

### 4.3 RAID

**RAID** は、複数のディスクを組み合わせて、容量・性能・耐障害性を得る技術です。

| レベル | 方式 | 使える容量（n 台） | 何台の故障に耐えるか | 小さなランダム書き込みのコスト |
|---|---|---|---|---|
| RAID 0 | ストライピング（分散） | n 台分 | 0（1 台の故障で全損） | 1 回の書き込み |
| RAID 1 | ミラーリング（複製） | 1 台分 | n−1 | n 回の書き込み |
| RAID 5 | 分散パリティ（1 台分） | n−1 台分 | 1 | 4 回の I/O（旧データと旧パリティを読み、両方を書く） |
| RAID 6 | 分散パリティ（2 台分） | n−2 台分 | 2 | 6 回の I/O |
| RAID 10 | ミラーのストライピング | n/2 台分 | 各ミラーの組で 1 台まで | 2 回の書き込み |

大容量の HDD で RAID 5 を組むと、1 台が故障して再構築（リビルド）している間は冗長性がなく、再構築では残りの全ディスクを読み切る必要があるため、その間に 2 台目の故障や読み込みエラーが起きるとデータを失います。大容量のディスクで RAID 6 や RAID 10 が選ばれるのはこのためです。

そして最も重要なのは、**RAID はバックアップではない** ことです。RAID は装置の故障からデータを守りますが、誤った削除、アプリのバグによる破壊、ランサムウェアによる暗号化は、そのまますべてのディスクに書き込まれます。冒頭の GitLab の事故が示すように、複製やスナップショットの仕組みがあっても、それが実際に使える状態かを確かめていなければ意味がありません。バックアップは、**別の場所に、過去の時点のコピーを、変更できない形で持ち、定期的に復元を試す** ことで初めて意味を持ちます（[10.3](../../10-cloud-and-sre/03-reliability-engineering/README.md)）。

## 5. ネットワーク越しのストレージ

クラウドでは、ストレージの多くがネットワークの向こう側にあります。種類によって、保証するセマンティクスがまったく違います。

| 種類 | 例 | アクセス方法 | セマンティクスの要点 | 向いている用途 |
|---|---|---|---|---|
| ブロックストレージ | Amazon EBS、iSCSI | 1 台のマシンのディスクとして接続し、その上にファイルシステムを作る | ローカルディスクと同じ（fsync、rename の原子性）。基本的に 1 台から使う | データベース、OS のディスク |
| ファイル共有 | NFS、SMB、Amazon EFS | 複数のマシンから POSIX に近い API でマウント | ロックやキャッシュの一貫性に独特の制約がある（NFS の close-to-open 一貫性など） | 共有のホームディレクトリ、既存アプリの共有ファイル |
| オブジェクトストレージ | Amazon S3、GCS | HTTP の API でオブジェクト単位に PUT/GET | オブジェクト全体の置き換えのみ（追記・部分更新・rename はない）。一覧は名前の接頭辞による | 画像・動画、ログ、バックアップ、データレイク |

いくつか注意点を挙げます。

- **NFS** の上でローカルディスクと同じ振る舞いを期待すると失敗します。NFS クライアントは属性やデータをキャッシュし、他のクライアントの変更は「ファイルを閉じて、開き直したとき」に見えるのが基本です（close-to-open 一貫性）。ファイルロックの実装も環境によって信頼性が異なり、SQLite のような組み込みデータベースを NFS に置くことは、SQLite 自身のドキュメントでも推奨されていません。また、NFS サーバーが応答しなくなると、読み書きしているプロセスは D 状態で止まり、4.1 で見たロードアベレージの急上昇として現れます。
- **Amazon S3** は、2020 年 12 月から、新規作成・上書き・削除の直後の読み取りと一覧に **強い一貫性（strong read-after-write consistency）** を提供しています。それ以前は、上書き直後に古いデータが読めることがありました。2024 年には、条件付き書き込み（「存在しなければ書く」など）も追加されています（2026 年時点の仕様は公式ドキュメントで確認してください）。
- オブジェクトストレージには rename がないので、「一時的な名前で書いてから付け替える」という 2.4 の技法は使えません。完成したオブジェクトを 1 回の PUT で書く（PUT はオブジェクト全体について原子的）、あるいは「どのオブジェクトが最新か」を別の場所（マニフェスト、データベース）で管理します。データレイクのテーブル形式（Apache Iceberg、Delta Lake など）がメタデータのファイルでこれを管理しているのはこのためです（[12.1](../../12-data-and-ai/01-data-engineering/README.md)）。

## 6. I/O モデルと C10K

### 6.1 スレッドで待つ: ブロッキング I/O

最も素直なサーバーの書き方は、接続ごとにスレッドを 1 本作り、`recv` や `read` でデータが来るまでそのスレッドを **ブロック**（待機）させることです。コードは上から下へ素直に読めます。

問題は数です。接続が 1 万あればスレッドも 1 万本必要で、スレッドごとのスタック（多くの環境で既定の予約は数 MB、実際に使う物理メモリはもっと小さい）、カーネルの管理構造、そして大量のコンテキストスイッチ（[4.1](../01-processes-and-syscalls/README.md)）のコストがかさみます。ほとんどの接続は大半の時間、何もせずに待っているだけなのに、です。

### 6.2 ノンブロッキング I/O と多重化

ソケットを **ノンブロッキング**（`O_NONBLOCK`）にすると、データがなければ `recv` は待たずに `EAGAIN`（Python では `BlockingIOError`）を返します。しかし、それを全接続についてぐるぐる試す（ビジーループ）のは CPU の無駄です。

そこで、「どの fd が読める／書ける状態になったか」を OS にまとめて尋ねる **I/O 多重化** の仕組みが使われます。

| 仕組み | 特徴 |
|---|---|
| `select` | 最も古く移植性が高い。扱える fd の番号に上限（多くの環境で 1024）があり、呼ぶたびに全 fd を渡して調べるので O(n) |
| `poll` | 番号の上限はないが、やはり毎回全 fd を渡して調べる O(n) |
| `epoll`（Linux） | 監視する fd を事前にカーネルに登録しておき、準備ができたものだけを受け取る。接続数が多くても準備ができた数に比例するコスト |
| `kqueue`（BSD 系・macOS） | epoll と同様の仕組みで、ファイルの変更やタイマーなど、より多くの種類のイベントを扱える |

Python の `selectors` モジュールは、環境で最良の仕組みを自動で選びます（この環境では `selectors.DefaultSelector()` は `EpollSelector` でした）。

注意すべき例外は **通常のファイル** です。通常のファイルは常に「読める」と判定されるので（Linux の epoll にはそもそも登録できません）、ディスクの読み込みの待ちを多重化で隠すことはできません。Node.js（libuv）がファイル操作を内部のスレッドプールで実行しているのはこのためです。

### 6.3 イベントループ

I/O 多重化の上に組み立てるのが **イベントループ** です。1 本のスレッドが次のループを回し続けます。

```python
# 擬似コード（演習5で、本物を selectors で実装します）
while running:
    for key, events in selector.select():       # 準備ができた fd を待つ（唯一ブロックする場所）
        if key.fileobj is listener:
            accept_new_connection()              # 新しい接続を登録する
        else:
            if events & READ:  handle_readable(key.data)   # 読めるだけ読む（部分的なこともある）
            if events & WRITE: handle_writable(key.data)   # 書けるだけ書く（部分的なこともある）
```

この設計は、接続ごとの状態（読みかけのリクエスト、送り切れていないデータ）を、スレッドのスタックではなく明示的なデータ構造として持つことになります。演習5で実装すると分かりますが、次の点に気を配る必要があります。

- **部分的な読み書き**: `recv` は届いた分だけ、`send` は送れた分だけを扱う。1 回で全部送れるとは限らない。
- **背圧（バックプレッシャー）**: 相手が受信しないのに読み続けると、送れないデータがサーバーのメモリに際限なく溜まる。送信待ちが一定量を超えたら、その接続からの読み込みを止める。
- **ループを止めない**: イベントループの中で、時間のかかる計算や、ブロックする呼び出し（通常のファイルの読み書き、同期的な DNS の問い合わせ、スリープ）を 1 つでも行うと、**すべての接続** が止まる（[4.4](../04-concurrency/README.md)）。

**nginx** は CPU コア数程度のワーカープロセスがそれぞれイベントループを回し、1 プロセスで数万の接続を扱います。**Node.js** はアプリケーションのコード全体を 1 本のイベントループの上で動かします。Python の **asyncio** も同じ構造で、`await` は「ここでイベントループに制御を返す」という印です（4.4）。

### 6.4 非同期 I/O と io_uring

I/O 多重化は「準備ができたら教えて（readiness）」というモデルで、実際の読み書きはアプリが行います。これに対して **非同期 I/O** は「この読み込みをしておいて、終わったら教えて（completion）」というモデルです。Windows の I/O 完了ポート（IOCP）がこの方式です。

Linux では長く、非同期 I/O の仕組みが限定的でした（POSIX AIO は glibc がスレッドで模倣しており、ネイティブの Linux AIO は実質的に O_DIRECT のファイルでしか非同期に動かない）。これを変えたのが、Linux 5.1（2019 年）で導入された **io_uring** です。アプリとカーネルが共有メモリ上の 2 つのリングバッファ（要求を積む投入キューと、結果が積まれる完了キュー）でやり取りするので、多数の I/O をシステムコール 1 回で、あるいはシステムコールなしで投入でき、ファイルもソケットも同じ仕組みで非同期に扱えます。2.3 の「システムコールをまとめて少なく」の原則を突き詰めた設計です。

一方、io_uring はカーネルの中で大きく複雑な機能であるため、脆弱性の温床にもなりました。Google は 2023 年に、自社の脆弱性報奨金プログラムに提出された Linux カーネルの攻撃手法の多くが io_uring を悪用していたとして、一部の環境で io_uring を無効化したと公表しています。性能と攻撃対象領域のトレードオフの典型例です。

| モデル | 待ち方 | 代表例 | 向いている場面 |
|---|---|---|---|
| ブロッキング＋スレッド（またはプロセス） | スレッド・プロセスごとに待つ | 伝統的な Java のサーブレット、PostgreSQL（接続ごとのプロセス） | 接続数が中程度、コードの素直さを優先 |
| 多重化＋イベントループ | 1 スレッドで多数の fd を待つ | nginx、Node.js、Redis | 大量の接続で、それぞれの処理が軽い |
| 非同期 I/O（完了通知） | カーネルに I/O を任せる | io_uring、Windows の IOCP | 極めて高い I/O 性能が必要な場面 |
| 軽量スレッド | ランタイムが多重化を隠す | Go の goroutine、Java の仮想スレッド | 素直なコードのまま大量の接続を扱いたい |

## 7. ファイルロック

複数のプロセスが同じファイルを扱うときは、ロックで調整します。Unix のファイルロックは基本的に **勧告的（advisory）** で、「ロックを確認する約束を守るプロセス同士」でしか効きません。ロックを無視して書き込むプロセスは止められません。

| 仕組み | 範囲 | 持ち主 | 注意点 |
|---|---|---|---|
| `flock` | ファイル全体 | オープンファイル記述（fork した子と共有） | シンプル。NFS では環境によって振る舞いが異なる |
| `fcntl`（POSIX ロック） | バイト範囲 | プロセス | そのプロセスが **同じファイルのどの fd を閉じても** ロックが外れる、という有名な落とし穴がある |
| OFD ロック（Linux 3.15 以降） | バイト範囲 | オープンファイル記述 | POSIX ロックの落とし穴を解消したもの |

cron で定期実行するバッチが二重に動かないようにする、といった用途では `flock` が手軽です。

```python
import fcntl
import os
import time

path = "job.lock"
pid = os.fork()
if pid == 0:                                    # 子: 少し遅れてロックを試みる
    time.sleep(0.2)
    with open(path, "a") as f:
        try:
            fcntl.flock(f, fcntl.LOCK_EX | fcntl.LOCK_NB)   # 取れなければすぐに諦める
        except BlockingIOError:
            print("子: 他のプロセスがロック中（非ブロッキングの試行は失敗）")
        fcntl.flock(f, fcntl.LOCK_EX)                     # 今度は取れるまで待つ
        print("子: 解放を待ってロックを取得した")
    os._exit(0)
with open(path, "a") as f:                      # 親: 先にロックを取り、0.5 秒保持する
    fcntl.flock(f, fcntl.LOCK_EX)
    print("親: ロックを取得")
    time.sleep(0.5)
    fcntl.flock(f, fcntl.LOCK_UN)
    print("親: ロックを解放")
os.waitpid(pid, 0)
os.remove(path)
```

```text
親: ロックを取得
子: 他のプロセスがロック中（非ブロッキングの試行は失敗）
親: ロックを解放
子: 解放を待ってロックを取得した
```

ロックはプロセスが終了すると自動的に外れるので、「ロックファイルが存在するかどうか」で排他する方法（プロセスが異常終了するとファイルが残り、永遠にロックされたままになる）より安全です。ただし、ファイルロックが効くのは 1 台のマシンの中（とロックを正しく実装した共有ファイルシステム）だけです。複数のマシンにまたがる排他には、分散ロックと、それにつきまとう難しさ（[7.4](../../07-distributed-systems/04-consensus-and-coordination/README.md)）が待っています。

## よくある落とし穴

1. **write() が成功したら保存されたと思い込む**。write はページキャッシュへのコピーにすぎず、電源断で消えます。ユーザーに「保存しました」と返す前に、どの時点で fsync されるのか（または複製されるのか）を設計で決めます。
2. **ファイルを `open(path, "w")` で上書きする**。開いた瞬間に中身が消えるので、途中のクラッシュで空のファイルが残ります。一時ファイル → fsync → rename → ディレクトリの fsync で置き換えます。
3. **fsync のエラーを無視する、または再試行で済ませる**。失敗した書き込みは失われたとみなし、確実に持っている場所からやり直すか、プロセスを止めます。
4. **RAID やレプリケーションをバックアップの代わりにする**。誤操作や破壊的なバグは複製先にも伝わります。別の場所に、変更できない過去のコピーを持ち、復元の訓練をします。
5. **削除したのにディスクが空かない、で慌てる**。開いている fd がある限り領域は解放されません。`lsof +L1` で探し、ログのローテーションではプロセスにファイルを開き直させます（`copytruncate` はコピー中の書き込みを失う可能性がある妥協策です）。
6. **イベントループの中でブロックする処理を呼ぶ**。通常のファイル I/O、同期的な DNS 解決、重い計算、`time.sleep` は、すべての接続を止めます。スレッドプールに逃がすか、非同期版を使います。
7. **NFS やオブジェクトストレージを、ローカルディスクと同じ意味で使う**。rename の原子性、ロック、キャッシュの一貫性の保証が違います。オブジェクトストレージには rename も追記もありません。
8. **inode の枯渇に気づかない**。小さなファイルを大量に作ると、容量が余っていても inode を使い切って新しいファイルを作れなくなります。`df -h` だけでなく `df -i` も監視します。

## CTOの視点

1. **「ユーザーに成功を返した時点で、データはどこにあるか」を必ず問う**。永続性は、fsync の方針、同期レプリケーションの有無、バックアップの頻度の組み合わせで決まる、事業上の約束です。「RPO（どの時点まで戻れるか）と RTO（何時間で戻せるか）」の目標を事業側と合意し、それを満たす設定（例えばデータベースの同期コミットの設定、キャッシュの永続化の設定）になっているかを、設計レビューで確認します（[10.3](../../10-cloud-and-sre/03-reliability-engineering/README.md)）。
2. **バックアップは「取っている」ではなく「戻せた」で評価する**。GitLab の事故の教訓は、仕組みの有無ではなく、失敗に気づく監視と、定期的な復元の訓練がなかったことです。3-2-1 ルール（3 つのコピー、2 種類の媒体、1 つは別の場所）に加え、ランサムウェアに備えた変更できないバックアップ（[11.5](../../11-security/05-security-operations/README.md)）と、復元の手順書と訓練の記録を、四半期ごとの確認項目にします。
3. **ストレージの種類の選択は、コストと設計の制約を同時に決める**。オブジェクトストレージは容量あたりの費用が安く耐久性も高い一方、rename や部分更新がないので、アプリの設計が変わります。共有ファイルシステムは既存のアプリを移しやすい反面、ロックや一貫性の制約、性能の頭打ちを抱えます。「とりあえず NFS」で始めたシステムの移行は大仕事になりがちなので、初期の選択で問いましょう。
4. **I/O モデルと言語・ランタイムの選択は、採用と運用に跳ね返る**。イベントループ型（Node.js、asyncio）は少ないリソースで多くの接続を捌けますが、ループを止めるコードが 1 行混ざるだけで全体が止まります。チームがその規律を守れるか、CPU を使う処理をどこに逃がすかまで含めて技術選定を行います。
5. **性能の数字を見るときは「fsync しているか」を確認する**。ストレージやデータベースのベンチマーク、ベンダーの提案資料の数字が、永続化の保証をどこまで含んでいるかで、比較の意味が変わります。クラウドのブロックストレージでは、IOPS やスループットの上限、バースト（一時的な上振れ）の仕組みも、突然の性能劣化の原因になるので、契約した性能を把握しておきます。

### 演習6（記述）: データの置き場所と永続化の設計

写真共有サービスのバックエンドを設計しています。次の 4 種類のデータについて、(a) 保存先の種類（ブロックストレージ上のファイルシステム／共有ファイルシステム／オブジェクトストレージ など）、(b) 書き込み時に永続性を守るための方法、(c) 障害や誤操作から守るための運用、を選び、理由を述べてください。

1. ユーザーがアップロードする写真（1 枚数 MB、一度書いたら変更しない、合計で数百 TB に増える）
2. ユーザー・投稿・コメントを管理する PostgreSQL のデータ
3. 20 台の推論サーバーが起動時に読み込む、画像分類の機械学習モデル（数 GB、週に 1 回更新）
4. 1 台の管理サーバー上の、ジョブの設定ファイル（管理画面から変更される）

<details>
<summary>解答例</summary>

| データ | 保存先 | 書き込み時の永続性 | 運用での保護 |
|---|---|---|---|
| 1. 写真 | オブジェクトストレージ（＋CDN で配信） | アップロードが完了（PUT が成功）してから、データベースに「投稿」を記録する。順序を逆にすると、存在しない写真を指す投稿ができる | バージョニングや削除保護、別リージョンへの複製、ライフサイクル管理（古いものを安い保存クラスへ）。容量が大きいので費用の見積もりが重要 |
| 2. PostgreSQL | ブロックストレージ上のファイルシステム（またはマネージドの DB サービス） | コミットは WAL の fsync（必要なら同期レプリケーション）で永続化される。fsync を無効にする設定はとらない | WAL のアーカイブによる任意時点への復元（PITR）と、定期的なベースバックアップを別の場所（オブジェクトストレージ）へ。復元の訓練を定期的に行う。NFS 上には置かない |
| 3. ML モデル | オブジェクトストレージに版ごとに不変の名前（例: バージョン番号やハッシュを含む名前）で置き、各サーバーが起動時にダウンロードする。コンテナイメージに含める方法もある | 書き込むのは学習パイプラインだけ。完成したファイルを 1 回の PUT で置き、最後に「現在の版」を示すマニフェストを更新する | 旧版を残しておき、問題があればマニフェストを戻して切り戻す。共有ファイルシステムで全サーバーが同じファイルを読む構成は、更新の途中の不整合や性能の頭打ちが起きやすい |
| 4. 設定ファイル | 管理サーバーのローカルディスク（ブロックストレージ） | 一時ファイル → fsync → rename → ディレクトリの fsync で原子的に置き換える | 変更の履歴を残す（設定を Git で管理する、変更前の版を保存する）。重要なら設定自体をデータベースで管理する |

採点の観点:

- 写真はオブジェクトストレージ、DB はブロックストレージ、という基本の対応に加え、「写真の PUT が成功してから DB に記録する」という **書き込みの順序** に触れていれば合格です。
- DB のバックアップを「スナップショットやレプリカがあるから十分」とせず、別の場所への PITR 可能なバックアップと **復元の訓練** まで書けていれば、本番の運用を任せられる水準です。
- ML モデルで「不変の名前 ＋ マニフェストの切り替え」によって、rename のないオブジェクトストレージで原子的な更新と切り戻しを実現できていれば、優れた設計です。

</details>

## 理解度チェック

**Q1. ハードリンクとシンボリックリンクの違いを、inode という言葉を使って説明してください。また、元のファイル名を `rm` したとき、それぞれのリンクはどうなりますか。**

<details>
<summary>解答</summary>

ハードリンクは、同じ inode（ファイルの実体）にディレクトリの中で別の名前を付けたもので、元の名前と区別はありません。inode のリンク数が増えます。シンボリックリンクは、「リンク先のパス名」を中身として持つ別のファイル（別の inode）です。

元の名前を `rm` すると、ハードリンクの場合はリンク数が 1 減るだけで、もう一方の名前から中身を今まで通り読めます。シンボリックリンクの場合は、指している名前が存在しなくなるので、たどろうとすると「ファイルが見つからない」エラーになります（リンク切れ）。

</details>

**Q2. `write()` が成功した後、`fsync()` を呼ぶ前に電源が落ちると、何が起きうるかを説明してください。また、Linux の既定の設定では、最大でどのくらいの時間分の書き込みが失われうるか、根拠とともに答えてください。**

<details>
<summary>解答</summary>

write の成功は、データがカーネルのページキャッシュにコピーされたことしか意味しません。ディスクへの書き戻しはカーネルが後で行うので、その前に電源が落ちると、書いたはずのデータは失われます。

既定では、書き戻しのスレッドが約 5 秒（`dirty_writeback_centisecs = 500`）ごとに起き、dirty になって 30 秒（`dirty_expire_centisecs = 3000`）を過ぎたページを書き出します。したがって、おおよそ 30 秒強の間の書き込みが失われうることになります（dirty ページの量が上限を超えた場合などは、それより早く書き出されます）。

</details>

**Q3. 設定ファイルを原子的に置き換える手順を 4 つのステップで書き、それぞれのステップを省いたときに何が起きうるかを説明してください。**

<details>
<summary>解答</summary>

1. **同じディレクトリに一時ファイルを作って書く**: 元のファイルを直接上書きすると、途中のクラッシュで空や書きかけのファイルが残る。別のファイルシステムに一時ファイルを作ると、rename が原子的でなくなる（コピーになるか、失敗する）。
2. **一時ファイルを fsync する**: 省くと、rename の記録が中身より先にディスクに届き、クラッシュ後に「新しい名前で中身が空（または一部）」のファイルが残りうる。
3. **rename で付け替える**: 同じファイルシステム内なら原子的で、読み手は古い版か新しい版のどちらかしか見ない。
4. **ディレクトリを fsync する**: 省くと、rename 自体（ディレクトリの内容の変更）がディスクに届く前にクラッシュした場合に、古い版に戻ってしまう（「保存しました」と応答した後なら、約束違反になる）。

</details>

**Q4. PostgreSQL が「fsync に失敗したら PANIC する」方針に変えたのはなぜですか。「失敗したら再試行する」方針の何が問題だったのでしょうか。**

<details>
<summary>解答</summary>

Linux では、書き戻しの I/O エラーは次の fsync で一度だけ報告され、その後、書き込めなかったページが clean（書き込み済み）として扱われたり、エラーの状態が消えたりする場合がありました。すると、再試行した fsync は成功を返すのに、データは実際にはディスクに届いていない、ということが起こりえます。「再試行すればいずれ書ける」という前提が成り立たなかったのです。

そこで PostgreSQL は、fsync が失敗したら、ページキャッシュ上のデータはもはや信用できないとみなしてプロセスを異常終了させ、確実にディスクに書かれている WAL から、再起動時にデータを作り直す方針にしました。

</details>

**Q5. RAID 5 の 4 台構成で、小さなランダム書き込みが遅くなる理由と、「RAID を組んでいるからバックアップは不要」という主張の誤りを説明してください。**

<details>
<summary>解答</summary>

RAID 5 では、データを書き換えるたびにパリティも更新する必要があります。小さな書き込みでは、旧データと旧パリティを読み、新しいパリティを計算して、新データと新パリティを書くため、1 回の書き込みが 4 回の I/O になります（書き込みペナルティ）。

RAID は、ディスクの物理的な故障からデータを守る仕組みです。誤った削除、アプリのバグによるデータの破壊、ランサムウェアによる暗号化などは、正常な書き込みとしてすべてのディスクに反映されるので、RAID では防げません。過去の時点に戻れるコピーを別の場所に持つバックアップが別途必要で、しかも定期的に復元できることを確かめる必要があります。

</details>

**Q6. オブジェクトストレージ（S3 など）と、ローカルのファイルシステムのセマンティクスの違いを 3 つ挙げ、それがアプリの設計にどう影響するかを説明してください。**

<details>
<summary>解答</summary>

- **部分更新・追記ができない**: オブジェクトは全体を PUT で置き換えるしかない。ログのような追記型のデータは、小さなオブジェクトに分けて書くか、別の仕組みに溜めてからまとめて書く。
- **rename がない**: 「一時的な名前で書いてから付け替える」原子的な置き換えができない。完成したオブジェクトを 1 回の PUT で書き、どれが最新かはマニフェストやデータベースで管理する。
- **ディレクトリがない**: 「ディレクトリ」はキーの接頭辞にすぎず、ディレクトリ単位の原子的な操作はない。大量のキーの一覧も、ページングされた API 呼び出しになる。
- ほかに、ロックの仕組みがない（条件付き書き込みで代替する）、1 回の操作の遅延がローカルディスクより桁違いに大きい、なども挙げられます。

</details>

**Q7. 接続ごとにスレッドを作るサーバーと、イベントループのサーバーを比べ、それぞれの長所と短所を挙げてください。また、イベントループの中で通常のファイルを読むと何が問題になりますか。**

<details>
<summary>解答</summary>

- **接続ごとのスレッド**: コードが上から下へ素直に書け、1 つの接続の処理が重くても他の接続は別スレッドで進む。一方、接続数に比例してスレッドのメモリとコンテキストスイッチのコストが増え、数万接続では重くなる。
- **イベントループ**: 1 本のスレッドで多数の接続を扱え、接続あたりのコストが小さい。一方、接続ごとの状態を明示的に管理する必要があり（部分的な読み書き、背圧）、ループの中でブロックする処理や重い計算を 1 つでも行うと、すべての接続が止まる。

通常のファイルは、epoll などの多重化の仕組みでは「常に準備ができている」と扱われ（Linux の epoll には登録すらできない）、実際の読み込みはディスクを待ってブロックします。その間、ループ全体が止まるので、ファイル I/O はスレッドプールに逃がすか（Node.js の libuv がそうしている）、io_uring のような本物の非同期 I/O を使います。

</details>

**Q8. `fcntl` による POSIX ロックと `flock` の違いのうち、実務で問題になりやすい点を説明してください。**

<details>
<summary>解答</summary>

POSIX ロック（`fcntl`）はプロセスが持ち主で、そのプロセスが **同じファイルを指す fd のどれか 1 つでも閉じると**、そのファイルに対するロックがすべて外れます。例えば、あるライブラリがロックを取っている間に、同じプロセスの別の部分（別のライブラリ）が同じファイルを開いて読み、閉じただけで、気づかないうちにロックが外れてしまいます。SQLite のドキュメントも、データベースが壊れる原因の 1 つとしてこの性質を挙げています。

`flock` はオープンファイル記述が持ち主なので、別に開いた fd を閉じても影響を受けません（ただしファイル全体のロックしかできない）。Linux 3.15 以降の OFD ロックは、バイト範囲のロックでありながらオープンファイル記述を持ち主にすることで、この問題を解消しています。

</details>

## まとめ

- ファイルは **inode（実体）** と **ディレクトリ（名前 → inode）** から成り、fd は「fd 表 → オープンファイル記述 → inode」の 3 段で実体を指す。削除しても、開いている fd がある限り領域は解放されない。
- `write` は **ページキャッシュへのコピー** にすぎない。永続化には `fsync` が必要で、それは高価（この環境で約 80 倍）なので、グループコミットなどでまとめて使う。
- ファイルの置き換えは **一時ファイル → fsync → rename → ディレクトリの fsync**。fsync の失敗は再試行で取り返せないので、確実な場所からやり直す。
- ジャーナリングやコピーオンライト型のファイルシステムが守るのはファイルシステム自身の一貫性で、アプリのデータは **長さ＋チェックサム** の形式と回復処理で自ら守る。RAID はバックアップではない。
- SSD は上書きできず、FTL・ガベージコレクション・寿命という独特の性質を持つ。ネットワーク越しのストレージは、ブロック・ファイル共有・オブジェクトで **セマンティクスが違う**。
- 大量の接続は **I/O 多重化（epoll・kqueue）とイベントループ** で捌く。部分的な読み書き・背圧・ループを止めないことが要点。io_uring は完了通知型の非同期 I/O を Linux にもたらした。
- ファイルロックは勧告的で、1 台のマシンの中でしか効かない。POSIX ロックの「どの fd を閉じても外れる」性質に注意する。
