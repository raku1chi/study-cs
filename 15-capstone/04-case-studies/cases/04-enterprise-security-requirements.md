# ケース04: 大型商談で SOC 2／ISMS と SAML SSO を求められた

> 年間 1.8 億円の商談。条件は「ISMS 認証または SOC 2 報告書」と「SAML によるシングルサインオン」です。相手の契約判断は 3 か月後。CEO は「チェックシートは全部『対応予定』と書いておいて」と言っています。

| 項目 | 内容 |
|---|---|
| あなたの立場 | 建設業向け施工管理 SaaS の CTO（セキュリティ責任者も兼務） |
| テーマ | エンタープライズ対応、セキュリティ認証、誠実な顧客対応 |
| 難易度 | ★★☆ |
| 目安時間 | 回答 45 分 ＋ 解説の検討 20 分 |

## 状況

### 会社の概要

| 項目 | 内容 |
|---|---|
| 会社 | 株式会社ノキシタ（架空）。中小の建設会社向けに、写真・図面・日報・工程表を現場で共有する施工管理アプリ「ノキシタ」を提供 |
| ステージ | シリーズ A。導入 2,300 社、ARR 7 億円 |
| 人員 | 従業員 70 名、エンジニア 16 名。セキュリティの専任者はいない |

### セキュリティの現状

- 認証はメールアドレスとパスワード（任意で Google アカウントでのログイン）。多要素認証はない。
- アプリの操作ログは 30 日保存。顧客が参照する機能はない。
- 規程は「情報セキュリティ基本方針」だけ。2 年前に作成し、それ以降は更新していない。
- 第三者による脆弱性診断は、一度も受けていない。
- 本番環境には、エンジニア 16 名全員が管理者権限でアクセスできる。
- 退職者のアカウント削除は手作業で、チェックリストはない。

### 商談

大手ゼネコンの峰岸建設（架空、従業員 1.2 万人）が、全国の現場と協力会社を含む 8,000 ID での導入を検討しています。年間 1.8 億円、3 年契約。実現すれば ARR は 1.26 倍になります。

峰岸建設の情報システム部から、312 項目のセキュリティチェックシートとともに、次の要件が示されました。

1. ISMS 認証（ISO/IEC 27001）の取得、または SOC 2 Type 2 報告書の提出
2. 同社の ID 管理基盤（IdP）と SAML 2.0 で連携するシングルサインオンと、退職者のアカウントの自動削除（プロビジョニング）
3. IP アドレスによるアクセス制限
4. 監査ログの 1 年以上の保存と、顧客による参照・エクスポート
5. 年 1 回の第三者による脆弱性診断
6. データの国内保管

### 関係者の声

- 峰岸建設 情報システム部の堤課長: 「現場からは、ぜひ使いたいと言われています。ただ、うちも監査で説明しなければならないので、チェックシートは形式だけでなく中身を見ます」
- CEO の大野さん: 「これが取れれば会社のステージが変わる。チェックシートは全部『対応予定』と書いておいて、契約してから考えればいい」
- 営業部長の飯田さん: 「競合の大手はもう ISMS を持っています。うちだけ無いと、比較表で負けます」
- セキュリティに関心のあるエンジニアの堀さん: 「SAML なら 2 週間で作れますよ。ライブラリもありますし」

## 制約

- 先方の契約判断（役員会）は 3 か月後。
- 今期のロードマップには、既存顧客に約束した工程表の機能強化がある。
- 今回の対応に使える予算は、外部支援を含めて約 3,000 万円（CEO と CFO の内諾済み）。
- SOC 2 Type 2 報告書は、統制が一定の期間（数か月〜1 年程度）有効に運用されていたことを監査人が評価するもので、3 か月以内に取得するのは現実的ではない。
- ISMS 認証も、規程の整備、一定期間の運用、内部監査、マネジメントレビューを経て審査を受ける。ゼロから始める場合、半年〜1 年程度かかることが多い（2026 年時点の一般的な目安。審査機関や支援会社に確認すること）。

## 問い

1. 3 か月で「できること」「できないこと」「期限付きで約束できること」を整理してください。
2. CEO の「全部『対応予定』と書いておいて」に、どう応えますか。
3. SAML SSO を自前で実装するか、外部の認証基盤サービスを使うか。判断の観点を挙げてください。
4. この商談を機に、会社のセキュリティ体制をどう立ち上げますか（人・予算・順序）。

## 考えるヒント

- 峰岸建設の情報システム部は、何を恐れていて、社内の誰に何を説明しなければならないのでしょうか。
- チェックシートの回答は、契約上どういう意味を持ちうるでしょうか。
- 認証そのものが間に合わなくても、先方の懸念を下げる方法はないでしょうか。
- SAML の実装で、過去に多くの脆弱性が見つかってきたのはどの部分でしょうか。
- この 1 社への対応は、会社の戦略（大企業市場に本格的に進むかどうか）とどう関係するでしょうか。

### 検討の観点

**1. 顧客の本当の関心を理解する。** 峰岸建設の情報システム部は、ツールそのものより、「自社のデータを預けても大丈夫だと、社内の監査や経営に説明できるか」を気にしています。認証（ISMS・SOC 2）は、第三者が統制を確認したという証拠の一つの形であり、目的は統制そのものです。証明書が間に合わなくても、統制の実態と改善の道筋を示せれば、交渉の余地は生まれます。

**2. 誠実さは交渉の武器になる。** チェックシートの回答は、契約の前提として扱われることが多く、事実と異なる回答は、発覚したときに契約解除や損害賠償の問題になりえます。何より、大企業の情報システム部門は、回答の矛盾を見抜くのに慣れています。「全部対応予定」と書くより、「ここは対応済み、ここは○月までに対応、ここは代替策」と具体的に書いた回答の方が、信頼を得やすいものです。

**3. 時間の現実を受け入れる。** 3 か月で ISMS 認証や SOC 2 Type 2 を取るのは困難です。代わりに提示できる証拠は次のようなものです。

- 第三者の脆弱性診断の報告書と、指摘への是正の記録
- セキュリティの取り組みをまとめた資料（ホワイトペーパー）
- すでに整備した規程と、実施した統制（管理者権限の削減、多要素認証の必須化など）の記録
- 認証取得のロードマップと、それを契約上約束する条項（例: 契約開始から一定期間内に ISMS 認証を取得する、四半期ごとに進捗を報告する、未達の場合の解約権）

6 つの要件を、3 か月という時間軸で整理すると、例えば次のようになります。

| 区分 | 該当する要件・施策 |
|---|---|
| 3 か月でできる | SAML SSO の基本機能、IP アドレスによる制限、監査ログの保存期間の延長とエクスポート、第三者の脆弱性診断と是正、多要素認証の必須化、本番の管理者権限の最小化、規程の整備 |
| 3 か月ではできない | ISMS 認証の取得、SOC 2 Type 2 報告書の提出 |
| 期限付きで約束できる | ISMS 認証の取得（審査機関と確認した時期）、SCIM による自動プロビジョニング（3 か月で間に合わない場合）、年 1 回の診断の継続 |
| 確認すれば「対応済み」にできる可能性 | データの国内保管（すでに国内のリージョンで運用していれば、バックアップやログの保存先まで含めて確認する） |

**4. ISMS と SOC 2 のどちらを目指すか。** 国内の大企業や自治体が顧客の中心なら、ISMS 認証（日本では JIS Q 27001 として規格化され、認定を受けた審査機関が審査する）が伝わりやすいことが多いでしょう。海外展開や外資系の顧客が視野にあるなら、米国公認会計士協会（AICPA）の枠組みに基づく SOC 2 が求められやすくなります。両方を同時に目指すのは、この規模の会社には重すぎます。なお、ISMS の規格は 2022 年に改訂されています（2026 年時点）。

**5. SSO はエンタープライズの「入場券」。** 大企業は、社員の入退社に合わせてアカウントを一元管理したいので、SAML や OpenID Connect による SSO と、SCIM などによる自動プロビジョニングを求めます。これは峰岸建設だけでなく、今後のすべての大企業案件で必要になります。なお、SSO を必須にすれば、IdP 側でアカウントを無効にした時点でログインはできなくなりますが、アプリ側のアカウントや、発行済みのセッション・API トークンは残ります。初回ログイン時にアカウントを自動で作る方式（JIT プロビジョニング）だけでは「退職者のアカウントの自動削除」は満たせないため、SCIM への対応か、それに代わる運用を示す必要があります。

**6. 自前か、外部サービスか。** SAML は XML 署名に基づく仕組みで、署名の検証の不備に起因する脆弱性が、複数の SAML ライブラリで繰り返し報告されてきました。実装するなら、実績があり保守の続いているライブラリを使い、署名の検証を自作しないことが大前提です。また、「2 週間で作れる」のはログインの基本部分であり、顧客ごとの IdP の設定画面、証明書の更新、主要な IdP ごとの差異への対応、エラー時の振る舞い、プロビジョニングまで含めると、数か月単位の仕事になることが珍しくありません。

**7. これは戦略の問題でもある。** 大企業向けに進むなら、SSO、監査ログ、権限管理、SLA、サポート体制、契約法務、セキュリティ審査への対応が継続的に必要になります。この 1 社のための一時的な対応ではなく、「大企業市場に進む」という経営判断として CEO と合意し、価格（大企業向けプランに SSO などを含める）にも反映させます。

### 選択肢とトレードオフ

**認証について**

| 選択肢 | 主な利点 | 主なリスク・コスト | 向いている条件 |
|---|---|---|---|
| A. ISMS 認証の取得を目指す | 国内の大企業・自治体に広く認知されている。チェックシートの多くの項目に答えやすくなる | 整備と運用に数か月〜1 年。維持審査・更新の継続コスト。書類だけの形骸化の危険 | 顧客の中心が国内企業 |
| B. SOC 2（Type 1 から Type 2 へ） | 海外・外資系の顧客に通じる。統制の運用の評価として詳細 | 監査費用が高くなりやすい。Type 2 には観察期間が必要 | 海外展開や外資系顧客が視野にある |
| C. 認証なしで、診断報告書・資料・誠実な回答で対応 | 早く安い | 要件を満たせない顧客がいる。案件ごとの個別対応が重い | 中小企業中心で、大企業案件が例外的 |
| D. C で当面をしのぎつつ、A を期限付きで契約上約束する | 商談を進めながら、実態を伴わせられる | 期限を守れないと契約上のリスク。社内の工数の確保が必要 | 今回のように、認証が間に合わない大型案件 |
| E. 商談を見送る | 既存顧客への約束に集中できる | 成長機会を失う | 大企業市場に進まないと決めた場合 |

**SSO について**

| 選択肢 | 主な利点 | 主なリスク・コスト |
|---|---|---|
| 自前実装（実績のあるライブラリを使う） | 継続費用が低い。柔軟に作れる | 署名検証まわりの脆弱性の歴史。IdP ごとの差異、証明書の更新、顧客ごとの設定画面など、周辺の作業が大きい |
| 外部の認証基盤サービス（IDaaS など） | 早い。SAML・OpenID Connect・SCIM・多要素認証をまとめて得られる | 利用者数に応じた費用。認証という中核を外部に依存する。既存ユーザーの移行 |

判断の観点は、今後の大企業案件の見込み数、認証まわりを保守できる人材がいるか、1 ユーザーあたりの費用と価格の関係、既存の認証の作りです。

### 推奨アプローチの一例

**最初の 24 時間**

- CEO の大野さんと 1 対 1 で話す。「全部『対応予定』と書く」ことのリスク（契約上の問題、先方の情報システム部は中身を見ること、発覚すれば取引全体を失うこと）を伝え、代わりに「誠実なロードマップで勝つ」案を示す。
- 営業を通じて、先方の意思決定の関係者、スケジュール、評価の基準を確認する。

**最初の 1 週間**

1. 312 項目を 4 つに仕分ける: 対応済み／3 か月以内に対応／期限付きで約束／対応しない（代替策を示す）。
2. 3 か月以内にやる統制を決める: 本番の管理者権限の最小化、全社員の多要素認証、退職者処理の手順化、監査ログの保存期間の延長。
3. 第三者の脆弱性診断を発注する。
4. 認証取得の支援会社と審査機関に相談し、現実的なスケジュールを確認する。
5. SAML SSO を自前で作るか外部サービスを使うか、1 週間で比較して決める。

**2 週目**

- 営業に依頼し、峰岸建設の堤課長との面談を設定する。ロードマップを直接説明し、先方が社内の説明に使える資料として渡す。要件のうち、絶対に必要なものと調整の余地があるものを確認する。

**最初の 1 か月**

- SSO（SAML と、SCIM または初回ログイン時の自動作成）の実装を開始する。IP 制限と監査ログのエクスポートも並行して進める。
- 体制を作る。堀さんをセキュリティ担当に任命して工数の半分を割り当て、外部のセキュリティ専門家（非常勤の CISO のような役割）と契約し、ISMS の取り組みを正式に開始する。予算 3,000 万円は、外部支援、診断、審査、SSO の費用、社内の工数の確保に配分する。
- 既存顧客への約束（工程表の強化）の時期に影響が出るなら、その顧客に早めに伝える。

**3 か月後（契約判断）**

- 診断報告書と是正結果、SSO の提供開始、ISMS 取得のスケジュールと進捗を示す。
- 契約書に、認証の取得期限と報告義務を盛り込む。期限は、審査機関と確認した現実的な日付にする。

### 避けるべき対応

- **実施していないことを「対応済み」「対応予定」と書く**。信頼と契約の両方を失うおそれがあります。
- **審査機関に確認せずに、認証の取得期日を約束する**。
- **認証を「書類づくり」として外注に丸投げする**。現場の運用が伴わない形骸化した ISMS は、次の事故を防ぎません。
- **SAML の署名検証を自作する**。
- **既存顧客への約束を黙って後回しにする**。
- **この 1 社の要件を無批判にすべて受け入れる**。先方専用の機能分岐を作ると、製品が個別仕様化し、保守の負担が増え続けます。

### 条件が変わると

- 同様の大企業案件が今後も続く見込みなら、認証取得は「この案件のため」ではなく、事業戦略として正当化できます。
- 顧客が外資系や海外企業なら、SOC 2 を優先します。
- 相手が官公庁の場合は、政府のクラウドサービス調達で使われる評価制度（ISMAP）など、別の枠組みが関係することがあります（2026 年時点の制度を確認してください）。
