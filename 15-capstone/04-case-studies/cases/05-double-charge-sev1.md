# ケース05: SEV1 — 決済の二重課金が発生した

> 月初の定期課金で、約 1.8 万人のお客様に二重請求が発生しました。月曜の午前 9 時 50 分、オンコール担当から電話が入ります。CEO は飛行機の中、決済に最も詳しいエンジニアは休暇中。そして正午には、次の課金バッチが自動で動く予定です。

| 項目 | 内容 |
|---|---|
| あなたの立場 | ミールキット定期宅配サービスの CTO |
| テーマ | インシデント対応、顧客対応、冪等性 |
| 難易度 | ★★☆ |
| 目安時間 | 回答 45 分 ＋ 解説の検討 20 分 |

## 状況

### 会社の概要

| 項目 | 内容 |
|---|---|
| 会社 | 株式会社キッチンメイト（架空）。ミールキットの定期宅配サービスを運営。月額 5,980 円のプランが中心 |
| 規模 | 会員 9.2 万人、年間売上 70 億円。従業員 240 名、エンジニア 22 名、カスタマーサポート 30 名 |
| 決済 | クレジットカード・デビットカードで、決済代行会社（PSP）を経由して課金。毎月 1 日の午前 3 時に定期課金バッチが動く |

### 時系列（10 月 1 日・月曜）

| 時刻 | 出来事 |
|---|---|
| 03:00 | 定期課金バッチが開始 |
| 03:40 | PSP の API の応答が遅延し、バッチの一部の要求がタイムアウト。バッチのリトライ機能が、「完了を確認できなかった」約 1.8 万件の課金要求をそのまま再送した |
| 04:10 | バッチ完了。「失敗」と判定された 1,120 件は、12:00 の再課金バッチで再度課金される予定になっている |
| 08:30 | SNS で「キッチンメイトから 2 回引き落とされた」という投稿が広がり始める |
| 09:12 | カスタマーサポートへの電話とメールが急増 |
| 09:40 | オンコール担当の井上さん（入社 2 年目）が、PSP の管理画面で、同じ会員の課金が 2 件ずつ成立していることを確認 |
| 09:50 | あなたに電話 |

### 10 時の時点で分かっていること

- 二重課金は推定約 1 万 8,400 件。1 件あたりは主に 5,980 円で、合計約 1.1 億円。
- デビットカードの会員は、口座から即時に 2 回引き落とされている。「今日の家賃の引き落としができなくなる」という問い合わせも来ている。
- クレジットカードの利用限度額に達し、他の支払いが通らなくなった会員もいる。
- 問い合わせは 1 時間で 214 件。SNS の投稿は増え続けている。
- 決済まわりに最も詳しい西さんは休暇中（電話はつながる）。
- CEO の田村さんは福岡行きの飛行機の中で、11 時 30 分に着陸予定。
- 広報担当は 1 名。
- PSP の担当者の説明は次の通り。「当日中であれば、カード会社への売上データの送信前に取り消せる取引があり、その場合は会員の明細に載らない可能性が高い。送信後の取引は返金（売上の取消）扱いになり、明細に請求と取消の両方が載ることがある。デビットカードの口座への返金の時期はカード発行会社によって異なる。返金 API は毎秒 20 件まで」。

## 制約

- 12:00 に再課金バッチが自動で実行される予定になっている。
- 決済の「正」の記録は PSP 側にある。社内のデータベースの課金ステータスは、タイムアウトした要求については正確ではない。
- カスタマーサポートは 30 名体制、電話回線は 20 回線。
- 返金 API の上限は毎秒 20 件。1.8 万件なら単純計算で 15 分程度だが、確認と再試行を含めると数時間かかりうる。

## 問い

1. 電話を受けてから最初の 60 分で、何をしますか。「止血」「顧客」「社内外への連絡」の 3 つの面で答えてください。
2. 返金を「機械的に一括」で行うか、「確認してから」行うか。判断の観点と、あなたの案を示してください。
3. 顧客・CEO・取締役・PSP・カスタマーサポートへの連絡を、誰が、いつ、何を伝えるか設計してください。
4. 再発防止策を、技術と組織の両面から提案してください。

## 考えるヒント

- 今この瞬間も被害を広げうる「時限爆弾」はどこにありますか。
- 返金の処理そのものが、2 つ目のインシデントを生む可能性はありませんか。
- 原因がすべて分かるまで、お客様への告知を待つべきでしょうか。
- なぜタイムアウトの後の再送で二重課金が起きたのでしょうか。「一度だけ実行する」ことを、ネットワーク越しの呼び出しで保証するには何が必要でしょうか。
- 西さんが休暇中だと対応が難しくなることは、何を示唆していますか。

### 検討の観点

**1. 止血が最優先。** 最も危険なのは、12:00 の再課金バッチです。「失敗」と判定された 1,120 件の中には、実際には PSP 側で課金が成立しているものが含まれている可能性が高く、再課金すればさらに二重課金が増えます。まず自動実行を止め、他に自動で動く決済関連のジョブがないかを確認し、決済まわりのデプロイを凍結します。

**2. 指揮系統をはっきりさせる。** SEV1（最も重大度の高い障害）を宣言し、インシデントコマンダー（指揮役）を決めます。CTO がすべてを 1 人で抱えると、技術の調査・顧客対応・経営への報告のどれかが止まります。例えば、経験のある EM が指揮役、井上さんと西さん（電話で参加）が技術調査、あなたが経営・社外への判断と連絡、カスタマーサポートのリーダーが顧客対応、という分担にします。時系列の記録係も置きます。

**3. 被害範囲は「正」の記録から求める。** 社内の DB はタイムアウトした要求の結果を知らないので、PSP の取引データを取得し、会員データと突き合わせて「同じ会員・同じ請求期間に成立した課金が 2 件以上ある」一覧を作ります。

**4. 顧客の被害を小さくすることを、最優先の基準にする。** 同じ二重課金でも、デビットカードの会員は今まさに口座の残高が減っており、家賃や公共料金の引き落とし不能という二次被害が起きうる状態です。取消・返金をデビットカードの会員から優先し、二次被害で発生した手数料などを補償する窓口を用意することも検討します。

**5. 返金そのものを安全に行う。** 大量の返金を急いで行うと、同じ課金を 2 回返金する「二重返金」という第二のインシデントが起きえます。返金の要求にも、元の課金 ID をキーとした冪等性（同じ要求を何度送っても結果が 1 回分になる性質）を持たせ、実行前の確認（dry run）、少量での試行、実行後の突合をセットにします。

**6. コミュニケーションは「早く・正直に・具体的に」。** 原因が分かるまで黙っているのは最悪の選択です。第一報では、分かっている事実（10 月 1 日の定期課金の一部で二重請求が発生したこと）、対応（全額を取消・返金すること、お客様の手続きは不要であること）、次の更新の時刻を伝えます。原因の推測は書きません。「システム障害により」といった曖昧な表現より、何が起きたのかを具体的に書く方が信頼されます。

**7. 根本原因は「結果不明」の扱い。** タイムアウトは「失敗」ではなく「結果が分からない」状態です。これを失敗とみなして同じ要求を再送したことが、二重課金の直接の原因です。分散システムでは、メッセージは「少なくとも 1 回」届くことは保証できても、「ちょうど 1 回」を保証するには、受け手の側で重複を検出する仕組み（冪等キー）が必要です。多くの決済 API には、要求ごとに一意のキーを付けて重複を防ぐ仕組みがあります（例: Stripe の `Idempotency-Key` ヘッダ）。PSP がその仕組みを提供していない場合は、再送の前に照会 API で結果を確認する設計にします。

### 選択肢とトレードオフ

| 返金の方法 | 主な利点 | 主なリスク・コスト | 向いている条件 |
|---|---|---|---|
| A. 検出した全件を、ただちに機械的に取消・返金 | 最速。顧客の負担が最小 | 判定の誤り（正当な 2 件目の課金、例えば追加注文）まで返金してしまう。二重返金の危険 | 判定条件が単純で、正当な複数課金がありえない場合 |
| B. 1 件ずつ人が確認して返金 | 誤りが少ない | 1.8 万件では数日〜数週間かかる。顧客の不満と二次被害が拡大する | 件数が少ない場合 |
| C. 厳格な条件で「明白な重複」を機械的に判定して取消・返金し、曖昧なものだけ人が確認 | 速さと正確さの両立 | 判定条件の設計と検証が必要 | 多くの場合 |

C の判定条件の例は、「同じ会員・同じ請求期間・同じ金額で、PSP 上で成立した課金が 2 件あり、どちらも 03:00〜04:10 のバッチの時間帯に作られ、その日に他の注文がない」ものです。実行前に対象を抽出し、2 名で 50 件程度を抜き取り確認してから、1,000 件単位で実行し、各回の後に突合します。当日中に取り消せる取引は、会員の明細に載らない可能性が高いので、返金より取消を優先します。

### 推奨アプローチの一例

**最初の 15 分**

1. SEV1 を宣言し、インシデントコマンダーを任命する。専用のチャンネルと電話会議を立ち上げ、記録を開始する。
2. 12:00 の再課金バッチの自動実行を止める。止めたことを 2 人で確認する。
3. 決済まわりのデプロイを凍結する。西さんに電話し、調査への参加を依頼する。

**15〜60 分**

1. 技術: PSP の取引データと会員データを突き合わせ、二重課金の一覧を作るクエリを書く（まず件数と金額の確定）。
2. 顧客: カスタマーサポートに一次回答の文面を渡す（「二重請求を確認しています。全額を取消・返金します。お客様の手続きは不要です。詳細は本日○時までにメールでお知らせします」）。電話回線は 20 しかないので、電話がつながりにくい前提で、ウェブのお知らせとメールを主な連絡手段にする。問い合わせフォームに専用の項目を設ける。
3. 社外: 11 時までに、公式サイト・アプリ・SNS に第一報を出す。CEO が機内にいる間の第一報は、事前の取り決め（またはあなたの判断）で出し、着陸後すぐに電話で報告できるよう要点をまとめる。取締役にはチャットで第一報を入れる。
4. PSP: 取消・返金の方法、優先順位、返金 API の制限の緩和が可能かを相談する。

**連絡の設計（例）**

| 相手 | 誰が | いつ | 何を |
|---|---|---|---|
| カスタマーサポート | CS リーダー（文面は指揮役と CTO が承認） | 30 分以内。以後 1 時間ごと | 一次回答の文面、エスカレーションの基準、デビットカードの会員の優先対応 |
| 会員全体 | 広報担当（CTO が承認） | 11 時までに第一報。以後は予告した時刻に | 事実、全額の取消・返金、手続き不要、次の更新の時刻 |
| 対象の会員（個別） | CS と技術チーム | 24 時間以内 | 金額、取消・返金の方法と反映時期の目安、補償の窓口 |
| CEO | CTO | 着陸直後（11:30）に電話 | 事実、影響、実施済みの措置、CEO に決めてほしいこと（補償の方針、公表の範囲） |
| 取締役 | CTO（CEO の着陸後は CEO） | 11 時ごろにチャットで第一報。当日中に続報 | 事実、影響の規模、対応の状況 |
| PSP | 技術リード（西さんが電話で補佐） | ただちに | 取消・返金の方法、API の制限の緩和、カード会社からの問い合わせへの対応 |
| 経理 | CTO | 当日中 | 返金の規模と会計処理 |

**24 時間以内**

- 明白な重複の取消・返金を完了する（デビットカードの会員を優先）。
- 対象の会員全員に個別のメールを送る。金額、取消・返金の方法、明細や口座に反映される時期の目安（カード会社によって異なることも含めて）、二次被害の補償の窓口。
- 第二報で、原因の概要と再発防止の方針を伝える。
- 会計処理（売上と返金の修正）を経理と確認する。

**1 週間以内**

- 残りの曖昧なケースの確認と返金を終える。PSP のデータとの突合で、差分がゼロであることを確認する。
- 非難しない形式のポストモーテム（事後検証）を行い、取締役会に報告する。

**1 か月以内（次の 1 日の課金の前に）**

- 課金要求への冪等キーの付与、課金の状態管理（未課金 → 要求中 → 成功・失敗・結果不明）、結果不明の場合の照会 API による確認。
- 毎日の PSP との突合と、異常の検知（成立した課金の件数が対象会員数を超えたら、ただちにアラート）。
- 次回の定期課金は、少量で実行して突合してから全量に進む手順にする。
- 決済を理解するメンバーを最低 2 名にし、手順書と障害訓練を整える。

### 避けるべき対応

- **状態を合わせるために、バッチを「念のため」再実行する**。被害を拡大させる典型的な行動です。
- **本番のデータベースを手作業で直接書き換える**。何をしたかの記録が残らず、突合ができなくなります。
- **原因がすべて分かるまで告知を待つ**。SNS で先に広がり、隠していると受け取られます。
- **決済代行会社を公に非難する**。タイムアウトは起こりうる前提で設計すべきでした。顧客に対する責任は自社にあります。
- **入社 2 年目のオンコール担当に任せきりにする、あるいは CTO がすべてを 1 人で抱える**。
- **返金の時期について、守れない約束をする**（「明日には口座に戻ります」）。反映の時期はカード会社によって異なります。
- **管理画面から手作業で返金し、記録を残さない**。二重返金の原因になります。

### 条件が変わると

- 影響が 20 件なら、1 件ずつ電話で謝罪し、手作業で返金するのが最善かもしれません。規模によって最適な手段は変わります。
- 資金移動業や前払式支払手段の発行など、決済そのものが規制の対象となる事業では、監督官庁への報告が必要になる場合があります。具体的には専門家に確認してください。
- 原因が PSP 側の障害だった場合でも、顧客への一次対応と説明の責任は自社にあります。
