## なぜ学ぶのか

バージョン管理システムは、ソフトウェア開発のすべての活動の土台です。コードの変更は必ずそこを通り、レビューもリリースも障害調査も、その履歴の上で行われます。

- **仕組みを知らないと、事故の対応を誤る**: 間違ったリベースで他人のコミットを消す、衝突の解消でコードを失う、`git push --force` で共有ブランチを壊す、といった事故は、Git の内部モデル（ref はコミットを指すポインタにすぎない）を理解していれば、原因の見当も復旧（reflog）もすぐにつきます。
- **秘密情報の漏洩は現実の事件になっている**: 米国連邦取引委員会（FTC）の発表によれば、Uber では 2014 年にエンジニアが GitHub に公開してしまったアクセスキーが悪用され、2016 年には GitHub の非公開のリポジトリのコードに平文で含まれていたクラウドのアクセスキーが悪用されて、米国の利用者とドライバーの氏名とメールアドレス約 2,560 万件などが流出しました（Uber 自身は、全世界で約 5,700 万人の情報が流出したと公表しています）。「リポジトリに秘密情報を入れない」「入れてしまったら即座に無効化する」は、全エンジニアが知っているべき規律です。
- **レビューは開発速度を左右する**: 多くのチームで、コードを書き終えてからマージされるまでの時間の大部分は、レビューの「待ち」です。レビューの目的と運用を設計することは、組織のスループットを設計することでもあります（[13.7](../../13-technical-leadership/07-delivery-and-productivity/README.md)）。

## 1. バージョン管理が解決する問題

バージョン管理システム（VCS）は、次の 3 つの問題を解決します。

1. **履歴**: いつ、誰が、なぜ、何を変えたか。過去のどの時点にも戻れる。
2. **並行作業**: 複数の人が同じコードを同時に変更し、後で統合できる。
3. **信頼**: 手元のコードが、レビューを通った「あのコード」と同じであることを確かめられる。

初期の VCS（RCS）はファイル単位で履歴を管理し、CVS や Subversion は 1 台の中央サーバーにリポジトリを置く **集中型** でした。Git（2005 年に Linus Torvalds が Linux カーネルの開発のために作成）や Mercurial は、全員が履歴の完全な複製を持つ **分散型** です。分散型では、コミット・ブランチ作成・履歴の閲覧がすべて手元で完結するので速く、ブランチを気軽に作れるようになりました。2026年時点では、ソフトウェア開発のバージョン管理は事実上 Git が標準になっています。

## 2. Git の内部構造 — 内容で番地が決まるオブジェクト

### 2.1 blob — ファイルの内容

Git の中核は、**内容のハッシュ値をキーにしてデータを保存する、キー・バリュー型の保管庫**（content-addressable storage, 内容アドレス方式）です。保存されるものを **オブジェクト** と呼び、ファイルの内容は **blob** オブジェクトになります。

```bash
$ echo "hello" | git hash-object --stdin
ce013625030ba8dba906f756967f9e9ca394464a
```

このハッシュ値は、次の規則で計算されています。`"<型> <バイト数>\0"` というヘッダを内容の前に付け、全体の SHA-1 を取るのです。

```python
import hashlib
data = b"hello\n"
print(hashlib.sha1(b"blob %d\x00" % len(data) + data).hexdigest())
```

```text
ce013625030ba8dba906f756967f9e9ca394464a
```

`git hash-object -w` で実際に保存すると、ハッシュの先頭 2 文字をディレクトリ名、残りをファイル名として `.git/objects/` の下に、zlib で圧縮して書き込まれます。

```bash
$ echo "hello" > hello.txt
$ git hash-object -w hello.txt
ce013625030ba8dba906f756967f9e9ca394464a
$ ls .git/objects/ce/
013625030ba8dba906f756967f9e9ca394464a
$ git cat-file -t ce01362      # 型
blob
$ git cat-file -s ce01362      # 大きさ（バイト）
6
$ git cat-file -p ce01362      # 中身
hello
```

```python
import zlib
raw = zlib.decompress(open('.git/objects/ce/013625030ba8dba906f756967f9e9ca394464a', 'rb').read())
print(raw)
```

```text
b'blob 6\x00hello\n'
```

内容アドレス方式には、重要な性質がいくつもあります。

- **同じ内容は必ず同じハッシュになる**。1,000 個のブランチに同じファイルがあっても、保存されるのは 1 つだけ（重複の排除）。
- **内容が 1 ビットでも変われば、ハッシュが変わる**。したがって、ハッシュ値を知っていれば、受け取ったデータが改ざんされていないかを検証できる。
- blob には **ファイル名が含まれない**。名前は次の tree が持つ。

（本文の Git の出力は Git 2.43 で確認したものです。）

### 2.2 tree — ディレクトリ

**tree** オブジェクトはディレクトリに相当し、「モード・名前・参照先オブジェクトのハッシュ」の組を並べたものです。

```bash
$ git cat-file -p 15bbfb89
100644 blob 587be6b4c3f93f93c489c0111bba5596147a26cb	a.txt
040000 tree 2534d776854450fafa6839beab4d19369b521aac	a
100644 blob ce013625030ba8dba906f756967f9e9ca394464a	hello.txt
100755 blob 85ba14df52f8c72688537de6e7555fb402217b1e	run.sh
040000 tree 212c4fdae26c1d9b9ecee80ce328176151064663	src
```

モードは、通常のファイルが `100644`、実行可能ファイルが `100755`、サブディレクトリ（tree）が `040000` です（ほかにシンボリックリンクの `120000` と、サブモジュールのコミットを指す `160000` があります）。注目してほしい点が 2 つあります。

1. **並び順**: `a.txt` がディレクトリ `a` より先に来ています。Git は名前をバイト列として並べますが、**ディレクトリ名は末尾に `/` が付いているものとして比較** します。`a.txt` と `a/` を比べると、`.`（0x2E）は `/`（0x2F）より小さいので `a.txt` が先です。
2. **中身は人間向けの表示と違う**: `cat-file -p` は読みやすく整形した表示です。オブジェクトの実際の中身では、ハッシュは 16 進数の文字列ではなく **20 バイトの生のバイト列** で、ディレクトリのモードは先頭の 0 がない `40000` です。

```python
import zlib
raw = zlib.decompress(open('.git/objects/15/bbfb89a66be054ceb4e2b1023d98ab8d2fc6c4', 'rb').read())
print(raw[:60])
```

```text
b'tree 162\x00100644 a.txt\x00X{\xe6\xb4\xc3\xf9?\x93\xc4\x89\xc0\x11\x1b\xbaU\x96\x14z&\xcb40000 a\x00%4\xd7v\x85DP\xfa\xfah'
```

tree が子のハッシュを含み、その tree のハッシュが親の tree に含まれる、という入れ子の構造は **マークル木（Merkle tree）** と呼ばれます。根の tree のハッシュ 1 つで、ディレクトリ全体のすべてのファイルの内容が確定します。どこか 1 つのファイルが変われば、そこから根までの tree のハッシュがすべて変わり、変わっていない部分の tree と blob はそのまま再利用されます。

### 2.3 commit と tag

**commit** オブジェクトは、根の tree と、親のコミット、作者（author）と確定者（committer）、メッセージを持つテキストです。

```bash
$ git cat-file -p 5a28fd34
tree 15bbfb89a66be054ceb4e2b1023d98ab8d2fc6c4
author Alice <alice@example.com> 1700000000 +0900
committer Alice <alice@example.com> 1700000000 +0900

最初のコミット
```

時刻は UNIX 時間（秒）とタイムゾーンで記録されます（[1.1 情報の表現](../../01-computer-systems/01-data-representation/README.md)）。2 つ目以降のコミットには `parent` 行が、マージコミットには 2 つ以上の `parent` 行が入ります。author は変更を書いた人、committer はそれをリポジトリに確定させた人で、リベースやパッチの適用では両者が異なることがあります。

コミットのハッシュは、tree のハッシュと親のハッシュを含んでいます。したがって **コミットのハッシュ 1 つで、そのコミットに至るまでの全履歴と全ファイルの内容が確定** します。過去のどこかを 1 ビットでも書き換えれば、それ以降のすべてのコミットのハッシュが変わります。これが「履歴の書き換え」がはっきり分かる理由であり、ブロックチェーンと同じ種類の構造です。

4 つ目のオブジェクト **tag**（注釈付きタグ）は、特定のオブジェクト（通常はコミット）を指し、タグ名・作成者・メッセージ・（任意で）署名を持ちます。リリースのように「このコミットがバージョン 1.2.0 である」と記録するのに使います。

演習 1 では、ここまでの blob・tree・commit を Python で作り、本物の Git と同じハッシュ値になることを確かめます。

### 2.4 ref・HEAD・インデックス

オブジェクトは作られたら変わりません。では「ブランチに新しいコミットを積む」とは何をしているのでしょうか。

**ブランチは、コミットのハッシュを 1 つ書いただけのファイル** です。これを **ref（参照）** と呼びます。

```bash
$ cat .git/HEAD
ref: refs/heads/main
$ cat .git/refs/heads/main
2d414e0d74d43c08507a62407f69406a534f1c95
```

- `refs/heads/main` はブランチ main で、最新のコミットのハッシュを保持している。コミットすると、この 1 行が新しいハッシュに書き換わるだけ。
- `HEAD` は「今どのブランチにいるか」を指す **シンボリック ref**。特定のコミットを直接指している状態を detached HEAD と呼ぶ。
- タグは `refs/tags/` の下の ref。ref は `git gc` などのときに `.git/packed-refs` という 1 つのファイルにまとめて保存されることもある（新しい reftable 形式を使うリポジトリでは、保存の仕組み自体が違う）。
- ref が過去に指していた値は **reflog** に記録される（既定で一定期間保存される）。誤ったリセットやリベースでブランチが「消えた」ように見えても、`git reflog` で元のハッシュを見つけて戻せるのは、オブジェクトそのものは消えていないから。

3 つ目の重要な要素が **インデックス**（ステージングエリア）です。`.git/index` というバイナリファイルで、「次のコミットの tree をどういう内容にするか」を、パス・モード・blob のハッシュの一覧として保持します。

```bash
$ git ls-files -s
100644 587be6b4c3f93f93c489c0111bba5596147a26cb 0	a.txt
100644 975fbec8256d3e8a3797e7a3611380f27c49f4ac 0	a/b.txt
100644 ce013625030ba8dba906f756967f9e9ca394464a 0	hello.txt
100755 85ba14df52f8c72688537de6e7555fb402217b1e 0	run.sh
100644 b80e3222ab264bd7cafb376749bd18814fd66776 0	src/app.py
```

Git の日常的な操作は、**HEAD が指すコミットの tree・インデックス・作業ディレクトリ** の 3 つの間の移動として理解できます。

| コマンド | 3 つの木の間で起きること |
|---|---|
| `git add` | 作業ディレクトリの内容を blob にして、インデックスに登録する |
| `git commit` | インデックスから tree を作り、それを指す commit を作り、ブランチの ref を進める |
| `git status` | HEAD とインデックスの差（コミット予定の変更）と、インデックスと作業ディレクトリの差（未登録の変更）を表示する |
| `git switch` / `git checkout` | HEAD を別のブランチに向け、インデックスと作業ディレクトリをそのコミットの tree に合わせる |
| `git reset --soft` / `--mixed` / `--hard` | ブランチの ref を動かす。`--mixed` はインデックスも、`--hard` は作業ディレクトリも合わせる |

### 2.5 SHA-1 から SHA-256 へ

Git は当初から SHA-1 を使ってきました。2017 年、Google とオランダの研究機関 CWI は、SHA-1 の実用的な衝突（同じハッシュ値を持つ 2 つの異なる PDF）を公表しました（SHAttered）。ハッシュの衝突は、内容アドレス方式の前提（ハッシュが同じなら内容も同じ）を崩します。

Git はこれに対し、2017 年の 2.13 から、既知の衝突攻撃のパターンを検出する SHA-1 の実装（衝突検出付き SHA-1）を既定で使うようにしました。さらに長期的な対策として、2020 年の 2.29 から、オブジェクトの名前に SHA-256 を使うリポジトリを実験的な機能として作れるようになり、2023 年の 2.42 では「実験的」という強い警告が外されました（今後も互換性を壊す変更は予定していない、という位置づけ）。

```bash
$ git init --object-format=sha256 repo256 && cd repo256
$ echo "hello" | git hash-object --stdin
2cf8d83d9ee29543b34a87727421fdecb7e3f3a183d337639025de576db9ebb4
```

```python
import hashlib; d = b'hello\n'; print(hashlib.sha256(b'blob %d\x00' % len(d) + d).hexdigest())
```

```text
2cf8d83d9ee29543b34a87727421fdecb7e3f3a183d337639025de576db9ebb4
```

仕組みは同じで、ハッシュ関数だけが変わっています。2026年時点では、SHA-1 と SHA-256 のリポジトリの相互運用はまだ開発の途上で、ホスティングサービスや周辺ツールの対応も限定的です（GitLab は 2024 年に実験的に対応しましたが、GitHub は未対応と報じられています）。Git プロジェクトは公式の文書（BreakingChanges）で、次のメジャーバージョン Git 3.0 から新規リポジトリの既定を SHA-256 にする（既定のブランチ名を main に、ref の保存形式を reftable にする変更も同時に行う）方針を示していますが、2026 年 9 月時点で Git 3.0 は未公開で、公開日も決まっていません。既存のリポジトリが自動で変わるわけではないので、時期と移行方法は公式のリリースノートで確認してください。

## 3. 履歴は DAG — マージ・リベース・衝突

### 3.1 コミットの DAG とブランチ

コミットは親を指し、親は自分より前に作られているので、コミットの集まりは **有向非巡回グラフ（DAG）** になります（[2.5](../../02-math-and-algorithms/05-trees-heaps-graphs/README.md)）。ブランチは DAG の中の 1 点を指す、動くラベルにすぎません。

```bash
$ git log --graph --oneline --all
*   a42ee69 Merge branch 'feature/decimal'
|\
| * 36c8e99 fix: 金額を Decimal で合計する
* | ad78194 refactor: 初期値を float にする
|/
* 2d414e0 feat: 合計を計算する関数を追加
```

main と feature/decimal は 2d414e0 から分岐し、それぞれ 1 つずつコミットを積み、最後にマージコミット a42ee69（親が 2 つ）で合流しています。

### 3.2 3 方向マージとマージベース

2 つのブランチをマージするとき、Git は 2 つの先端だけを比べるのではなく、**分岐した時点のコミット（マージベース）** とも比べます。マージベースは、2 つのコミットの共通の祖先のうち、最も新しいもの（DAG の最小共通祖先）です。

```text
          base（マージベース）
          ┌───────┴───────┐
        ours            theirs
     base → ours の差分   base → theirs の差分
          └───────┬───────┘
               マージ結果
```

各箇所について、次のように判断します。

| base と比べて | 結果 |
|---|---|
| どちらも変えていない | そのまま |
| 片方だけが変えた | 変えた方を採用（相手が「変えていない」ことが base との比較で分かる） |
| 両方が同じように変えた | その変更を採用 |
| 両方が違うように変えた | **衝突（conflict）** |

2 方向の比較（ours と theirs だけ）では、「ours にあって theirs にない行」が、ours が追加したものか theirs が削除したものか区別できません。base があって初めて、どちらが何をしたかが分かるのです。

前の例で、両方のブランチが同じ行（`s = 0`）を違うように変えたので、マージは衝突しました。`merge.conflictStyle` を `diff3` にすると、衝突のマーカーに base の内容も表示されます（Git 2.35 以降では、さらに共通部分を省く `zdiff3` も選べます）。

```bash
$ git config merge.conflictStyle diff3
$ git merge feature/decimal
Auto-merging calc.py
CONFLICT (content): Merge conflict in calc.py
Automatic merge failed; fix conflicts and then commit the result.
$ cat calc.py
def total(items):
<<<<<<< HEAD
    s = 0.0
||||||| 2d414e0
    s = 0
=======
    s = Decimal(0)
>>>>>>> feature/decimal
    for x in items:
        s += x
    return s
```

base の行（`s = 0`）が見えると、「自分は float にし、相手は Decimal にした」という **両者の意図** が読み取れ、正しい解消（おそらく Decimal に統一し、float の変更の意図も確認する）を判断しやすくなります。衝突中、インデックスには同じパスの 3 つの版が「ステージ番号」付きで入っています。

```bash
$ git ls-files -s
100644 ac79db9a65464228e8ced868442cb12107cc4d10 1	calc.py
100644 ca8be8cc2e4e31ca651f99ca3e788451da59ec3f 2	calc.py
100644 c76a781845f2e0418486286a1b3df0155eb938c2 3	calc.py
```

ステージ 1 が base、2 が ours（HEAD）、3 が theirs です。

注意すべき性質が 2 つあります。

- **隣り合う行の変更も衝突になる**。片方が 2 行目、もう片方が 3 行目を変えただけでも、変更の区間が接しているため、Git は機械的に安全な統合ができないと判断します。
- **テキストとして衝突しないことは、正しいことを意味しない**。片方が関数の引数を増やし、もう片方がその関数の新しい呼び出しを別の場所に追加すると、テキストの衝突はないのに、マージ結果はコンパイルできません（意味的な衝突）。マージ後にも CI を実行する必要があるのはこのためです（[8.4](../04-ci-cd-and-release/README.md)）。

互いにマージし合った履歴（criss-cross merge）では、最良の共通祖先が 2 つ以上になることがあります。Git の既定のマージ戦略（ort）は、その場合まず複数のマージベースどうしをマージした仮想的なベースを作ってから 3 方向マージを行います。演習 1 ではマージベースの計算を、演習 2 では行単位の 3 方向マージそのものを実装します。

### 3.3 リベースと「共有した履歴を書き換えない」

**リベース（rebase）** は、自分のブランチのコミットを、別の起点の上に「作り直す」操作です。

```text
リベース前:                         git rebase main の後:
      C'─D'  ← feature（新しいコミット）
     /                                         A─B─E─F─C'─D'  ← feature
A─B─E─F  ← main                                       ↑ main
 \
  C─D   ← 元の feature（参照されなくなる）
```

リベースは、各コミットの差分を新しい起点に適用し直すので、**内容が同じでも親が変わるため、ハッシュの違う新しいコミット（C'、D'）が作られます**。元のコミット C、D は（reflog から一定期間たどれますが）ブランチからは参照されなくなります。

ここから、Pro Git などで繰り返し説かれる黄金律が導かれます。**自分のリポジトリの外に出た（他の人が基にしているかもしれない）コミットをリベースしてはいけない**。他の人が C、D の上に作業を積んでいると、あなたが C'、D' で置き換えて強制プッシュした瞬間、その人の履歴とあなたの履歴は食い違い、同じ変更が二重に現れたり、作業が失われたりします。

| | マージ | リベース |
|---|---|---|
| 履歴 | 分岐と合流がそのまま残る（事実の記録） | 一直線になる（読みやすい物語） |
| 既存のコミット | 変わらない | 作り直される（ハッシュが変わる） |
| 衝突の解消 | マージコミットで 1 回 | 作り直すコミットごとに発生しうる |
| 向いている場面 | 共有ブランチの統合 | 自分だけのブランチを、最新の main に追従させる・整理する |

多くのチームでは「自分の手元のブランチは自由にリベースして整える。main にはマージ（またはスカッシュマージ）で入れる。共有ブランチへの `push --force` は禁止（必要なら `--force-with-lease`）」という規則に落ち着きます。**スカッシュマージ**（ブランチの全コミットを 1 つにまとめて main に入れる）は履歴を簡潔にしますが、ブランチ内の細かいコミットの情報は失われます。どちらを選ぶかは、次節のコミットの粒度の考え方とあわせて決めます。

## 4. ブランチ戦略

### 4.1 3 つの代表的な戦略

| 戦略 | 概要 | 向いている状況 | 弱点 |
|---|---|---|---|
| **Git Flow**（Vincent Driessen, 2010） | main・develop・feature・release・hotfix の 5 種類のブランチ | 複数のバージョンを並行して保守する、リリースの頻度が低い製品（パッケージソフト、組み込み） | ブランチが長命になり、統合が遅れて衝突が大きくなる |
| **GitHub Flow**（Scott Chacon, 2011） | main は常にデプロイ可能。短いトピックブランチを PR でレビューしてマージし、すぐにデプロイ | 継続的にデプロイする Web サービス | 複数バージョンの保守には向かない |
| **トランクベース開発** | 全員が 1 つのトランク（main）に、少なくとも 1 日 1 回は統合する。ブランチを作るとしても数時間〜1 日で消す | 高頻度のデプロイ、大きなチーム | 未完成の機能を隠すフィーチャーフラグ（[8.4](../04-ci-cd-and-release/README.md)）と、強い自動テストが前提 |

Git Flow の提唱者 Driessen 自身も、2020 年に元の記事に「継続的にデリバリーされる Web アプリケーションには、GitHub Flow のようなもっと単純なワークフローを勧める」という趣旨の注記を追加しています。

### 4.2 研究が示すこと

Nicole Forsgren・Jez Humble・Gene Kim の『Accelerate』（2018）は、DORA（DevOps Research and Assessment）の数年にわたる調査をもとに、トランクベース開発の実践——同時に存在するブランチが 3 本未満、ブランチの寿命が 1 日未満、コードフリーズ期間がない——が、ソフトウェアのデリバリー性能の高さと結びついていると報告しています。

理由は、統合の間隔と衝突の大きさの関係にあります。2 つのブランチが離れている時間が長いほど、その間に積み重なる変更が増え、マージの衝突も「意味的な衝突」も大きくなります。長命なブランチは、**統合の痛みを後回しにして、しかも利子を付けて払う** ことになるのです。こまめに統合すれば、1 回の衝突は小さく、原因もすぐに分かります。

### 4.3 選び方

- 継続的にデプロイするサービスなら、短命なトピックブランチ ＋ PR レビュー ＋ main へのマージ（GitHub Flow）から始め、フィーチャーフラグと CI が整うにつれてトランクベース開発に近づける。
- 複数のバージョンを保守する製品（顧客ごとにバージョンが違う、オンプレミス版がある）なら、main での開発 ＋ バージョンごとのリリースブランチ（修正は main に入れてからリリースブランチへ cherry-pick）が現実的。
- どの戦略でも、**「長く生きるブランチは負債」** という原則は変わりません。環境ごとのブランチ（develop = 開発環境、staging = 検証環境…）は、同じコードを何度もマージする手間と差分の混乱を生むので避け、環境の違いは設定で表します（[8.4](../04-ci-cd-and-release/README.md)）。

## 5. コミットの粒度とメッセージ

### 5.1 コミットは「1 つの論理的な変更」

良いコミットは、**1 つの論理的な変更** を含み、そのコミットの時点でビルドとテストが通ります。

- **レビューしやすい**: リファクタリングと振る舞いの変更が別のコミットなら、それぞれの意図を確かめやすい（[8.1](../01-code-quality-and-design/README.md)）。
- **戻しやすい**: 問題のある変更だけを `git revert` できる。
- **原因を探しやすい**: `git bisect` は、良い版と悪い版の間を二分探索して、問題を持ち込んだコミットを特定するコマンドです。各コミットがビルド可能で小さければ、1,000 コミットの中からでも 10 回程度のテストで原因のコミットにたどり着けます（log₂ 1000 ≈ 10）。

### 5.2 コミットメッセージ

コミットメッセージは、未来の読者（障害調査中のあなた）への手紙です。**何を変えたかは差分を見れば分かりますが、なぜ変えたかは、メッセージにしか残りません**。

広く使われている形式は次の通りです。

```text
送料の無料条件を割引後の金額で判定する            ← 要約（50 文字程度まで。命令形・現在形で）
                                                  ← 空行
これまでは割引前の小計で判定していたため、クーポンで
5,000 円未満になった注文も送料無料になっていた。         ← 本文: なぜ変えたか、何が問題だったか
経理から、月 30 万円程度の送料の取りこぼしがあると
報告があった（#1234）。

判定を割引後の金額に変え、境界値のテストを追加した。
```

**Conventional Commits**（仕様 1.0.0）は、要約行に型を付ける規約です。

```text
feat(cart): 定期購入の申し込みを追加
fix(pricing): 送料の無料条件を割引後の金額で判定する
refactor!: 価格計算の公開 API を Money 型に変更

BREAKING CHANGE: calculate_total は int ではなく Money を返す
```

`feat`（機能追加）と `fix`（バグ修正）が仕様で定められた型で、`!` またはフッターの `BREAKING CHANGE:` が互換性を壊す変更を表します。`docs`・`refactor`・`test`・`ci` などの型も、慣例として広く使われています。型が機械的に読めるので、セマンティックバージョニング（fix → パッチ、feat → マイナー、破壊的変更 → メジャー。[8.4](../04-ci-cd-and-release/README.md)）の自動判定や、変更履歴（CHANGELOG）の自動生成に使えます。導入するなら、commitlint のような道具で CI で検査すると定着します。

### 5.3 署名付きコミット

コミットの author 欄は自由に書けるので、「このコミットを本当にその人が作ったか」は保証されません。GPG 鍵や（Git 2.34 以降の）SSH 鍵でコミットに署名すると、ホスティングサービスは検証済み（Verified）として表示できます。Sigstore の gitsign のように、長期の鍵を持たずに署名する方式もあります。ソフトウェアサプライチェーンの保護の一部として、[11.5](../../11-security/05-security-operations/README.md) で扱います。

## 6. リポジトリと秘密情報

API キー・パスワード・秘密鍵をコミットしてしまったら、どうすればよいでしょうか。

**正解は、まず直ちにその秘密情報を無効化（ローテーション）することです**。履歴から消すことではありません。

- 2.3 節で見たように、秘密情報を含むコミットのハッシュは、以降のすべてのコミットに影響します。履歴を書き換えて（`git filter-repo` や BFG Repo-Cleaner で）取り除くと、全員の履歴が変わり、強制プッシュが必要になります。
- しかも、書き換えても消えない場所が残ります。他の開発者の手元のクローン、フォーク、CI のキャッシュやログ、プルリクエストの参照、ホスティングサービスのキャッシュ。公開リポジトリなら、プッシュから数分で自動収集される前提で考えるべきです。
- したがって順序は、**(1) 無効化・再発行 → (2) 悪用の痕跡を監査ログで確認 → (3) 必要に応じて履歴から除去 → (4) 再発防止** です。

再発防止には、コミット前のフック（pre-commit で秘密情報のパターンを検出）、ホスティングサービスのシークレットスキャンとプッシュの拒否（GitHub の push protection など）、そして何より **秘密情報をコードや設定ファイルに書かず、シークレット管理の仕組みから実行時に注入する** 設計があります（[11.5](../../11-security/05-security-operations/README.md)）。CI からクラウドへの認証も、長期の鍵ではなく一時的な資格情報（OIDC 連携）にすれば、漏洩する鍵そのものがなくなります（[8.4](../04-ci-cd-and-release/README.md)）。

## 7. モノレポとポリレポ

組織の全コード（または多くのサービス）を 1 つのリポジトリに入れる **モノレポ（monorepo）** と、サービスやライブラリごとにリポジトリを分ける **ポリレポ（polyrepo）** があります。Google は巨大なモノレポを運用していることで知られ、2016 年の論文（Potvin・Levenberg, Communications of the ACM）では、約 20 億行のコードを含む単一のリポジトリで数万人の開発者が作業していると報告されています。

| | モノレポ | ポリレポ |
|---|---|---|
| 複数のコンポーネントにまたがる変更 | 1 つのコミット・1 つの PR で原子的にできる | 複数のリポジトリで順番にリリースが必要 |
| 依存関係 | 常に最新の内部ライブラリを使う（全員が同じ版） | 版の組み合わせを管理する必要がある |
| コードの発見と再利用 | 全体を検索できる | どこに何があるか分かりにくい |
| ビルドと CI | 影響範囲だけをビルド・テストする専用の道具が必要 | 小さく単純 |
| 権限と所有 | ディレクトリ単位の所有者の設定が必要 | リポジトリ単位で自然に分かれる |
| 規模の限界 | 大きくなると Git の性能・クローン時間が問題になる | 問題になりにくい |

モノレポを採用するなら、変更の影響を受けるものだけをビルド・テストし、結果をキャッシュする道具（Bazel、Nx、Turborepo、Pants など。2026年時点）が事実上必須です。ディレクトリごとの責任者は **CODEOWNERS** ファイル（GitHub・GitLab）で宣言でき、ブランチ保護と組み合わせると「そのディレクトリの変更には、所有チームの承認が必要」という規則を強制できます。

どちらが正しいかではなく、**組織の構造と変更のパターンに合わせる** のが原則です。コンポーネントをまたぐ変更が頻繁で、チーム間で共通の基盤を使うならモノレポの利点が大きく、独立したチームが独立したペースでリリースするならポリレポが自然です（チームの構造とシステムの構造の関係は [13.6](../../13-technical-leadership/06-team-and-org-design/README.md)）。

## 8. コードレビュー

### 8.1 レビューは何のためにあるか

コードレビューの目的と聞いて、多くの人は「バグを見つけること」を挙げます。しかし、Microsoft で行われた Bacchelli と Bird の調査（2013）では、開発者が最も期待していたのは欠陥の発見だった一方、実際のレビューで得られていたのは、コードの改善、**知識の共有**、チームの状況把握、別の解法の検討といった成果が中心で、欠陥の発見は期待されたほど多くないと報告されています。

レビューの価値を整理すると、次のようになります。

| 目的 | 内容 |
|---|---|
| 知識の共有 | 変更の内容を少なくとも 2 人が知っている状態を作る。担当者の休暇・退職に強くなる |
| 設計と保守性 | 読みやすさ・一貫性・設計の問題を、書いた直後の安いうちに直す |
| 欠陥の発見 | ロジックの誤り、境界値、セキュリティの問題 |
| 規範の伝達 | チームの設計方針や暗黙の知識を、具体的なコードを通じて伝える |

欠陥の発見は自動テストと静的解析が得意な領域です。人間のレビューは、**機械にできないこと**——意図と設計の妥当性、読む人にとっての分かりやすさ、知識の共有——に時間を使うべきです。

### 8.2 レビューの基準

Google は、社内のコードレビューの指針を "Google Engineering Practices Documentation"（https://google.github.io/eng-practices/）として公開しています。その中心にある考え方は、**レビュアーは、変更が完璧でなくても、コードベース全体の健全性を確実に改善しているなら承認すべきだ** というものです。完璧を求めてレビューを長引かせると、改善そのものが止まってしまいます。

この指針は、ほかにも実務的な助言を含んでいます（詳細は原文を参照してください）。

- 必須ではない指摘には `Nit:`（些細な点）を付け、作者が対応しなくてもよいことを明示する。
- レビュー依頼への応答は、遅くとも 1 営業日以内に。
- 変更（CL）は小さく保つ。100 行程度なら通常は適切で、1,000 行は通常大きすぎる、という目安が示されています。

### 8.3 PR の大きさと待ち時間

大きな PR は、レビューの質も速さも下げます。SmartBear 社が Cisco で行ったレビューの調査（2006 年の書籍 "Best Kept Secrets of Peer Code Review" で報告）では、一度にレビューするコードが 200〜400 行を超えると欠陥を見つける能力が落ちるとされています。1,000 行の PR は、深く読まれずに「LGTM（Looks Good To Me）」で通るか、何日も放置されるかのどちらかになりがちです。Google の事例研究（Sadowski ら, 2018）では、社内の変更の多くが小さく（変更行数の中央値は 24 行）、レビュー全体の所要時間の中央値は 4 時間未満と報告されています。

大きな変更を小さな PR に分ける方法:

- **準備のリファクタリングを先に出す**。「変更を容易にする」PR と「容易な変更をする」PR を分ける（[8.1](../01-code-quality-and-design/README.md)）。
- **層ごとに分ける**。DB のスキーマ変更 → データアクセス層 → API → 画面、のように、下の層から順に、単独でマージしても壊れない形で出す。
- **フィーチャーフラグで未完成の機能を隠す**。途中の状態を main に入れても利用者には見えないようにする（[8.4](../04-ci-cd-and-release/README.md)）。
- **積み重ねた PR（stacked PR）** を使い、前の PR の上に次の PR を作ってレビューを並行して進める。

待ち時間を減らすには、レビュー依頼への最初の応答までの時間をチームの指標として見る、レビューを 1 日の決まった時間帯にまとめず「作業の区切りごとに」行う習慣を作る、担当者を自動で割り当てる、などが有効です。

### 8.4 コメントの書き方

レビューコメントは、**コードについて** 書き、**書いた人について** 書きません。そして、指摘の重さを明示します。Conventional Comments という規約は、コメントの先頭にラベルを付けることを提案しています。

| ラベル | 意味 | 例 |
|---|---|---|
| `praise:` | 良い点 | `praise: テストの名前が仕様書のように読めて分かりやすいです` |
| `issue:` | 直す必要がある問題（ブロッキング） | `issue: 在庫が 0 のときに負の数を返します。境界値のテストを追加してください` |
| `suggestion:` | 改善の提案 | `suggestion: この 3 つの if は、割引率の辞書にすると追加が楽になりそうです` |
| `question:` | 理解のための質問 | `question: ここで UTC ではなく現地時刻を使っているのは意図的ですか？` |
| `nitpick:` / `nit:` | 些細な点（任意） | `nit: 変数名 d は discount の方が読みやすいです` |

`(blocking)` や `(non-blocking)` を添えて、マージを妨げる指摘かどうかをはっきりさせると、作者は優先順位をつけやすくなります。

書き方のコツ:

- **理由を書く**。「これはダメです」ではなく、「この書き方だと、ランクを追加するたびに 2 か所を直す必要があります」。
- **質問の形を使う**。レビュアーが文脈を知らないだけのことはよくあります。「なぜ〜ですか？」は、指摘よりも角が立たず、学びも生みます。
- **良い点も伝える**。レビューが指摘だけの場になると、PR を出すこと自体が苦痛になります。
- **スタイルの指摘はしない**。フォーマッタとリンタに任せる（[8.1](../01-code-quality-and-design/README.md)）。
- **長い議論は同期で**。コメントの往復が 3 回を超えたら、短い通話やペアで話した方が早く、誤解も少ない。結論はコメントに残す。

作者の側の作法もあります。PR の説明に「なぜ」「何を」「どう確かめたか」を書く、出す前に自分で差分を読み直す（セルフレビュー）、指摘を個人攻撃と受け取らず、合意できない点は理由を添えて議論する、などです。

### 8.5 心理的安全性

Amy Edmondson は 1999 年の研究で、チームの学習行動を支える要因として **心理的安全性**（対人関係のリスクをとっても安全だという、チームで共有された信念）を示しました。Google の社内研究プロジェクト（Project Aristotle, 2015 年に公表）も、効果的なチームを分ける要因の中で心理的安全性が最も重要だったと報告しています。

レビューは、心理的安全性が試される場です。辛辣なコメントが続くと、人は小さな PR を避けて大きな PR をまとめて出すようになり、分からないことを質問しなくなり、新しいメンバーは萎縮します。シニアエンジニアやリーダーのレビューは、チームの規範として真似されることを意識しましょう。

### 8.6 所有・ペアプログラミング・AI レビュー

- **CODEOWNERS とレビューの割り当て**: 変更されたパスに応じて、所有チームのレビューを必須にできます。ただし、所有チームがボトルネックにならないよう、所有者の人数と応答時間の目標を合わせて設計します。
- **ペアプログラミングとモブプログラミング**: 2 人（または全員）で同時に 1 つのコードを書くと、レビューは書きながら連続的に行われ、後からのレビュー待ちがなくなります。知識の共有の効果も大きく、難しい設計や新人のオンボーディングに向いています。すべての作業をペアでする必要はなく、場面で使い分けます。
- **AI を使ったレビュー**: 2026年時点では、AI によるレビューコメントの自動生成が広く使われています。見落としがちな境界値・エラー処理・セキュリティの問題を指摘させるのは有効ですが、設計の妥当性やチームの文脈に照らした判断はまだ人間の役割です。「AI が承認したからマージしてよい」ではなく、**人間のレビュアーがマージの責任を持つ** 規則を明確にしましょう。AI が生成したコードほど、作者本人が内容を説明できるかを確かめる必要があります（[8.2](../02-testing/README.md)）。

## よくある落とし穴

1. **共有ブランチをリベースして強制プッシュする**。他の人の履歴と食い違い、作業が失われます。リベースは自分だけのブランチに限り、共有ブランチでは `push --force` を禁止（ブランチ保護で強制）します。どうしても必要なら `--force-with-lease` を使い、事前に周知します。
2. **長命なブランチで大きな機能を作る**。数週間後のマージで巨大な衝突と意味的な衝突が起き、統合に何日もかかります。小さく分けて頻繁に統合し、未完成の機能はフィーチャーフラグで隠します。
3. **秘密情報をコミットしてしまい、履歴の書き換えだけで済ませる**。クローン・フォーク・キャッシュに残るので、まず無効化・再発行が必須です。その上で監査ログを確認し、再発防止策を入れます。
4. **衝突を機械的に解消する**。「自分の側を採用」を繰り返すと、相手の変更が黙って消えます。base の内容（diff3 形式）を見て両者の意図を理解し、解消後はテストを実行します。
5. **何でも入った巨大なコミットと「修正」「wip」だけのメッセージ**。revert も bisect もできず、半年後に「なぜ」が誰にも分かりません。1 つの論理的な変更ごとにコミットし、理由をメッセージに書きます。
6. **1,000 行の PR を出す**。深く読まれないまま承認されるか、何日も放置されます。準備のリファクタリング・層・フラグで分割し、数百行以内に保ちます。
7. **レビューで好みやスタイルを延々と議論する**。道具で決まることは道具に任せ、好みの指摘には `nit:` を付けて任意にします。
8. **レビューを門番（ゲートキーパー）の儀式にする**。承認者が 1 人しかいない、応答に数日かかる、指摘が人格攻撃になる——こうしたレビューは開発速度と心理的安全性の両方を損ないます。応答時間の目標、複数の承認者、コメントの作法を明文化しましょう。

## CTOの視点

1. **ブランチ戦略はデリバリー性能の設計である**。長命なブランチ、環境ごとのブランチ、コードフリーズは、統合の痛みを先送りにし、デプロイの頻度を下げます。DORA の研究が示すように、トランクベース開発に近づくほどデリバリー性能は上がる傾向があります。移行には、フィーチャーフラグ、速い CI、小さな PR の文化が前提になるので、CTO はこれらをセットで投資対象にします（[8.4](../04-ci-cd-and-release/README.md)）。
2. **レビューの待ち時間を指標として管理する**。PR の作成から最初のレビューまでの時間、マージまでの時間、PR の大きさの分布を見ます。「レビューが遅い」は個人の怠慢ではなく、担当の集中（特定のシニアにしか承認できない）、PR の大きさ、優先順位の不明確さといった仕組みの問題であることがほとんどです。
3. **秘密情報の漏洩は「起きる前提」で備える**。全員がいつかは誤ってコミットしうる、という前提で、シークレットスキャンとプッシュの拒否を全リポジトリで有効にし、漏洩時の手順（無効化 → 監査 → 除去 → 報告）を手順書にしておきます。長期の鍵を減らす（OIDC、短命な資格情報）ことが最も効果的です。障害対応と同じく、責任追及ではなく仕組みの改善で扱います（[10.5](../../10-cloud-and-sre/05-incident-management/README.md)）。
4. **レビューの文化はリーダーの振る舞いで決まる**。シニアエンジニアの辛辣なコメントは、チーム全体の規範として真似されます。レビューガイドライン（目的、応答時間、ラベル、スタイルの指摘をしない、承認の基準）を明文化し、リーダー自身がそれを最も忠実に守ることが、心理的安全性を作る一番の近道です。
5. **モノレポかポリレポかは「一方通行に近いドア」**。途中での移行には、ビルドシステム・CI・権限・履歴の移行という大工事が伴います。組織の構造（チームの境界と変更のパターン）と、ビルドの道具に投資できるかを見て判断し、採用するなら CODEOWNERS と影響範囲のビルドを最初から整えます。
6. **採用ではレビューの仕方を見る**。候補者に問題のあるコードをレビューしてもらうと、技術的な指摘の質だけでなく、指摘の優先順位のつけ方、言葉の選び方、相手の意図を確かめる姿勢が分かります。一緒に働く人の能力を最もよく表す場面の一つです。

### 演習 3（記述）: レビューコメントと PR の分割

**(a)** 次のレビューコメントを、この章の作法に沿って書き直してください。

1. 「なんでこんな書き方してるの？普通 dict 使うでしょ」
2. 「テストがない。やり直し」
3. 「この変数名ダサい」
4. 「前にも言ったけど、例外を握りつぶさないで」

**(b)** 同僚が「決済手段にコンビニ払いを追加する」PR を出しました。差分は 2,300 行で、決済手段のクラス階層のリファクタリング、DB のスキーマ変更（支払い期限のカラム追加）、コンビニ払いの API 連携、管理画面の変更、既存のクレジットカード決済のバグ修正が 1 つに入っています。どう分割すべきか、順序と理由を提案してください。

<details>
<summary>解答例</summary>

**(a)** 書き直しの例:

1. `question: 割引率を if の連鎖で判定していますが、ランクと割引率の辞書にしない理由はありますか？ 辞書にすると、ランクを追加するときに 1 行で済みそうです。`（相手の意図を尋ね、提案の理由を添える）
2. `issue (blocking): 支払い期限を過ぎた注文を自動キャンセルする処理にテストがありません。期限ちょうど・期限の 1 秒後の境界値のテストを追加してもらえますか？ 時計は clock 引数で差し替えられます。`（何のテストが、なぜ必要かを具体的に）
3. `nit (non-blocking): tmp2 だと何が入っているか分かりにくいので、pending_orders のような名前はどうでしょう。`（任意であることを明示し、代案を出す）
4. `issue: except Exception: pass だと、メール送信の失敗に誰も気づけません。失敗はログとメトリクスに残して、ここで握りつぶさずに上に伝えませんか。チームのガイドラインのエラー処理の節にも同じ方針があります。`（「前にも言った」は責める言葉なので使わず、繰り返し起きるなら個別に話すか、ガイドラインやリンタの規則にする）

**(b)** 分割の例（上から順にマージ）:

1. **クレジットカード決済のバグ修正**: 独立した修正なので最初に単独で出す。本番に早く届き、万一のときに単独で revert できる。
2. **決済手段のクラス階層のリファクタリング**: 振る舞いを変えない変更として、既存のテストが通ることだけを確かめる。「変更を容易にする」PR。
3. **DB スキーマの変更**: 支払い期限のカラムを NULL 許容で追加する（拡張のみ。既存のコードは影響を受けない）。スキーマ変更は単独でデプロイして確認する（[8.4](../04-ci-cd-and-release/README.md) の expand/contract）。
4. **コンビニ払いの API 連携**: フィーチャーフラグで無効にした状態でマージする。
5. **管理画面の変更**: 同じフラグの背後で。最後にフラグを段階的に有効化する。

採点の観点: (a) は、人ではなくコードについて書いているか、理由があるか、ブロッキングかどうかが明確か、の 3 点。(b) は、バグ修正の分離、リファクタリングと振る舞いの変更の分離、スキーマ変更を先に後方互換な形で出すこと、未完成の機能をフラグで隠すこと、が入っていれば十分です。

</details>

## 理解度チェック

**Q1. 内容が "hello\n" のファイルの blob のハッシュは、どういうバイト列の SHA-1 ですか。また、ファイル名を変えるとハッシュは変わりますか。**

<details>
<summary>解答</summary>

`b"blob 6\x00hello\n"`（型・空白・内容のバイト数・NUL 文字・内容）の SHA-1 で、`ce013625030ba8dba906f756967f9e9ca394464a` です。blob には内容しか含まれないので、ファイル名を変えても blob のハッシュは変わりません。変わるのは、名前を持っている tree のハッシュ（と、それを含む上位の tree と commit のハッシュ）です。

</details>

**Q2. 過去のコミットのファイルを 1 つだけ書き換えると、なぜそれ以降のすべてのコミットのハッシュが変わるのですか。**

<details>
<summary>解答</summary>

ファイルの内容が変わると blob のハッシュが変わり、その blob を含む tree のハッシュが変わり、根の tree までの tree のハッシュが連鎖して変わります。コミットは根の tree のハッシュを含むので、そのコミットのハッシュも変わります。さらに、子のコミットは親のコミットのハッシュを含むので、子・孫と以降のすべてのコミットのハッシュが変わります。このため、履歴のどこかが改ざんされたら、最新のコミットのハッシュを比べるだけで検出できます。

</details>

**Q3. ブランチとは Git の内部で何ですか。「ブランチを削除するとコミットが消える」は正しいですか。**

<details>
<summary>解答</summary>

ブランチは、コミットのハッシュを 1 つ保持する ref（`.git/refs/heads/<名前>`、または packed-refs の 1 行）にすぎません。ブランチを削除しても消えるのはその ref だけで、コミットのオブジェクト自体はすぐには消えません。reflog やほかのブランチから参照されていれば残り、どこからも参照されなくなったオブジェクトも、ガベージコレクション（`git gc`）で一定期間の後に削除されるまでは `git reflog` などから復旧できます。

</details>

**Q4. 3 方向マージでは、なぜマージベースが必要なのですか。2 つのブランチの先端だけを比べる方法の問題を説明してください。**

<details>
<summary>解答</summary>

2 つの先端だけを比べると、「ours にあって theirs にない行」が、ours が追加したのか theirs が削除したのかを区別できません。マージベース（分岐した時点の版）と比べれば、どちらが何を変えたかが分かるので、「片方だけが変えた箇所はその変更を採用し、両方が違うように変えた箇所だけを衝突にする」という判断ができます。

</details>

**Q5. 次の 2 つのうち、マージで衝突するのはどちらですか。また、衝突しない方にも危険が残る理由を説明してください。(A) ours が 10 行目、theirs が 11 行目を変更した。(B) ours が 10 行目、theirs が 50 行目を変更した。**

<details>
<summary>解答</summary>

(A) が衝突します。隣り合う行の変更は、変更の区間が接しているため、Git は安全に統合できないと判断します。(B) はテキストとしては衝突せずにマージされます。しかし、例えば ours が 10 行目で関数の引数を変え、theirs が 50 行目でその関数を古い引数で呼ぶ処理を追加していれば、マージ結果は動きません（意味的な衝突）。テキストの衝突がないことは正しさを保証しないので、マージ後のコードに対して CI のテストを実行する必要があります。

</details>

**Q6. リベースの黄金律とは何ですか。それを破ると何が起きるかを、コミットのハッシュの観点から説明してください。**

<details>
<summary>解答</summary>

「自分のリポジトリの外に出た（他の人が基にしている可能性のある）コミットをリベースしてはいけない」です。リベースは各コミットを新しい親の上に作り直すので、内容が同じでもハッシュの違う新しいコミットになります。他の人が元のコミットの上に作業を積んでいると、あなたが作り直した履歴を強制プッシュした後、その人の履歴と食い違い、同じ変更が別のハッシュで二重に現れたり、マージのたびに衝突したり、作業が失われたりします。

</details>

**Q7. 公開リポジトリにクラウドのアクセスキーをコミットしてしまいました。取るべき行動を、順序とその理由とともに答えてください。**

<details>
<summary>解答</summary>

(1) 直ちにそのキーを無効化し、新しいキーを発行する。公開された時点で、自動収集ツールに取得されている前提で動くべきで、履歴の書き換えより先に被害の拡大を止める必要があります。(2) クラウドの監査ログで、そのキーが悪用されていないかを確認し、悪用があれば障害として対応する。(3) 必要に応じて `git filter-repo` などで履歴から除去する（ただし、クローン・フォーク・キャッシュには残るので、これだけでは対策にならない）。(4) プッシュ時のシークレットスキャン、pre-commit フック、実行時にシークレットを注入する設計、長期の鍵をなくす（OIDC など）といった再発防止策を入れる。

</details>

**Q8. レビューの目的として「欠陥の発見」以外に何がありますか。また、1,000 行の PR が問題なのはなぜですか。**

<details>
<summary>解答</summary>

知識の共有（変更の内容を複数人が知っている状態を作る）、設計と保守性の改善、チームの規範や暗黙知の伝達、別の解法の検討などです。研究でも、実際のレビューの成果はこれらが中心で、欠陥の発見は期待ほど多くないと報告されています。1,000 行の PR は、レビュアーの集中力の限界を超えるため、深く読まれずに承認されるか、長く放置されるかのどちらかになりがちです。一度にレビューする量が数百行を超えると欠陥の発見能力が落ちるという調査もあります。準備のリファクタリング・層ごと・フィーチャーフラグを使って分割するべきです。

</details>

## まとめ

- Git は、内容のハッシュを番地にするオブジェクトの保管庫。blob（内容）・tree（ディレクトリ）・commit（スナップショットと親）・tag の 4 種類で、ハッシュは `"<型> <バイト数>\0" + 内容` の SHA-1（将来は SHA-256）。
- tree と commit はマークル木を作るので、コミットのハッシュ 1 つで全ファイルと全履歴が確定し、改ざんを検出できる（ハッシュ関数が衝突に強い限り。SHA-1 の弱さへの対策が SHA-256 への移行）。
- ブランチや HEAD は、コミットを指すポインタ（ref）にすぎない。コミット・インデックス・作業ディレクトリの 3 つの木の関係で、日常の操作を理解できる。
- マージはマージベースとの 3 方向の比較で、両者が同じ区間を違うように変えたときだけ衝突する。テキストの衝突がなくても意味的な衝突は起きるので、マージ後にもテストを実行する。
- リベースはコミットを作り直す。共有した履歴は書き換えない。長命なブランチは統合の痛みを利子付きで先送りするので、短いブランチとこまめな統合（トランクベース開発に近づける）を目指す。
- コミットは 1 つの論理的な変更にし、「なぜ」をメッセージに書く。秘密情報をコミットしたら、履歴の書き換えより先に無効化する。
- コードレビューの主な価値は知識の共有と設計の改善。小さな PR、速い応答、理由とラベルのあるコメント、心理的安全性が、レビューの速さと質を両立させる。
