## なぜ学ぶのか

2012 年 8 月 1 日、米国の証券会社 Knight Capital は、取引システムの不具合により約 45 分間で大量の意図しない注文を出し、巨額の損失を出しました。米国証券取引委員会（SEC）が 2013 年に公表した命令書によれば、経緯は次の通りです。

- 新機能のコードを 8 台のサーバーに手作業でデプロイした際、技術者が **1 台にだけ新しいコードをコピーし忘れた**。デプロイを別の技術者が確認する手順はなかった。
- 新機能は、以前は何年も前に使われなくなった古い機能（Power Peg）を起動するために使っていた **フラグを再利用** していた。古い機能のコードは削除されずに残っていた。
- 取引開始後、そのフラグが有効になった注文が届くと、更新されていなかった 1 台のサーバーでは古いコードが動き出し、45 分間に 154 銘柄で 400 万回以上の約定が発生した。
- SEC の命令書は、この取引による損失を 4 億 6,000 万ドル超としています（Knight 社は事故の翌日、税引前損失を約 4 億 4,000 万ドルと発表）。同社は独立した会社として存続できず、翌年に他社と統合されました。

この事故には、この章で扱うテーマがすべて含まれています。**手作業で一貫性のないデプロイ**、**フラグの再利用と消されない古いコード**（フラグの負債）、**異常を検知して自動で止める仕組みの欠如**、そして **ロールバックの手順が問題を悪化させた** とも報告されています。リリースの仕組みは、事業の存続に直結するのです。

一方で、DORA（DevOps Research and Assessment）の長年の調査と、その成果をまとめた『Accelerate』（2018）は、デプロイの頻度が高くリードタイムが短い組織ほど、変更の失敗率が低く、障害からの復旧も速い傾向があると報告しています。**速さと安定性はトレードオフではない**——小さな変更を、自動化された安全な仕組みで頻繁に届けることが、両方を同時に高めるのです。

## 1. 継続的インテグレーション（CI）

**継続的インテグレーション（Continuous Integration, CI）** は、開発者が自分の変更を **少なくとも 1 日に 1 回は** 共有のメインライン（main）に統合し、統合のたびに自動でビルドとテストを行う実践です。Martin Fowler の同名の記事（2000 年に初版、その後改訂）が広めました。主な原則は次の通りです。

| 原則 | 意味 |
|---|---|
| 頻繁にメインラインに統合する | 長命なブランチを作らない（[8.3](../03-version-control-and-review/README.md)） |
| 自己テストするビルド | ビルドの中で自動テストが実行され、失敗したらビルド全体が失敗する |
| ビルドを速く保つ | XP の「10 分ビルド」。遅いテストは後段に回す（[8.2](../02-testing/README.md)） |
| 壊れたビルドはすぐに直す | main が赤いときは、それを直すことが最優先。直せないならすぐに戻す（revert） |
| 誰でも状態が見える | ビルドの結果と、何がどこにデプロイされているかが見える |

よくある誤解は「Jenkins や GitHub Actions を使っている = CI をしている」というものです。CI は **道具ではなく実践** です。数週間生きるフィーチャーブランチの上で自動テストを回していても、統合（main への合流）が数週間に 1 回なら、それは CI ではありません。

## 2. 継続的デリバリーとデプロイメントパイプライン

### 2.1 デリバリーとデプロイ

| 用語 | 意味 |
|---|---|
| **継続的デリバリー（Continuous Delivery）** | main のすべての変更が、**いつでも本番にリリースできる状態** に保たれている。本番へのデプロイは、ボタンを押す（人が判断する）だけ |
| **継続的デプロイ（Continuous Deployment）** | パイプラインを通過したすべての変更が、**人の判断なしに自動で** 本番にデプロイされる |

Jez Humble と David Farley は『Continuous Delivery』（2010）で、継続的デリバリーの中心に **デプロイメントパイプライン**——コミットから本番までの全工程を自動化し、各段階で品質のゲートを設けたもの——を置きました。

```mermaid
flowchart LR
  C["コミット"] --> B["ビルド<br>成果物を 1 回だけ作る"]
  B --> T["自動テスト<br>単体・統合・契約"]
  T --> R[("成果物のリポジトリ<br>版とダイジェストで管理")]
  R --> S["ステージング<br>同じ成果物をデプロイ"]
  S --> P["本番<br>カナリアから全体へ"]
```

### 2.2 ビルドは 1 回、同じ成果物を昇格させる

パイプラインの重要な原則は、**成果物（コンテナイメージ・パッケージ）を 1 回だけビルドし、同じものをステージング、本番へと昇格（promote）させる** ことです。環境ごとにビルドし直すと、依存関係の解決やビルド環境の違いで、「ステージングで試したもの」と「本番に出したもの」が別物になります。

- 成果物は、変更できないタグ（コミットの SHA など）と、内容のハッシュ（コンテナイメージのダイジェスト）で識別する。`latest` のような動くタグでデプロイしない。
- 環境ごとの違いは、成果物の中ではなく **設定**（環境変数・設定サービス）で与える（The Twelve-Factor App の「設定を環境に格納する」）。
- パスワードなどの秘密情報も成果物に焼き込まない（[8.3](../03-version-control-and-review/README.md) の 6 節）。

### 2.3 再現可能なビルドとキャッシュ

**再現可能なビルド（reproducible build）** とは、同じソースコード・同じビルド環境・同じ手順から、誰がビルドしてもビット単位で同一の成果物ができることです。再現可能であれば、「この成果物は確かにこのソースからビルドされた」と第三者が検証でき、サプライチェーン攻撃（ビルドの途中での改ざん）を検出できます（SLSA などの枠組みは [11.5](../../11-security/05-security-operations/README.md)）。

再現性を壊す主な原因は、ビルド時刻の埋め込み、ファイルの並び順、ロックされていない依存関係、ネットワークからのその場のダウンロードです。逆に、入力が同じなら出力が同じ、という性質があれば、**ビルドやテストの結果をキャッシュ** できます。Bazel などのビルドツールは、入力のハッシュをキーに結果を共有キャッシュに保存し、変わっていない部分の再ビルドを省くことで、大きなリポジトリでも CI を速く保ちます。

## 3. 依存関係の管理

### 3.1 ロックファイル

`requirements.txt` に `requests>=2.0` と書くと、インストールするたびに、その時点の最新版が入ります。今日と来週で別の版が入り、ある日突然ビルドが壊れる——これを防ぐのが **ロックファイル** です。`package-lock.json`（npm）、`poetry.lock`・`uv.lock`（Python）、`Cargo.lock`（Rust）、`go.sum`（Go）などは、間接的な依存（依存の依存）まで含めた **正確な版とハッシュ** を記録します。

- アプリケーションでは、ロックファイルを **必ずリポジトリにコミット** し、CI と本番はロックファイルどおりにインストールする。
- ライブラリでは、利用者の環境と組み合わせられるよう、依存を範囲で指定する（ロックファイルは開発とテストの再現性のために使う）。

### 3.2 セマンティックバージョニングと範囲指定

**セマンティックバージョニング（SemVer）2.0.0** は、版番号 `MAJOR.MINOR.PATCH` に意味を持たせる規約です。

| 上げる部分 | 意味 |
|---|---|
| MAJOR | 後方互換性のない変更（既存の利用者のコードが壊れうる） |
| MINOR | 後方互換性のある機能追加 |
| PATCH | 後方互換性のあるバグ修正 |

`1.0.0-beta.2` のようなプレリリース版や、`+build.5` のようなビルドメタデータも定められています。ただし、SemVer は **作者の約束** にすぎず、実際に互換性が保たれている保証はありません。

npm などの範囲指定の意味を、演習 4 の実装で確かめてみます。

```python
from semver import max_satisfying, satisfies

versions = ["1.4.2", "1.5.0", "1.5.1", "1.6.0-beta.1", "2.0.0"]
for r in ["^1.4.2", "~1.4.2", ">=1.5.0 <2.0.0", "^0.4.2"]:
    print(f"{r:16s} → {max_satisfying(versions, r)}")
print(satisfies("0.5.0", "^0.4.2"), satisfies("1.6.0-beta.1", "^1.4.2"), satisfies("1.6.0-beta.1", ">=1.6.0-beta.0"))
```

```text
^1.4.2           → 1.5.1
~1.4.2           → 1.4.2
>=1.5.0 <2.0.0   → 1.5.1
^0.4.2           → None
False False True
```

- `^1.4.2` は「MAJOR を固定」（`>=1.4.2 <2.0.0-0`）、`~1.4.2` は「MINOR まで固定」（`>=1.4.2 <1.5.0-0`）。
- **0.x 系では `^` の意味が変わる**。`^0.4.2` は `>=0.4.2 <0.5.0-0` で、0.5.0 は含まれません。0.x の段階では MINOR の変更が破壊的でありうる、という SemVer の考え方を反映しています。
- **プレリリース版は、明示的に指定しない限り範囲に入らない**。`^1.4.2` の利用者に、1.6.0-beta.1 が勝手にインストールされることはありません。

### 3.3 依存関係の更新を運用する

依存関係は、放っておくと古くなり、セキュリティの修正を取り込めなくなります（[8.5](../05-refactoring-and-tech-debt/README.md) のセキュリティ負債）。2021 年 12 月に公表された Java のログライブラリ Log4j の脆弱性（Log4Shell, CVE-2021-44228）では、多くの組織が「自社のどのシステムが Log4j を使っているか」をすぐに答えられず、対応に時間がかかりました。

- **Renovate や Dependabot** のような道具で、更新の PR を自動で作らせる。小さな更新をこまめに取り込む方が、年に 1 回の大移行より安全。
- 更新の PR も通常の CI で検証し、PATCH・MINOR の更新は（テストが通れば）自動でマージするなど、方針を決める。
- どのシステムが何に依存しているかの一覧（SBOM, ソフトウェア部品表）を作れるようにしておく（[11.5](../../11-security/05-security-operations/README.md)）。
- 外部のパッケージは消えたり差し替えられたりしうる。2016 年 3 月には、npm で作者が自分のパッケージを一斉に公開停止し、その中のわずか 11 行の `left-pad` に依存していた多くのプロジェクトのビルドが失敗しました（npm は後に公開停止の規則を変更しています）。重要なシステムでは、社内のパッケージのミラーやキャッシュを検討します。

## 4. デプロイ戦略

### 4.1 主な戦略

| 戦略 | 仕組み | 利点 | 欠点・コスト |
|---|---|---|---|
| 再作成（recreate） | 旧版をすべて止めてから新版を起動 | 単純。新旧が混在しない | 停止時間が生じる |
| ローリング | サーバーを少しずつ新版に入れ替える | 追加の資源がほぼ不要 | 新旧が混在する時間がある。戻すのにも同じ時間がかかる |
| ブルーグリーン | 新版の環境（グリーン）を丸ごと用意し、トラフィックを一度に切り替える | 切り替えも戻しも一瞬 | 環境が 2 倍必要。DB など共有する状態は切り替えられない |
| カナリア | 新版を一部（例: 1%→5%→25%→100%）のトラフィックにだけ出し、指標を比べながら広げる | 問題の影響範囲を小さくできる | 指標の比較の仕組みが必要。新旧が長く混在する |
| シャドー（ミラーリング） | 本番のリクエストを複製して新版にも流すが、利用者には旧版の応答を返す | 利用者への影響なしに本番の負荷と入力で試せる | 書き込み（副作用）のある処理には使いにくい。資源が 2 倍 |

どの戦略でも、**新旧の版が同時に動く時間がある**（再作成を除く）ことを前提に設計する必要があります。新しい版が書いたデータを古い版が読めるか、API の形が変わっても古いクライアントが動くか。この「混在の期間の互換性」が、6 節のスキーマ変更の設計につながります。

**プログレッシブデリバリー（progressive delivery）** は、カナリアやフィーチャーフラグを組み合わせて、利用者への公開範囲を段階的に広げ、各段階で自動的に指標を確かめる考え方の総称です（2018 年ごろに RedMonk の James Governor が提唱したとされます）。

### 4.2 カナリアの判定を自動化する

カナリアの判定を人がグラフを見て行うと、見落としや判断のばらつきが生じ、深夜のリリースでは特に危険です。Netflix と Google は、この判定を自動化するツール Kayenta を 2018 年にオープンソースとして公開しています。自動判定の基本は、**同じ時間帯の旧版（ベースライン）と新版（カナリア）を、統計的に比べる** ことです。

演習 2 で作る判定器の例です。エラー率を 2 つの比率の差の検定で、レイテンシを p95 の比で比べます。

```python
from canary import GroupMetrics, analyze

baseline = GroupMetrics(requests=12_000, errors=18, latencies_ms=[80 + (i % 50) for i in range(2000)])
canary = GroupMetrics(requests=12_000, errors=41, latencies_ms=[82 + (i % 50) for i in range(2000)])
verdict = analyze(baseline, canary)
print(verdict.decision)
print(verdict.reasons)
print(f"p 値 = {verdict.p_value:.4f}, p95: {verdict.baseline_p95} ms → {verdict.canary_p95} ms")
```

```text
ROLLBACK
('エラー率が悪化: 0.150% → 0.342%（p = 0.0014 < 0.01）',)
p 値 = 0.0014, p95: 127 ms → 129 ms
```

設計上の注意点がいくつかあります。

- **ベースラインは同じ時間帯の旧版** と比べる。昨日の同じ時刻と比べると、曜日やキャンペーンの影響と区別できない。ベースラインもカナリアと同じ台数で新しく起動すると、起動直後のキャッシュの冷え方などの条件もそろう。
- **最小の標本数を決める**。リクエストが少ないうちは、偶然の揺らぎで判定が振れる。
- **統計的に有意かどうかと、実務上意味のある差かどうかは別**。何百万件もの標本があると、0.01 ポイントの差でも「有意」になる。効果量の下限（例: エラー率 0.1 ポイント）を組み合わせる。
- **何度も覗くと偽陽性が増える**。一定間隔で何度も検定を繰り返すと、そのうちどれかが偶然「有意」になる確率が上がる（[2.2](../../02-math-and-algorithms/02-probability-statistics/README.md) の多重検定の問題）。実用のツールは、有意水準を厳しくする、判定の回数を決めておく、分布全体を比べる検定（Kayenta はマン・ホイットニーの U 検定を使う）を使う、などの工夫をしています。

## 5. フィーチャーフラグ

### 5.1 デプロイとリリースを切り離す

**フィーチャーフラグ（feature flag / feature toggle）** は、コードの中の分岐を、デプロイし直さずに実行時の設定で切り替える仕組みです。これにより、**デプロイ**（コードを本番に置く）と **リリース**（利用者に機能を見せる）を別の時点で行えます。未完成の機能を main に統合したまま隠せるので、トランクベース開発（[8.3](../03-version-control-and-review/README.md)）の前提にもなります。

Pete Hodgson は Martin Fowler のサイトの記事 "Feature Toggles (aka Feature Flags)"（2017）で、フラグを目的と寿命で 4 種類に分けています。

| 種類 | 目的 | 寿命 | 例 |
|---|---|---|---|
| リリースフラグ | 未完成・未公開の機能を隠す | 短い（数日〜数週間） | 新しい決済画面 |
| 実験フラグ | A/B テストで利用者を振り分ける | 実験の期間 | ボタンの文言の比較 |
| 運用フラグ | 障害時に機能を止める（キルスイッチ）、負荷を落とす | 長いこともある | 重いレコメンド機能を止める |
| 権限フラグ | 特定の利用者（有料プラン・社内・ベータ参加者）にだけ機能を開く | 長い | 企業向け機能 |

### 5.2 評価の仕組み — 安定したハッシュによる割合の出し分け

「10% の利用者にだけ機能を出す」とき、リクエストごとに乱数で決めると、同じ利用者の体験がページごとに揺れてしまいます。そこで、**フラグのキーと利用者 ID から計算したハッシュで、利用者を 0〜9999 の「バケット」に割り当て**、バケットの番号で出し分けます（演習 1）。

```python
from flags import bucket, evaluate

print(bucket("new-checkout", "user-42"), bucket("new-checkout", "user-42"), bucket("dark-mode", "user-42"))

def rollout(percent):
    return {"new-checkout": {
        "enabled": True,
        "variants": {"on": True, "off": False},
        "off_variant": "off",
        "default": {"rollout": [["on", percent], ["off", 100 - percent]]},
    }}

users = [{"user_id": f"user-{i}"} for i in range(10_000)]
previous = set()
for percent in (1, 5, 25, 100):
    on = {u["user_id"] for u in users if evaluate(rollout(percent), "new-checkout", u).value}
    print(f"{percent:3d}% → {len(on):5d} 人が有効。前の段階の利用者は全員含まれるか: {previous <= on}")
    previous = on
```

```text
1762 1762 7851
  1% →    79 人が有効。前の段階の利用者は全員含まれるか: True
  5% →   481 人が有効。前の段階の利用者は全員含まれるか: True
 25% →  2524 人が有効。前の段階の利用者は全員含まれるか: True
100% → 10000 人が有効。前の段階の利用者は全員含まれるか: True
```

この方式には 3 つの良い性質があります。

1. **安定**: 同じ利用者は、いつ・どのサーバーで評価しても同じ結果になる（状態を保存する必要がない）。
2. **段階的に広げても、すでに有効だった利用者は有効のまま**。1% → 5% → 25% と広げるとき、先に機能を見た利用者から機能が消えることがない。
3. **フラグごとに独立**: フラグのキーをハッシュに混ぜるので、「どの実験でも同じ 10% の利用者が対象になる」という偏りが生じない（`user-42` は new-checkout ではバケット 1762、dark-mode では 7851）。

B2B のサービスでは、利用者 ID ではなく **組織 ID で割り当てる** ことも重要です。同じ会社の中で、ある人には新しい画面が、隣の人には古い画面が見えると、サポートが混乱します。

### 5.3 フラグの負債

フラグは便利な反面、**放っておくと技術的負債になります**。フラグが 1 つ増えるたびに、コードの分岐が増え、テストすべき組み合わせが増え、「このフラグは今どちらになっているのか」を誰も把握していない状態が生まれます。Knight Capital の事故は、古いフラグの意味を再利用し、古いコードを消していなかったことが直接の原因の一つでした。

- フラグには **所有者と期限** を付ける。リリースフラグは、全員に公開したら速やかにフラグとコードの分岐を削除する（削除までを 1 つの作業として見積もる）。
- **フラグの名前（キー）を再利用しない**。役目を終えたフラグは削除し、新しい用途には新しいキーを作る。
- フラグの評価は **決して例外で落ちない** ように作る（演習 1 の大原則）。フラグの設定の誤りが全体の障害にならないよう、安全な既定値を返す。
- フラグの変更も本番の変更である。誰が・いつ・何を変えたかを記録し、影響の大きいフラグの変更はレビューする。
- フラグ管理のための製品や、ベンダーに依存しない API の標準（CNCF の OpenFeature など）もあります（2026年時点）。

## 6. データベースのマイグレーション

### 6.1 版管理されたマイグレーション

アプリケーションのコードと違い、データベースには **データという「状態」** があり、デプロイし直すだけでは元に戻せません。スキーマの変更は、番号付きのマイグレーションのファイルとしてリポジトリで管理し、「どこまで適用したか」を DB 自身のテーブルに記録するのが標準的なやり方です（Flyway、Liquibase、Alembic、Rails のマイグレーションなど）。演習 3 で作る実行器の動きを見てみます。

```python
import sqlite3
from datetime import datetime, timezone
from pathlib import Path
from migrate import migrate, status

conn = sqlite3.connect(":memory:")
clock = lambda: datetime(2026, 9, 28, 3, 0, tzinfo=timezone.utc)
print(migrate(conn, Path("mig"), clock=clock))     # 1 回目: 2 つ適用
print(migrate(conn, Path("mig"), clock=clock))     # 2 回目: 何もしない（冪等）
for row in conn.execute("SELECT version, name, substr(checksum, 1, 12), applied_at FROM schema_migrations"):
    print(row)

# 適用済みのファイルを書き換えると……
Path("mig/0001_create_users.sql").write_text("CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT NOT NULL);\n")
print(status(conn, Path("mig")))
try:
    migrate(conn, Path("mig"), clock=clock)
except Exception as e:
    print(type(e).__name__, e)
```

```text
[1, 2]
[]
(1, 'create_users', 'd09c49c4b061', '2026-09-28T03:00:00+00:00')
(2, 'add_email', '7a3a4c70d5af', '2026-09-28T03:00:00+00:00')
[(1, 'create_users', 'modified'), (2, 'add_email', 'applied')]
ChecksumMismatchError 適用済みのマイグレーション 1_create_users が変更されています。直したい場合は、新しいマイグレーションを追加してください
```

- **何度実行しても安全（冪等）** なので、デプロイのたびに無条件に実行できる。
- **適用済みのマイグレーションは書き換えない**。書き換えても、すでに適用した環境には反映されず、環境ごとにスキーマがずれる。チェックサムでこれを検出する。
- **1 つのマイグレーションを 1 つのトランザクションで適用する**。途中で失敗しても、中途半端なスキーマが残らない。ただし、DDL をトランザクションの中でロールバックできるかは DB によって違う。SQLite や PostgreSQL はできるが、MySQL では多くの DDL が暗黙にコミットされる。PostgreSQL の `CREATE INDEX CONCURRENTLY` のように、トランザクションの中では実行できない操作もある。

### 6.2 拡張・縮小 — 無停止のスキーマ変更

列の名前を変える、型を変える、テーブルを分ける、といった変更を 1 回のデプロイで行うと、デプロイの途中で新旧のアプリケーションが混在する間に、どちらかが壊れます。古いアプリは新しい列名を知らず、新しいアプリは古い列名を知らないからです。

これを解くのが **拡張・縮小（expand–contract）**、または **並行変更（parallel change）** と呼ばれる手順です（Danilo Sato が Martin Fowler のサイトの記事 "ParallelChange" で整理しています）。`users.name` を `users.full_name` に改名する例で、3 回のリリースに分けます（演習 3）。

| リリース | マイグレーション | アプリ | 混在するアプリ |
|---|---|---|---|
| 1. 拡張 | `full_name` 列を追加し、既存の行を埋め戻す。旧アプリの書き込みを `full_name` にも写すトリガーを作る | v2: 両方の列に書き、`full_name` を読む | v1（`name` だけ）と v2 |
| 2. 移行 | 同期のトリガーを削除 | v3: `full_name` だけを読み書きする | v2 と v3 |
| 3. 縮小 | `name` 列を削除 | v3 のまま | v3 だけ |

```mermaid
flowchart LR
  E["リリース 1 拡張<br>新しい列を追加・埋め戻し・同期<br>アプリは両方に書く"] --> M["リリース 2 移行<br>読み書きを新しい列へ<br>同期を止める"]
  M --> K["リリース 3 縮小<br>古い列を削除"]
```

各段階で、**そのとき同時に動きうるすべての版のアプリが正しく動く** ことが条件です。そして、どの段階でも 1 つ前に戻れます。古い列を消す（縮小）のは、古い列を使うアプリが確実にいなくなり、戻す必要もなくなってからです。

大きなテーブルでの実務上の注意:

- **埋め戻し（backfill）は小分けにする**。数億行を 1 つの UPDATE で更新すると、長時間のロックと巨大なトランザクションログで本番が止まる。主キーの範囲で数千行ずつ、間隔を空けて実行する。
- **ロックを取る DDL に注意する**。DB と版によって、列の追加がテーブルの書き直しを伴うかどうかが違う（例: PostgreSQL は 11 以降、揮発性でない既定値付きの列の追加で表を書き直さなくなった）。MySQL では、表のコピーを作りながら切り替える gh-ost（GitHub が公開）や pt-online-schema-change（Percona Toolkit）のような道具も使われる。適用する前に、本番と同じ規模のデータでかかる時間とロックを確かめる。
- **API とイベントの形式も同じ考え方で変える**。新旧の両方の形式を受け付ける期間を設けてから、古い形式をやめる（[9.4](../../09-architecture/04-api-design/README.md)）。

## 7. ロールバック・ロールフォワードと、速さと安定性

### 7.1 戻せる変更と、戻せない変更

問題のあるリリースへの対処には 2 つあります。

- **ロールバック**: 1 つ前の版に戻す。原因が分からなくても、まず影響を止められる。
- **ロールフォワード**: 修正版を作って前に進める。

原則は「**まず戻して、落ち着いて直す**」です。そのためには、ロールバックが常に可能でなければなりません。

- 前の版の成果物がすぐにデプロイできる状態で残っている（2.2 節）。
- **スキーマの変更が後方互換になっている**（6.2 節）。新しい版がスキーマを破壊的に変えていると、アプリだけ戻しても動かない。
- 新しい版が書いたデータを、古い版が読めて壊さない。
- 外部への副作用（送ったメール、実行した決済）は戻せないので、フィーチャーフラグで止められるようにしておく。

データの変換（移行）を伴う変更や、配布したモバイルアプリのように、本当に戻せない変更もあります。その場合は、フラグで止められるようにしたうえでロールフォワードを前提に計画し、段階的に公開します。

### 7.2 DORA の 4 つの指標

DORA は、ソフトウェアのデリバリー性能を次の指標で測ります（指標の定義や名前は年次の報告書で見直されることがあるので、最新は DORA の公式情報を確認してください）。

| 指標 | 意味 | 何の代理か |
|---|---|---|
| デプロイの頻度 | 本番にデプロイする頻度 | 速さ |
| 変更のリードタイム | コミットから本番で動くまでの時間 | 速さ |
| 変更の失敗率 | デプロイのうち、障害や手直し（ロールバック・修正）が必要になった割合 | 安定性 |
| デプロイ失敗からの復旧時間 | 失敗したデプロイから回復するまでの時間（以前は「平均復旧時間（MTTR）」と呼ばれていた） | 安定性 |

『Accelerate』が報告したのは、これらの指標で上位の組織は、速さと安定性の **両方** で優れているということです。小さな変更は、テストしやすく、レビューしやすく、壊れても原因がすぐ分かり、戻すのも簡単です。変更をまとめて大きくすると、そのすべてが悪化します。**リリースの頻度を下げて安全にする、は逆効果** なのです。これらの指標を組織の運営にどう使うか（使い方を誤ると数字のゲームになる）は [13.7](../../13-technical-leadership/07-delivery-and-productivity/README.md) で扱います。

### 7.3 重い承認会議なしの変更管理

多くの組織では、本番の変更の前に、変更諮問委員会（CAB, Change Advisory Board。ITIL の用語）や「リリース判定会議」の承認を必要としています。『Accelerate』は、こうした **外部の組織による承認** が、リードタイム・デプロイ頻度・復旧時間の悪化と結びつき、変更の失敗率の改善とは結びついていなかったと報告しています。変更の内容をよく知らない人が、まとめて大量の変更を承認しても、リスクは減らないのです。

代わりに有効なのは、**変更の近くにいる人によるレビュー**（ピアレビュー）と、**自動化されたチェック**（テスト・カナリアの判定・セキュリティの検査）、そして変更の記録と可視化です。規制などで承認の記録が必要な場合も、PR の承認と CI の結果を監査の証跡として残す形にすれば、デリバリーを遅くせずに要件を満たせることが多いでしょう（具体的な規制の要件は専門家に確認してください）。

## 8. 環境・モバイル・GitOps・CI のセキュリティ

### 8.1 環境

- **本番との同等性（dev/prod parity）**: 開発・ステージングと本番の違い（OS、DB の種類と版、設定）が大きいほど、「ステージングでは動いたのに」が増える。コンテナと IaC（[10.1](../../10-cloud-and-sre/01-cloud-and-iac/README.md)）で環境の定義をコード化して、違いを小さくする。
- **使い捨てのプレビュー環境**: PR ごとに一時的な環境を自動で作り、レビュアーや企画者が実際に触って確かめられるようにする。共有のステージング環境の取り合いがなくなる。
- ステージングで本番と同じ規模・同じデータを再現するのは難しい。完全な再現を目指すより、カナリアや本番での観測（[8.2](../02-testing/README.md) の 8 節）と組み合わせる。

### 8.2 モバイルアプリのリリース

モバイルアプリは、Web と違って **配布したものを取り戻せません**。

| 特徴 | 対策 |
|---|---|
| ストアの審査があり、公開までに時間がかかる（審査の期間は時期や内容で変わる） | 修正版をすぐに出せない前提で、フラグで機能を止められるようにする |
| 利用者が更新しない。古い版が何年も使われ続ける | API は古い版のアプリも動くように後方互換を保つ。最低限サポートする版を決め、それより古い版には更新を強制する仕組み（起動時の版の確認）を最初から入れておく |
| ロールバックできない | 段階的な公開（Google Play の段階的な公開、App Store の段階的なリリースなど）で、少数の利用者から広げ、クラッシュ率を見て止める |
| 画面や設定をアプリの中に焼き込むと変えられない | サーバー側の設定やフィーチャーフラグで振る舞いを変えられるようにする |

### 8.3 GitOps

**GitOps** は、本番環境の「あるべき状態」（どの版をどう動かすか）を Git リポジトリに宣言的に記述し、クラスタの中のエージェントがその状態を取り込み、実際の状態を継続的にそれに合わせる運用の方式です（2017 年に Weaveworks が提唱した用語）。Kubernetes の世界では Argo CD や Flux が代表的です（どちらも CNCF の卒業プロジェクト。2026年時点）。

- **変更はすべて Git への PR** になるので、レビュー・承認・監査の記録・ロールバック（`git revert`）が、コードと同じ仕組みでできる。
- CI から本番に「押し込む（push）」のではなく、本番側が「取りにいく（pull）」ので、CI に本番の強い権限を渡さずに済む。
- 手作業の変更（ドリフト）は、宣言された状態に自動で戻される。

Kubernetes の詳細は [10.2](../../10-cloud-and-sre/02-containers-and-kubernetes/README.md) で扱います。

### 8.4 CI/CD 自体を守る

CI/CD のパイプラインは、本番への書き込み権限と多数の秘密情報を持つ、攻撃者にとって魅力的な標的です。2025 年 3 月には、広く使われていた GitHub Actions のアクション（tj-actions/changed-files）が侵害され、既存のバージョンタグが悪意のあるコミットに付け替えられて、多数のリポジトリで CI の秘密情報がログに出力される事件が起きました（CVE-2025-30066）。

主な対策（GitHub Actions の設定例。SHA は実際の値に置き換えます）:

```yaml
name: ci
on:
  pull_request:
permissions:
  contents: read              # GITHUB_TOKEN の既定の権限を最小にする
jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      # タグ（v4 など）は付け替えられうるので、コミットの SHA（40 桁）で固定する
      - uses: actions/checkout@<コミットの SHA>   # vX.Y.Z
      - run: python3 tools/check.py
  deploy:
    if: github.ref == 'refs/heads/main'
    needs: test
    runs-on: ubuntu-latest
    permissions:
      contents: read
      id-token: write         # クラウドへの OIDC 認証に必要な権限だけを与える
    steps:
      - run: echo "OIDC で得た短命な資格情報でデプロイする"
```

- **サードパーティのアクションはコミットの SHA で固定する**。タグは後から付け替えられる。固定した SHA の更新は Renovate などに任せ、差分をレビューする。
- **トークンの権限を最小にする**。ワークフロー全体の既定を読み取りのみにし、必要なジョブにだけ必要な権限を与える。
- **長期のクラウドの鍵を CI に保存しない**。OIDC で CI の実行ごとに短命な資格情報を発行する（信頼する条件を、リポジトリ・ブランチ・環境で絞る）。[11.5](../../11-security/05-security-operations/README.md) で詳しく扱います。
- **信頼できないコードに秘密情報を渡さない**。フォークからの PR で動くワークフローには秘密情報を渡さない。GitHub の `pull_request_target` のように、権限の強い文脈で動くトリガーで PR のコードをチェックアウトして実行するのは危険。
- 本番へのデプロイは、保護されたブランチと環境（承認者の設定）に限定する。

## よくある落とし穴

1. **環境ごとにビルドし直す**。ステージングで試したものと本番に出したものが別物になります。1 回だけビルドし、同じ成果物（ダイジェストで識別）を昇格させます。
2. **ロックファイルをコミットしない、または無視してインストールする**。同じコミットから、日によって違う依存関係が入ります。アプリケーションではロックファイルを必ずコミットし、CI も本番もそれに従います。
3. **スキーマの破壊的な変更をアプリのデプロイと同時に行う**。デプロイの途中の混在期間に壊れ、しかもアプリだけ戻しても直りません。拡張・縮小で、各段階を後方互換にします。
4. **フラグを消さない、使い回す**。分岐と組み合わせが増え続け、Knight Capital のように、古いコードが予期せず動き出す原因になります。所有者と期限を付け、公開後に削除するまでを作業に含めます。
5. **カナリアを人の目視で判定する、または少ない標本で判定する**。見落としと、偶然の揺らぎによる誤判定が起きます。最小標本数・統計的な検定・効果量の下限を決めて自動化します。
6. **「安全のために」リリースの頻度を下げる**。1 回の変更が大きくなり、失敗の確率も影響範囲も、原因の特定の難しさも増えます。小さく頻繁に出し、仕組みで安全を確保します。
7. **ロールバックを一度も試したことがない**。いざというときに手順が動かないか、DB の変更のせいで戻せません。ロールバックも定期的に実行して確かめます。
8. **CI のアクションをタグで参照し、強い権限と長期の鍵を持たせる**。サプライチェーン攻撃の格好の標的になります。SHA での固定・最小権限・OIDC を標準にします。

## CTOの視点

1. **デリバリー性能を経営の指標にする**。デプロイの頻度・リードタイム・変更の失敗率・復旧時間は、エンジニアリング組織が事業の変化にどれだけ速く安全に対応できるかを表します。四半期ごとに推移を見て、悪化の原因（CI の遅さ、承認の待ち、大きな変更）に投資します。ただし、指標をチームや個人の評価に直結させると、数字を良く見せるための行動（意味のない細かいデプロイなど）を招くので、改善のための道具として使います（[13.7](../../13-technical-leadership/07-delivery-and-productivity/README.md)）。
2. **承認の会議を、自動化とピアレビューに置き換える**。重い変更管理のプロセスがある組織では、「安全のため」という理由で導入された会議が、実際にはリスクを減らさずにリードタイムを延ばしていることが多いです。監査や規制の要件を満たす証跡（PR の承認・CI の結果・デプロイの記録）を自動で残す仕組みを作り、会議は本当に重大な変更に絞ります。
3. **「戻せること」をリリースの完了条件にする**。設計レビューでは「この変更は、デプロイの途中で新旧が混在しても動くか」「問題が起きたら何分で、どうやって戻すか」「戻せない部分（データ移行・外部への副作用・配布したアプリ）はどこで、どう段階的に公開するか」を必ず問いましょう。
4. **フラグとパイプラインは、全社の基盤として提供する**。チームごとにフラグの仕組みやデプロイの方式を作ると、品質がばらつき、Knight Capital のような事故の芽が残ります。フラグの管理（所有者・期限・監査の記録）、カナリアの自動判定、ロールバックの手順を、プラットフォームとして提供し、各チームが最初から安全な道を通れるようにします（[13.6](../../13-technical-leadership/06-team-and-org-design/README.md) のプラットフォームチーム）。
5. **CI/CD をセキュリティの最重要資産として扱う**。パイプラインは本番への鍵を持っています。アクションの固定、最小権限、OIDC、秘密情報の扱い、ランナーの隔離を全社の標準とし、定期的に棚卸しします。侵害されたときの影響範囲（どの鍵で何ができるか）を把握していることが、インシデント対応の速さを決めます（[14.6](../../14-cto/06-crisis-management/README.md)）。

### 演習 5（記述）: 多通貨対応のリリース計画

EC サイトの注文テーブルは、金額を `orders.amount`（円の整数）だけで持っています。海外展開のため、`amount_minor`（最小単位の整数）と `currency`（ISO 4217 の通貨コード）の 2 列に移行することになりました。注文テーブルは 3 億行あり、24 時間止められません。iOS・Android のアプリは注文履歴 API から `amount` を受け取って表示しており、古い版のアプリも多く使われています。

リリースの計画を、(1) DB の変更の段階、(2) アプリと API の変更、(3) 公開の方法と判定、(4) 戻し方、の観点で書いてください。

<details>
<summary>解答例</summary>

**(1) DB の変更（拡張・縮小）**

1. 拡張: `amount_minor BIGINT NULL` と `currency CHAR(3) NULL` を追加する（本番規模のデータで、ロックとかかる時間を事前に確認する。必要ならオンラインのスキーマ変更の道具を使う）。
2. アプリを「両方に書く」版にしてから、既存の 3 億行を主キーの範囲で小分けに埋め戻す（`amount_minor = amount`, `currency = 'JPY'`）。進捗と DB の負荷を監視し、夜間だけに限らず、負荷に応じて速度を調整する。
3. 埋め戻しが終わり、新旧の列が全件一致することを検証するジョブで確認してから、`NOT NULL` 制約を付ける。
4. 縮小: 読み書きをすべて新しい列に切り替え、古い列を使う版が残っていないことを確認してから、`amount` を削除する（古いアプリのための API の互換を保つ期間が終わってから。数か月後になることもある）。

**(2) アプリと API**: API には `amount_minor` と `currency` を追加し、既存の `amount` は日本円の注文に限って当面返し続ける（古いアプリが壊れないように）。外貨の注文を古いアプリにどう見せるか（表示できないので更新を促すなど）を決め、最低サポート版の強制更新の仕組みを使う。

**(3) 公開の方法と判定**: 多通貨の機能はフィーチャーフラグの背後に置き、社内の利用者 → 一部の国の少数の利用者 → 段階的に拡大、とする。各段階で、注文のエラー率・決済の失敗率・金額の新旧の列の不一致数を指標にし、自動判定で広げる・止める。

**(4) 戻し方**: 各段階が後方互換なので、アプリは 1 つ前の版に戻せる（両方に書いている間は、古い列も正しい）。フラグを切れば外貨の注文を即座に止められる。戻せないのは、外貨で成立した注文（データと決済）なので、それが発生する段階の前に、返金・サポートの手順を決めておく。

採点の観点: 拡張・縮小の段階と、各段階での新旧アプリの混在、埋め戻しの小分けと検証、古いモバイルアプリへの互換、フラグによる段階的な公開と指標、戻せない部分の特定、が入っていれば十分です。「メンテナンス時間を取って一度に移行する」は、要件（24 時間止められない、古いアプリ）を満たさないので不可です。

</details>

## 理解度チェック

**Q1. 継続的デリバリーと継続的デプロイの違いは何ですか。また、「CI ツールを使っているが CI をしていない」とはどういう状態ですか。**

<details>
<summary>解答</summary>

継続的デリバリーは、main のすべての変更が常にリリース可能な状態に保たれ、本番へのデプロイは人の判断（ボタン）で行える状態です。継続的デプロイは、パイプラインを通ったすべての変更が人の判断なしに自動で本番にデプロイされる状態です。「CI ツールを使っているが CI をしていない」とは、自動テストは回しているものの、長命なフィーチャーブランチで開発していて、main への統合が数週間に 1 回しか起きない状態です。CI の本質は頻繁な統合であり、道具ではありません。

</details>

**Q2. 「ビルドは 1 回、同じ成果物を昇格させる」原則を守らないと、何が起きますか。**

<details>
<summary>解答</summary>

環境ごとにビルドし直すと、依存関係の解決（その時点の最新版が入る）、ビルド環境やツールの版の違い、ビルド時の設定の違いによって、ステージングでテストした成果物と本番に出した成果物が別物になります。「ステージングでは動いたのに本番で壊れた」の原因になり、何がデプロイされているかの追跡もできなくなります。成果物はコミットの SHA やダイジェストで識別し、環境の違いは設定で与えるべきです。

</details>

**Q3. `^0.4.2` と `^1.4.2` の意味の違いを説明し、0.x のライブラリに依存するときの注意点を述べてください。**

<details>
<summary>解答</summary>

`^1.4.2` は `>=1.4.2 <2.0.0-0` で、1.x の範囲の更新（機能追加とバグ修正）を受け入れます。`^0.4.2` は `>=0.4.2 <0.5.0-0` で、0.4.x のパッチだけを受け入れます。SemVer では 0.x の段階は「初期開発中で、いつでも何でも変わりうる」とされているため、MINOR の変更も破壊的でありうるからです。0.x のライブラリに依存するときは、MINOR の更新でも破壊的な変更を想定し、ロックファイルで固定したうえで、更新時に変更履歴とテストで確認する必要があります。

</details>

**Q4. フィーチャーフラグで「10% の利用者に公開」するとき、リクエストごとに乱数で決めると何が問題ですか。安定したハッシュを使う方法の利点を 3 つ挙げてください。**

<details>
<summary>解答</summary>

リクエストごとに乱数で決めると、同じ利用者がページを移動するたびに新旧の機能が入れ替わり、体験が揺れ、実験の結果も測れません。安定したハッシュ（フラグのキー＋利用者 ID のハッシュから 0〜9999 のバケットを決める）の利点は、(1) 同じ利用者はいつ・どのサーバーで評価しても同じ結果になり、状態の保存が要らない、(2) 割合を 10% → 25% と広げても、すでに有効だった利用者は有効のまま、(3) フラグのキーを混ぜるのでフラグごとに独立し、同じ利用者ばかりが実験の対象になる偏りを防げる、の 3 つです。

</details>

**Q5. 列の改名を 1 回のデプロイで行うと、なぜ問題が起きるのですか。拡張・縮小の手順で、各段階が満たすべき条件は何ですか。**

<details>
<summary>解答</summary>

ローリングデプロイなどでは、新旧のアプリが同時に動く期間があります。マイグレーションで列名を変えると、古いアプリは古い列名で読み書きして失敗し、マイグレーションを後にすると新しいアプリが失敗します。また、アプリだけを戻しても、スキーマが変わっているので直りません。拡張・縮小では、新しい列の追加と同期（拡張）→ 読み書きの移行 → 古い列の削除（縮小）と段階を分け、各段階で「そのとき同時に動きうるすべての版のアプリが正しく動く」ことと、「1 つ前の段階に戻せる」ことを満たします。

</details>

**Q6. カナリアの判定で「p 値が 0.01 未満」だけを条件にすると、どういう問題がありますか。**

<details>
<summary>解答</summary>

2 つの問題があります。第一に、標本が非常に多いと、実務上は無視できるほど小さな差（エラー率 0.01 ポイントなど）でも統計的に有意になり、不必要なロールバックが起きます。効果量の下限（例: 0.1 ポイント以上の悪化）と組み合わせる必要があります。第二に、判定を一定間隔で何度も繰り返すと、そのうちどれかが偶然に有意になる確率が上がります（多重検定・覗き見の問題）。判定の回数を決める、有意水準を厳しくする、最小標本数を設けるなどの対策が必要です。逆に、標本が少ないうちは差があっても有意にならないので、最小標本数に満たないうちは判定しない（CONTINUE）ことも必要です。

</details>

**Q7. 「リリースの頻度を下げれば安全になる」という主張に、DORA の研究を踏まえて反論してください。**

<details>
<summary>解答</summary>

DORA の調査（『Accelerate』）では、デプロイの頻度が高くリードタイムが短い組織ほど、変更の失敗率が低く、復旧も速い傾向が報告されています。頻度を下げると 1 回のリリースに含まれる変更が大きくなり、テストとレビューが難しく、壊れたときの影響範囲が広く、原因の特定と修正に時間がかかり、戻すのも難しくなります。安全性は頻度を下げることではなく、小さな変更・自動テスト・段階的な公開・すばやいロールバックという仕組みで確保するものです。

</details>

**Q8. GitHub Actions でサードパーティのアクションを `@v4` のようなタグで参照することの危険と、その対策を説明してください。**

<details>
<summary>解答</summary>

タグはリポジトリの所有者（または、その権限を奪った攻撃者）が後から別のコミットに付け替えられるため、昨日まで安全だったワークフローが、今日から悪意のあるコードを実行しうるからです。2025 年には、広く使われていたアクションのタグが悪意のあるコミットに付け替えられ、多くのリポジトリで CI の秘密情報が漏れる事件が起きました。対策は、アクションを 40 桁のコミットの SHA で固定し、その更新は自動化ツールで PR にして差分をレビューすることです。合わせて、GITHUB_TOKEN の権限を最小にし、長期の鍵の代わりに OIDC の短命な資格情報を使えば、侵害されたときの被害も小さくできます。

</details>

## まとめ

- CI は道具ではなく「頻繁に main に統合し、統合のたびに自動で検証する」実践。継続的デリバリーは常にリリース可能な状態、継続的デプロイはそれを自動で本番に出すこと。
- 成果物は 1 回だけビルドし、同じものを昇格させる。環境の違いは設定で与え、再現可能なビルドとキャッシュで速さと信頼性を両立する。
- ロックファイルで依存を固定し、SemVer の範囲指定の意味（0.x での `^`、プレリリースの除外）を正確に理解したうえで、自動の更新 PR で小さくこまめに取り込む。
- デプロイ戦略は、新旧が混在する期間の互換性が前提。カナリアは最小標本数・統計的な検定・効果量の下限で自動判定する。
- フィーチャーフラグはデプロイとリリースを切り離すが、負債にもなる。安定したハッシュで割合を出し分け、所有者と期限を付け、使い終えたら消す。評価は決して例外で落とさない。
- スキーマの変更は、版管理されたマイグレーションを 1 つずつトランザクションで適用し、破壊的な変更は拡張・縮小で複数のリリースに分けて無停止で行う。
- 「まず戻して、落ち着いて直す」ために、戻せることをリリースの条件にする。速さと安定性は両立し、重い承認会議より、ピアレビューと自動化が安全を生む。CI/CD 自体も SHA での固定・最小権限・OIDC で守る。
