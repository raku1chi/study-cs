## なぜ学ぶのか

計算量の見落としは、テスト環境の小さなデータでは現れず、本番の大きなデータで初めて牙をむきます。

- **うっかり二乗**: 2021 年、あるプログラマー（t0st）が、ゲーム「GTA Online」のロード時間が長い原因を解析して公開しました。約 10 MB の JSON を読む処理で、`sscanf` が呼ばれるたびに残りの文字列全体の長さを数え直していたこと（二乗時間）と、読み込んだ要素の重複チェックを毎回リストの先頭から線形に探していたこと（これも二乗時間）が原因で、修正によってロード時間が約 7 割短くなったと報告しています。開発元の Rockstar Games はこの分析を認め、修正を配布しました。
- **最悪ケースの計算量**: 2019 年 7 月 2 日、Cloudflare は、WAF（Web アプリケーションファイアウォール）に追加したルールの正規表現が、バックトラッキングによって入力長に対して爆発的な計算量になり、世界中のサーバーの CPU を使い切る障害を起こしました（同社の公開ポストモーテムによる）。正規表現エンジンの最悪計算量という、普段は意識しない性質が原因でした（[2.7 計算理論](../07-theory-of-computation/README.md)）。
- **計算量を攻撃に使う**: 2011 年、Alexander Klink と Julian Wälde は、ハッシュ値が衝突するキーを大量に送り付けるだけで、多くの Web フレームワークのハッシュテーブルが平均 O(1) から最悪 O(n) に劣化し、少ないリクエストでサーバーの CPU を占有できることを示しました（hash flooding）。Python はこれを受けて、文字列のハッシュのランダム化を導入し（3.3 以降は既定で有効）、のちにハッシュ関数を SipHash に変更しました（PEP 456）。

「平均的には速い」「手元では速い」では不十分です。**入力がどれだけ大きくなりうるか、最悪の場合に何が起きるか** を問えることが、スケールするシステムを作る前提になります。

## 1. アルゴリズムと正しさ

### 1.1 アルゴリズムとは

**問題（problem）** は入力と出力の関係（例:「整数の列を受け取り、昇順に並べた列を返す」）、**インスタンス** はその具体的な入力（`[3, 1, 2]`）、**アルゴリズム** はどのインスタンスに対しても有限の手順で正しい出力を求める方法です。Knuth は『The Art of Computer Programming』で、アルゴリズムの性質として有限性（必ず停止する）・明確性（各手順があいまいでない）・入力・出力・実効性（各手順が実行可能）を挙げています。

同じ問題に多くのアルゴリズムがあり、それらを比べる軸が **正しさ** と **効率** です。正しくない速いプログラムには価値がないので、まず正しさから始めます。

### 1.2 正しさはループ不変条件で示す

ソート済みの列から値を探す **二分探索（binary search）** は単純に見えますが、正しく書くのが難しいことで有名です。Jon Bentley は『珠玉のプログラミング』（原著 "Programming Pearls"）で、プロのプログラマーに二分探索を書かせると多くが誤りを含んでいたと述べています。また Joshua Bloch は 2006 年、Java の標準ライブラリの二分探索に、配列が非常に大きいとき `(low + high) / 2` が整数オーバーフローを起こす（[1.1 情報の表現](../../01-computer-systems/01-data-representation/README.md)）バグが長年潜んでいたことを報告しました。

こうした誤りを防ぐ方法が、2.1 章で学んだ **ループ不変条件** です。

```python
def binary_search(a, x):
    """昇順の列 a から x を探し、見つかれば添字、なければ -1 を返す"""
    lo, hi = 0, len(a)               # 探す範囲は半開区間 [lo, hi)
    while lo < hi:
        # 不変条件: x が a にあるなら、その位置は [lo, hi) の中にある
        mid = (lo + hi) // 2         # Python の int はあふれない。C や Java では lo + (hi - lo) // 2
        if a[mid] < x:
            lo = mid + 1             # a[mid] 以下の位置には x はない
        elif x < a[mid]:
            hi = mid                 # a[mid] 以上の位置には x はない
        else:
            return mid
    return -1                        # 範囲が空になった。不変条件より x は a にない

print(binary_search([2, 3, 5, 7, 11, 13], 7), binary_search([2, 3, 5, 7, 11, 13], 8))   # 3 -1
```

- **初期化**: 範囲は列全体なので、不変条件は自明に成り立つ。
- **維持**: 列が昇順なので、`a[mid] < x` なら mid 以下の位置に x はない。範囲を狭めても不変条件は保たれる。
- **停止**: 変量 hi − lo は毎回少なくとも 1 減る（mid は [lo, hi) の中にあるので、`lo = mid + 1` も `hi = mid` も範囲を狭める）。`lo = mid`（+1 なし）と書くと、範囲が 2 のとき進まなくなり、無限ループになります。
- **終了**: 範囲が空になれば、不変条件から x は存在しない。

区間を半開区間 [lo, hi) で表すと、「空の範囲」が lo == hi で表せて、境界の ±1 の扱いが統一できます。演習 2 では、この考え方で「x 以上の最初の位置」を返す `lower_bound` などの変種を実装します。

## 2. 計算量の考え方と漸近記法

### 2.1 何を数えるか

実行時間はマシン・言語・負荷で変わるので、アルゴリズムの比較には使いにくい指標です。そこで、入力の大きさ n に対して **基本操作（比較・代入・算術演算など）の回数** がどう増えるかを数えます。基本操作 1 回に一定の時間がかかるという、簡略化したモデル（RAM モデル）での議論です。現実にはキャッシュの効き方などで 1 回あたりの時間が大きく変わり（7 節）、この簡略化の限界も知っておく必要があります。

同じ n でも入力によって手間が変わるので、どの入力について考えるかを区別します。

| 種類 | 意味 | 例: 線形探索 | 例: クイックソート | 例: ハッシュテーブルの検索 |
|---|---|---|---|---|
| 最良計算量 | 最も有利な入力 | 先頭にある: O(1) | O(n log n) | O(1) |
| 平均計算量 | 入力（または乱択）の分布に関する期待値 | O(n) | O(n log n) | O(1) |
| 最悪計算量 | 最も不利な入力 | 末尾かない: O(n) | O(n²) | O(n)（全キーが衝突） |

実務で重視すべきは多くの場合 **最悪計算量** です。入力を攻撃者が選べるなら、最悪ケースは「めったに起きない」ではなく「狙って起こされる」ものです（hash flooding、正規表現の ReDoS）。

### 2.2 O・Ω・Θ の定義

関数の「増え方」を比べるのが **漸近記法（asymptotic notation）** です。定義は 2.1 章の量化子で書くと正確です。

```text
f(n) = O(g(n))  ⇔  ∃c > 0. ∃n₀. ∀n ≥ n₀. f(n) ≤ c·g(n)      上界（高々 g の定数倍）
f(n) = Ω(g(n))  ⇔  ∃c > 0. ∃n₀. ∀n ≥ n₀. f(n) ≥ c·g(n)      下界（少なくとも g の定数倍）
f(n) = Θ(g(n))  ⇔  f(n) = O(g(n)) かつ f(n) = Ω(g(n))        同じ増え方
```

例として、f(n) = 3n² + 10n + 5 が O(n²) であることを示します。c = 4 とすると、3n² + 10n + 5 ≤ 4n² ⇔ n² − 10n − 5 ≥ 0 で、これは n ≥ 11 で成り立ちます（n = 11 で 121 − 110 − 5 = 6 ≥ 0）。よって c = 4、n₀ = 11 が定義の「存在する」を満たします。同様に f(n) ≥ 3n² なので Ω(n²) でもあり、**f(n) = Θ(n²)** です。

直感的には、「**最も速く増える項だけを残し、係数を無視する**」ことです。定数倍を無視するのは、それがマシンや実装で変わり、n が大きくなると増え方の差が必ず勝つからです。

よくある誤解を 2 つ正しておきます。

- **O は「最悪計算量」の意味ではありません**。O は関数の上界を表す記法で、最悪・平均・最良のどの関数にも使えます。「クイックソートの平均計算量は Θ(n log n)、最悪計算量は Θ(n²)」のように組み合わせて使います。
- **O は上界なので、ゆるくても正しい**。線形探索は O(n²) でもあります（間違いではないが情報がない）。正確な増え方を言いたいときは Θ を使います。実務の会話で「O(n)」と言うとき、多くの人は Θ(n) の意味で使っています。

### 2.3 増え方を比べる — 1 秒で扱える n

| 計算量 | n = 10 | n = 1,000 | n = 10⁶ | 1 秒で扱える n の目安（CPython） | 同（コンパイル言語） |
|---|---|---|---|---|---|
| O(1) | 1 | 1 | 1 | 制限なし | 制限なし |
| O(log n) | 3 | 10 | 20 | 事実上制限なし | 事実上制限なし |
| O(n) | 10 | 10³ | 10⁶ | 約 10⁷ | 約 10⁸〜10⁹ |
| O(n log n) | 33 | 10⁴ | 2 × 10⁷ | 約 5 × 10⁵ | 約 5 × 10⁶〜4 × 10⁷ |
| O(n²) | 100 | 10⁶ | 10¹² | 約 3,000 | 約 10⁴〜3 × 10⁴ |
| O(n³) | 1,000 | 10⁹ | 10¹⁸ | 約 200 | 約 500〜1,000 |
| O(2ⁿ) | 1,024 | 約 10³⁰¹ | — | 約 23 | 約 27〜30 |
| O(n!) | 約 3.6 × 10⁶ | — | — | 約 10 | 約 11〜12 |

右の 2 列は、CPython が 1 秒に単純な操作を **およそ 10⁷ 回**、C や Java などのコンパイル言語が **およそ 10⁸〜10⁹ 回** 実行できると仮定した **桁の目安** です。実際の速さは処理の内容で 1 桁以上変わります（例えば、この章の執筆環境の Python 3.11 では、`s += i` だけの最も単純なループが 1 回あたり約 26 ns でした）。

この表から読み取るべきことは、正確な数字ではなく次の 2 点です。

- **O(n²) は 1 万件を超えると危険信号**。10⁶ 件で O(n²) なら 10¹² 回の操作で、CPython では約 28 時間かかります。テスト環境の 1,000 件では 0.1 秒だった処理が、本番の 100 万件では 1 日かかる。これがうっかり二乗の正体です。
- **指数時間は n を少し増やすだけで絶望的になる**。2ⁿ のアルゴリズムは、マシンが 1,000 倍速くなっても扱える n が 10 増えるだけです。

### 2.4 コードから計算量を読む

基本的な規則は次の通りです。

| コードの形 | 計算量 |
|---|---|
| 処理を順に並べる | 足し算（大きい方が残る）: O(f) + O(g) = O(max(f, g)) |
| ループの中で処理する | 掛け算: 反復回数 × 1 回あたりのコスト |
| 変数を毎回 2 倍（または半分）にするループ | O(log n) 回 |
| 再帰 | 漸化式を立てて解く（3 節） |

入れ子のループでも、内側の回数が外側に依存すると計算が必要です。

```python
for i in range(n):              # 内側は n - i 回 → 合計 n + (n-1) + … + 1 = n(n+1)/2 = Θ(n²)
    for j in range(i, n):
        ...

i = 1
while i < n:                    # i は 1, 2, 4, 8, … → Θ(log n) 回
    i *= 2

for i in range(1, n + 1):       # 内側は n/i 回 → n(1 + 1/2 + … + 1/n) ≈ n ln n = Θ(n log n)
    for j in range(i, n + 1, i):
        ...
```

最後の例の和 1 + 1/2 + … + 1/n（調和級数）は ln n 程度に増えます。2.1 章のエラトステネスの篩は素数 p についてだけ内側のループを回すので、さらに小さい O(n log log n) になります。

**隠れたループに注意してください**。`x in some_list`、`some_list.index(x)`、`some_list.pop(0)`、`sorted(...)`、文字列の連結、ORM の属性アクセスが発行する SQL などは、1 行でも O(n) 以上の仕事をします（8 節と 9 節）。

## 3. 再帰と漸化式

### 3.1 漸化式を立てる

再帰的なアルゴリズムの計算量は、**漸化式（recurrence）** で表せます。

| アルゴリズム | 漸化式 | 解 |
|---|---|---|
| 二分探索 | T(n) = T(n/2) + O(1) | Θ(log n) |
| マージソート（半分ずつソートして併合） | T(n) = 2T(n/2) + Θ(n) | Θ(n log n) |
| 素朴なフィボナッチ数の計算 | T(n) = T(n−1) + T(n−2) + O(1) | Θ(φⁿ)、φ ≈ 1.618 |

最後の例は、同じ部分問題を何度も解き直すせいで指数時間になります。実際に呼び出し回数を数えてみましょう。

```python
from functools import lru_cache

calls = 0
def fib(n):
    global calls
    calls += 1
    return n if n < 2 else fib(n - 1) + fib(n - 2)

print(fib(30), calls)                 # 832040 2692537

@lru_cache(maxsize=None)              # 一度計算した結果を覚えておく（メモ化）
def fib_memo(n):
    return n if n < 2 else fib_memo(n - 1) + fib_memo(n - 2)

print(fib_memo(30), fib_memo.cache_info())
# 832040 CacheInfo(hits=28, misses=31, maxsize=None, currsize=31)
```

fib(30) を求めるのに 269 万回呼び出していたものが、メモ化すると 31 回の計算で済みます。部分問題の結果を再利用するこの考え方は **動的計画法** の基礎です（[2.6 アルゴリズム設計技法](../06-algorithm-design/README.md)）。

### 3.2 再帰木で解く

漸化式を直感的に解く方法が **再帰木（recursion tree）** です。マージソートの T(n) = 2T(n/2) + cn を木にすると、次のようになります。

```text
段         部分問題                            その段の仕事量
0                      n                       cn
1              n/2            n/2              2 × c(n/2) = cn
2          n/4    n/4     n/4    n/4           4 × c(n/4) = cn
…                      …                       …
log₂n      1  1  1  1  …  1  1  1  1           n × c = cn
                                     合計: cn × (log₂ n + 1) = Θ(n log n)
```

各段の仕事量がちょうど cn で、段数が log₂ n + 1 なので、合計は Θ(n log n) です。

### 3.3 マスター定理

分割統治でよく現れる形 **T(n) = a·T(n/b) + Θ(nᵈ)**（大きさ n/b の部分問題を a 個解き、分割と統合に Θ(nᵈ) かかる）には、**マスター定理（master theorem）** が使えます（ここでは f(n) が多項式の場合の簡略版を示します）。

```text
a と bᵈ を比べる（= 葉の数の増え方 n^(log_b a) と、根の仕事量 nᵈ を比べる）
  場合 1: a > bᵈ  → T(n) = Θ(n^(log_b a))    葉（小さい部分問題の数）が支配的
  場合 2: a = bᵈ  → T(n) = Θ(nᵈ log n)       各段の仕事量が等しい
  場合 3: a < bᵈ  → T(n) = Θ(nᵈ)             根（最初の分割・統合）が支配的
```

再帰木で考えると、段 k の仕事量は aᵏ × (n/bᵏ)ᵈ = nᵈ × (a/bᵈ)ᵏ です。比 a/bᵈ が 1 より大きければ下の段ほど重く（場合 1）、1 なら全段が等しく（場合 2）、1 より小さければ上の段ほど重く（場合 3）なります。3 つの場合は、等比数列の和のどの項が支配的かの違いにすぎません。

| アルゴリズム | a, b, d | 比較 | 計算量 |
|---|---|---|---|
| 二分探索 | 1, 2, 0 | a = bᵈ | Θ(log n) |
| マージソート | 2, 2, 1 | a = bᵈ | Θ(n log n) |
| 二分木の全ノードをたどる | 2, 2, 0 | a > bᵈ | Θ(n) |
| 素朴な分割統治の掛け算（4 つの部分積） | 4, 2, 1 | a > bᵈ | Θ(n²) |
| カラツバ法（3 つの部分積） | 3, 2, 1 | a > bᵈ | Θ(n^log₂3) ≈ Θ(n^1.585) |
| シュトラッセン法（行列の積） | 7, 2, 2 | a > bᵈ | Θ(n^log₂7) ≈ Θ(n^2.807) |

**カラツバ法（Karatsuba）** は、n 桁の数や多項式の掛け算を半分の大きさの 3 回の掛け算に帰着させます。部分積を 4 回から 3 回に減らすだけで、指数が 2 から約 1.585 に下がるのです。CPython の `int` も、桁数の大きい整数の掛け算にカラツバ法を使っています。演習 5 では、実際に掛け算の回数を数えて、マスター定理の予測と一致することを確かめます。

マスター定理が使えない漸化式もあります。例えば T(n) = T(n−1) + n（1 つずつしか小さくならない）は、展開すると n + (n−1) + … + 1 = Θ(n²) です。「ソート済みの入力で、ピボットを先頭に選ぶクイックソート」がちょうどこの形で、最悪計算量が Θ(n²) になる理由です。

## 4. ならし解析 — 動的配列の append はなぜ O(1) なのか

### 4.1 集計法: 倍々に伸ばせば合計は線形

Python の `list` のような **動的配列** は、連続したメモリ領域に要素を並べ、領域が足りなくなると、より大きな領域を確保して全要素をコピーします。コピーは O(n) なので、「append は最悪 O(n)」です。それでも append が O(1) と言われるのは、**容量を定数倍ずつ広げると、コピーがめったに起きない** からです。

容量を 1, 2, 4, 8, … と 2 倍ずつ広げる場合、n 回の append でのコピーの合計は、2.1 章で帰納法を使って証明した等式から

```text
1 + 2 + 4 + … + 2ᵏ = 2ᵏ⁺¹ − 1 < 2n        （2ᵏ < n のとき）
```

です。append 自身の書き込み n 回と合わせても **3n 回未満** で、1 回あたり定数です。このように、操作列全体のコストの合計を操作の回数で割って評価する方法を **ならし解析（amortized analysis）** の **集計法（aggregate method）** といいます。

容量の広げ方を変えると、結果は大きく変わります。100 万回 append したときのコピー回数を数えてみましょう。

```python
def total_copies(n, grow):
    """容量が足りなくなるたびに grow(容量) へ広げたとき、n 回の append でのコピー回数の合計"""
    capacity, size, copies = 1, 0, 0
    for _ in range(n):
        if size == capacity:
            copies += size
            capacity = grow(capacity)
        size += 1
    return copies

n = 1_000_000
for name, grow in [("2 倍", lambda c: 2 * c), ("1.5 倍", lambda c: max(c + 1, c * 3 // 2)),
                   ("+1,000 ずつ", lambda c: c + 1000)]:
    c = total_copies(n, grow)
    print(f"{name:10}: コピー {c:>15,} 回（1 回の append あたり {c / n:,.1f} 回）")
```

```text
2 倍       : コピー       1,048,575 回（1 回の append あたり 1.0 回）
1.5 倍     : コピー       2,099,753 回（1 回の append あたり 2.1 回）
+1,000 ずつ : コピー     499,501,000 回（1 回の append あたり 499.5 回）
```

**定数倍（幾何級数的）に広げれば何倍でもならし O(1)** ですが、**一定数ずつ広げると全体が O(n²)** になります。倍率を大きくするとコピーは減りますが、使わない領域（メモリの無駄）が増えるトレードオフがあります。CPython の `list` は、実際には約 1.125 倍ずつ広げています（CPython 3.11、64 ビット環境での観察）。

```python
import sys

xs, last, changes = [], sys.getsizeof([]), []
for i in range(100):
    xs.append(i)
    if sys.getsizeof(xs) != last:
        last = sys.getsizeof(xs)
        changes.append((len(xs), (last - sys.getsizeof([])) // 8))   # (要素数, 新しい容量)
print(changes)
# [(1, 4), (5, 8), (9, 16), (17, 24), (25, 32), (33, 40), (41, 52), (53, 64), (65, 76), (77, 92), (93, 108)]
```

倍率が小さいとコピーは増えますが、CPython はメモリの再確保（realloc）がその場で領域を延長できる場合はコピーを避けられるので、実際のコストはこの計算より小さくなります。

### 4.2 会計法: 先に払っておく

**会計法（accounting method）** では、各操作に実際のコストより多めの「料金」を課し、余りを貯金して、後の高価な操作の支払いに充てます。倍々に広げる動的配列なら、append 1 回に 3 の料金を課します。

- 1 は、その要素を書き込むコストとして使う。
- 2 は貯金する。容量が 2k から 4k に広がるとき、コピーすべき要素は 2k 個あり、そのうち後半の k 個が前回の拡張以降に追加された要素です。その k 個が 2 ずつ貯めた 2k が、ちょうど 2k 個のコピー代になります。

貯金が負にならないので、n 回の操作の実際のコストは料金の合計 3n 以下です。演習 3 のテストは、この「総書き込み回数 ≤ 3n」を確かめます。

### 4.3 縮め方と振動

pop で要素が減ったとき、メモリを返すために領域を縮めたくなります。しかし「半分以下になったら半分に縮める」と、ちょうど境界で append と pop を繰り返したときに、拡張と縮小が交互に起きて **毎回 O(n) のコピー** が発生します（振動、thrashing）。

```text
容量 8 で満杯（8 個）→ append: 容量 16 に拡張（8 個コピー）→ pop: 8 個 = 16 の半分なので容量 8 に縮小（8 個コピー）
→ append: 満杯なので拡張（8 個コピー）→ …
```

解決策は、**拡張と縮小の閾値をずらす** ことです。「1/4 以下になったら半分に縮める」なら、縮小した直後の使用率は 1/2 で、次に拡張や縮小が起きるまでに少なくとも容量の 1/4 回分の操作が必要になり、そのあいだに貯金が貯まります。同じ考え方（ヒステリシス）は、オートスケーリングの「スケールアウトとスケールインの閾値を離す」設定にも現れます。

### 4.4 ならしは平均ではない

ならし解析は **確率を使わない、操作列全体についての最悪の保証** です。「平均的な入力なら速い」という平均計算量とは別物で、どんな操作列でも合計が抑えられます。

ただし、**個々の操作はたまに遅い** ことに変わりはありません。巨大なハッシュテーブルや配列の拡張は、その 1 回だけで数百ミリ秒かかることがあり、レイテンシの p99.9 に現れます。Redis のハッシュテーブルが、拡張時に全要素を一度に移すのではなく、以降の操作のたびに少しずつ移す **段階的な再ハッシュ（incremental rehashing）** を採用しているのは、この 1 回の停止を避けるためです。レイテンシに厳しいシステムでは、ならし O(1) でも十分ではないことがあります。

## 5. 空間計算量

アルゴリズムが使う **メモリ** の量も、入力サイズの関数として評価します。入力そのものを除いた追加の領域を **補助領域（auxiliary space）** と呼ぶことが多いです。

| アルゴリズム | 時間 | 補助領域 |
|---|---|---|
| マージソート | Θ(n log n) | Θ(n)（併合用の配列） |
| ヒープソート | Θ(n log n) | Θ(1) |
| 再帰の深さが d のアルゴリズム | — | Θ(d)（呼び出しごとのスタックフレーム） |
| メモ化したフィボナッチ | Θ(n) | Θ(n)（覚えておく表） |
| 移動平均や件数のストリーム集計 | 1 件あたり Θ(1) | Θ(1)（データを保存しない） |

見落としやすいのが **再帰の深さ** です。CPython の再帰の深さの上限は既定で 1000（`sys.getrecursionlimit()`）で、深さ n の再帰は n が数千を超えると `RecursionError` になります。連結リストや深い木を再帰でたどる処理は、ループと明示的なスタックに書き換えます。

時間と空間は **トレードオフ** の関係にあることが多く、メモ化、キャッシュ、データベースのインデックス、事前計算した表は、どれも「メモリを払って時間を買う」手段です（[6.2 インデックスとクエリ処理](../../06-databases/02-indexes-and-query-processing/README.md)）。

計算量が同じでも、**定数倍のメモリ** は現実のコストに直結します。Python の `int` はオブジェクトなので、100 万個の整数のリストは、整数そのもの（1 個 28 バイト程度）とリストのポインタ（8 バイト）で数十 MB を使います。

```python
import tracemalloc
from array import array

tracemalloc.start()
xs = list(range(10**6))
print(f"list  : {tracemalloc.get_traced_memory()[0] / 1e6:.1f} MB")   # list  : 40.0 MB（3.10 では 36.0 MB）
del xs
tracemalloc.stop(); tracemalloc.start()
ys = array("q", range(10**6))                                         # 64 ビット整数を詰めて持つ
print(f"array : {tracemalloc.get_traced_memory()[0] / 1e6:.1f} MB")   # array : 8.2 MB
```

大量の数値を扱うなら、`array` モジュールや NumPy のように値を連続した領域に詰めて持つ表現が、メモリでも速度（キャッシュ効率）でも有利です。

## 6. 計測する — 理論と実測をつなぐ

### 6.1 timeit で小さな処理を測る

標準ライブラリの `timeit` は、処理を何度も繰り返して時間を測ります。コマンドラインから使うのが手軽です（以下の数値はこの章の執筆環境での一例で、マシンによって変わります）。

```text
$ python3 -m timeit -s "xs = list(range(100_000)); x = 99_999" "x in xs"
500 loops, best of 5: 520 usec per loop
$ python3 -m timeit -s "xs = set(range(100_000)); x = 99_999" "x in xs"
10000000 loops, best of 5: 20.1 nsec per loop
```

10 万要素の `list` に対する `in` は約 520 µs、`set` なら約 20 ns で、2 万倍以上の差です。`list` の `in` は先頭から順に比べる O(n)、`set` の `in` はハッシュで直接探す平均 O(1) だからです。

`timeit` のドキュメントは、繰り返し計測した結果の **最小値** を見ることを勧めています。遅い回は、測りたい処理ではなく他のプロセスなどの割り込みで遅くなったものだからです。ただしこれは「その処理自体の速さ」を知りたいときの話で、本番のレイテンシのように **ばらつきそのものが問題** なら、分布（パーセンタイル）を見ます（[2.2 確率・統計と定量的思考](../02-probability-statistics/README.md)）。

### 6.2 倍増実験 — 実測から計算量を推定する

計算量が分からない処理は、入力サイズを 2 倍ずつ増やして時間の比を見ると推定できます（**倍増実験**、doubling experiment）。時間が c·nᵏ なら、n を 2 倍にすると時間は 2ᵏ 倍になるので、k ≈ log₂(時間の比) です。

```python
import math
import random
import timeit

def has_duplicates_slow(items):
    """すべての組を比べる: O(n^2)"""
    for i in range(len(items)):
        for j in range(i + 1, len(items)):
            if items[i] == items[j]:
                return True
    return False

rng = random.Random(0)
sizes = [500, 1000, 2000, 4000]
times = []
for n in sizes:
    data = rng.sample(range(10**9), n)            # 重複のないデータ = 最悪ケース
    t = min(timeit.repeat(lambda: has_duplicates_slow(data), number=1, repeat=3))
    times.append(t)
    print(f"n={n:5d}: {t * 1000:8.1f} ms")
for (n1, t1), (n2, t2) in zip(zip(sizes, times), zip(sizes[1:], times[1:])):
    print(f"n: {n1} → {n2}  時間の比 {t2 / t1:.2f}  指数の推定 log2(比) = {math.log2(t2 / t1):.2f}")
```

```text
n=  500:      3.2 ms
n= 1000:     11.8 ms
n= 2000:     46.6 ms
n= 4000:    188.1 ms
n: 500 → 1000  時間の比 3.71  指数の推定 log2(比) = 1.89
n: 1000 → 2000  時間の比 3.95  指数の推定 log2(比) = 1.98
n: 2000 → 4000  時間の比 4.04  指数の推定 log2(比) = 2.01
```

比がほぼ 4、指数がほぼ 2 で、O(n²) であることが実測からも確かめられました（時間の値は環境によって変わりますが、比はほぼ変わりません）。n が小さいうちは、ループの外の固定費や、キャッシュに収まるかどうかの影響で比がずれるので、**十分大きな n で、複数の点を使って** 推定します。演習 4 では、両対数グラフ上の最小二乗法で指数を求め、さらに O(n) と O(n log n) のような紛らわしい候補を、モデルごとの当てはまりの良さで見分ける関数を作ります。

### 6.3 プロファイラ — どこに時間を使っているか

プログラム全体が遅いとき、**推測で最適化してはいけません**。時間の大半は、ごく一部のコードで使われていることがほとんどだからです。Python 標準の **cProfile** は、関数ごとの呼び出し回数と時間を集計します。

次のプログラムは、注文データから顧客ごとの購入商品の一覧を作ります。

```python
"""report.py: 注文データから「顧客ごとの購入商品の一覧」を作る（うっかり二乗を含む）"""
import random

def load_orders(n, seed=0):
    rng = random.Random(seed)
    return [{"customer": rng.randrange(n // 10), "item": rng.randrange(1000)} for _ in range(n)]

def unique_customers(orders):
    seen = []
    for o in orders:
        if o["customer"] not in seen:      # list に対する in: O(len(seen))
            seen.append(o["customer"])
    return seen

def items_of(customer, orders):
    return sorted({o["item"] for o in orders if o["customer"] == customer})

def build_report(orders):
    return {c: items_of(c, orders) for c in unique_customers(orders)}   # 顧客ごとに全注文を走査

if __name__ == "__main__":
    build_report(load_orders(20_000))
```

`cumtime`（その関数から呼んだ関数も含む時間）を見ると、全体 1.8 秒のうち 1.6 秒が `items_of` の中の集合内包表記で使われています。2,000 人の顧客それぞれについて 2 万件の注文を全部なめる、2,000 × 20,000 = 4,000 万回のループだからです。`unique_customers` の `list` に対する `in` も二乗ですが、こちらは 0.1 秒で、先に直すべきではありません。注文を 1 回だけ走査して顧客ごとに集めれば O(n) になります。

```python
from collections import defaultdict

def build_report_fast(orders):
    items = defaultdict(set)
    for o in orders:                       # 1 回の走査で顧客ごとに集める: O(n)
        items[o["customer"]].add(o["item"])
    return {c: sorted(s) for c, s in items.items()}
```

この環境では、プロファイラなしで計測して 1,007 ms が 6.7 ms になりました（結果は同じ）。**プロファイルで最大の箇所を見つけ、計算量を下げ、また計測する** のが性能改善の基本の流れです。

### 6.4 計測の落とし穴

- **測る入力が現実的でない**: ソート済みのデータ、重複のないデータ、小さすぎるデータでは、本番とまったく違う結果になることがあります。最悪ケースと、本番に近いデータの両方で測ります。
- **ウォームアップとキャッシュ**: 初回はファイルや DB のキャッシュが冷えていて遅く、2 回目以降は速くなります。何を測りたいのか（初回か定常状態か）を決めます。
- **マイクロベンチマークの罠**: 結果を使わない計算は、コンパイラ（Python 以外の言語で）に消されることがあります。小さな処理の速さが、全体の速さに効くとは限りません。
- **ノイズ**: 同じマシンの他のプロセス、CPU の周波数の変動、GC の影響で結果は揺れます。複数回測り、差が揺れより十分大きいかを確認します。

## 7. 定数倍とキャッシュ — 同じ計算量でも速さは違う

漸近記法は定数倍を無視しますが、**実務の性能差の多くは定数倍** です。最大の要因の 1 つが、メモリのアクセスパターンとキャッシュです（[1.3 メモリ階層とキャッシュ](../../01-computer-systems/03-memory-hierarchy/README.md)）。

4096 × 4096 の整数の 2 次元配列を、行ごとと列ごとに合計する C のプログラムで比べます。どちらも同じ回数の足し算をする Θ(n²) のアルゴリズムです。

```c
/* traverse.c（抜粋）: a は N×N を 1 次元に並べた配列（行優先）。N = 4096 */
for (int i = 0; i < N; i++)            /* 行ごとに走査: メモリを連続に読む */
    for (int j = 0; j < N; j++) s1 += a[(long)i * N + j];

for (int j = 0; j < N; j++)            /* 列ごとに走査: 16KB 飛びにメモリを読む */
    for (int i = 0; i < N; i++) s2 += a[(long)i * N + j];
```

```text
$ gcc -O2 -o traverse traverse.c && ./traverse
行ごと: 0.011 秒, 列ごと: 0.182 秒 (合計 58720256, 58720256)
```

（この章の執筆環境、gcc 13.3 での一例です。）同じ計算量で **約 16 倍** の差がつきました。行ごとの走査は、キャッシュラインに読み込んだ隣の要素をすぐ使えるのに対し、列ごとの走査は毎回別のキャッシュラインを読むからです。

ほかにも、定数倍が効く例は多くあります。

- **Python のループと組み込み関数**: `sum(range(10**7))` は、同じ和を Python の `for` ループで求めるより約 3 倍速い（この環境で 0.09 秒対 0.26 秒）。組み込み関数のループは C で実行されるからです。
- **小さな n では単純なアルゴリズムが勝つ**: 挿入ソートは Θ(n²) ですが、要素が数十個以下ならマージソートより速いことが多く、Python の `sorted` が使う Timsort は、短い区間を挿入ソート（二分挿入ソート）で処理します。
- **連結リストより配列**: どちらも走査は Θ(n) ですが、ノードがメモリ上に散らばる連結リストは、ポインタをたどるたびにキャッシュミスが起きやすく、配列より何倍も遅くなりがちです（[2.4 基本データ構造](../04-basic-data-structures/README.md)）。

**計算量で候補を絞り、定数倍は計測で決める**、というのが実務での使い分けです。

## 8. うっかり二乗のパターン

**うっかり二乗（accidentally quadratic）** は、1 回あたり O(n) の操作を、気づかずに n 回繰り返してしまうパターンです。1 行ずつ見ると問題がないので、コードレビューで見逃されやすい性能バグの代表です。

| パターン | なぜ遅いか | 直し方 |
|---|---|---|
| ループの中で `list.pop(0)`・`list.insert(0, x)` | 残りの要素を全部ずらす O(n) | `collections.deque` の `popleft()`・`appendleft()`（O(1)） |
| ループの中で `x in list`・`list.index(x)`・`list.remove(x)` | 先頭から探す O(n) | 事前に `set` / `dict` を作る（平均 O(1)） |
| 重複チェックのための `if x not in result: result.append(x)` | 同上 | `set` で「見たもの」を管理する |
| 文字列やバイト列を `+=` で少しずつ連結 | 毎回全体をコピーしうる O(n) | 部品をリストにためて `"".join(...)`、または `io.StringIO` |
| ループの中で `sorted()`・`max()` | 毎回 O(n log n)・O(n) | ループの外で 1 回だけ、またはヒープ（`heapq`） |
| 2 つのリストを入れ子のループで突き合わせる | O(n·m) | 片方を `dict` にして引く（ハッシュ結合） |
| 一覧の各行について DB に問い合わせる（N+1 クエリ） | 往復遅延 × N | JOIN、`IN (...)` でまとめて取得、ORM の事前読み込み |

代表的なパターンを測ってみます（数値はこの環境での一例です）。

```python
import time
from collections import deque

def measure(func, arg):
    t0 = time.perf_counter()
    func(arg)
    return time.perf_counter() - t0

def drain_list(n):             # list.pop(0) は残りの要素を 1 つずつ前に詰める: O(n)
    q = list(range(n))
    while q:
        q.pop(0)

def drain_deque(n):            # deque.popleft() は O(1)
    q = deque(range(n))
    while q:
        q.popleft()

def common_list(n):            # ループの中で list に対する in: O(n) × n 回
    a, b = list(range(n)), list(range(n // 2, n + n // 2))
    return [x for x in a if x in b]

def common_set(n):             # set に変換してから in: O(1) × n 回
    a, b = list(range(n)), set(range(n // 2, n + n // 2))
    return [x for x in a if x in b]

for name, func, sizes in [
    ("list.pop(0)", drain_list, (25_000, 50_000, 100_000)),
    ("deque.popleft()", drain_deque, (25_000, 50_000, 100_000)),
    ("x in list", common_list, (2_500, 5_000, 10_000)),
    ("x in set", common_set, (2_500, 5_000, 10_000)),
]:
    times = [measure(func, n) for n in sizes]
    cells = "  ".join(f"n={n:>7,}: {t * 1000:8.1f} ms" for n, t in zip(sizes, times))
    print(f"{name:16} {cells}")
```

```text
list.pop(0)      n= 25,000:     55.4 ms  n= 50,000:    222.9 ms  n=100,000:    889.2 ms
deque.popleft()  n= 25,000:      1.1 ms  n= 50,000:      2.1 ms  n=100,000:      4.9 ms
x in list        n=  2,500:     19.9 ms  n=  5,000:     80.5 ms  n= 10,000:    320.1 ms
x in set         n=  2,500:      0.2 ms  n=  5,000:      0.6 ms  n= 10,000:      0.7 ms
```

二乗の側は n が 2 倍になるたびに時間が約 4 倍、直した側はほぼ 2 倍（線形）です。n = 10 万で既に 180 倍の差があり、この差は n に比例して広がり続けます。

**文字列の連結** には注意が必要です。CPython には、参照が 1 つしかない `str` への `s += t` をその場で延長する最適化があり、多くの場合は線形時間で動きます。しかしこれは CPython の実装の詳細で、同じ文字列への参照が他にあるだけで効かなくなります。

```python
import time

def concat(n, keep_alias):
    out = ""
    for _ in range(n):
        alias = out if keep_alias else None   # もう 1 つ参照があると、その場で延長できない
        out += "x" * 100
    return out

for keep_alias in (False, True):
    for n in (5_000, 10_000, 20_000):
        t0 = time.perf_counter()
        concat(n, keep_alias)
        print(f"別名あり={keep_alias!s:5}  n={n:6,}: {(time.perf_counter() - t0) * 1000:7.1f} ms")
```

```text
別名あり=False  n= 5,000:     0.7 ms
別名あり=False  n=10,000:     1.5 ms
別名あり=False  n=20,000:     3.4 ms
別名あり=True   n= 5,000:    35.7 ms
別名あり=True   n=10,000:   207.7 ms
別名あり=True   n=20,000:  1491.8 ms
```

PEP 8 も、この最適化に頼らず `"".join()` を使うよう求めています。`bytes` にはこの最適化がないので、`bytes` の `+=` によるループは常に二乗になります。

**N+1 クエリ** は、アプリケーションとデータベースの間で起きるうっかり二乗の親戚です。ORM で記事の一覧を取得し、各記事の著者名を表示すると、「一覧のクエリ 1 回 + 記事ごとの著者のクエリ N 回」が発行されることがあります。sqlite3 で、実行されたクエリの数を数えてみます。

```python
import sqlite3

con = sqlite3.connect(":memory:")
con.executescript("""
CREATE TABLE authors (id INTEGER PRIMARY KEY, name TEXT);
CREATE TABLE posts (id INTEGER PRIMARY KEY, author_id INTEGER, title TEXT);
""")
con.executemany("INSERT INTO authors VALUES (?, ?)", [(i, f"author{i}") for i in range(100)])
con.executemany("INSERT INTO posts VALUES (?, ?, ?)", [(i, i % 100, f"post{i}") for i in range(100)])

queries = []
con.set_trace_callback(queries.append)     # 実行された SQL を記録する

# N+1: 記事の一覧を 1 回で取り、著者を記事ごとに 1 回ずつ取りに行く
posts = con.execute("SELECT id, author_id, title FROM posts").fetchall()
for _, author_id, _ in posts:
    con.execute("SELECT name FROM authors WHERE id = ?", (author_id,)).fetchone()
print("N+1:", len(queries), "回のクエリ")

queries.clear()
rows = con.execute("""
    SELECT p.id, p.title, a.name FROM posts p JOIN authors a ON a.id = p.author_id
""").fetchall()
print("JOIN:", len(queries), "回のクエリ,", len(rows), "行")
```

```text
N+1: 101 回のクエリ
JOIN: 1 回のクエリ, 100 行
```

SQLite は同じプロセス内で動くので差は小さく見えますが、ネットワーク越しの DB で 1 回の往復に 1 ms かかるなら、101 回のクエリは約 100 ms、JOIN なら約 1 ms です。一覧の件数に比例して遅くなるので、ページのサイズを増やしたとたんに遅くなります（[6.2 インデックスとクエリ処理](../../06-databases/02-indexes-and-query-processing/README.md)）。

## 9. Python の組み込みデータ構造の計算量

CPython の主な操作の計算量をまとめます（Python Wiki の "TimeComplexity" ページなどにまとめられている、CPython の実装に基づく値です。言語仕様が保証するものではありません）。n はコンテナの要素数、k は引数の要素数です。

| 型 | 操作 | 計算量 |
|---|---|---|
| `list` | `a[i]`・`a[i] = x`・`len(a)`・`a.append(x)`・`a.pop()` | O(1)（append はならし） |
| | `a.pop(0)`・`a.insert(i, x)`・`del a[i]`（先頭付近） | O(n) |
| | `x in a`・`a.index(x)`・`a.remove(x)`・`min(a)`・`a.count(x)` | O(n) |
| | `a[i:j]`（スライス）・`a.extend(b)` | O(k) |
| | `a.sort()`・`sorted(a)` | O(n log n)（ほぼソート済みなら O(n) に近づく） |
| `collections.deque` | 両端の `append`・`appendleft`・`pop`・`popleft` | O(1) |
| | `d[i]`（中央付近） | O(n) |
| `dict` | `d[k]`・`d[k] = v`・`del d[k]`・`k in d` | 平均 O(1)、最悪 O(n) |
| | 走査・コピー | O(n) |
| `set` | `x in s`・`s.add(x)`・`s.discard(x)` | 平均 O(1)、最悪 O(n) |
| | `s \| t`・`s - t` | O(len(s) + len(t))・O(len(s)) |
| | `s & t` | 平均 O(min(len(s), len(t))) |
| `heapq` | `heappush`・`heappop` | O(log n) |
| | `heapify` | O(n) |
| `bisect` | `bisect_left`・`bisect_right` | O(log n) |
| | `insort`（挿入） | O(n)（探索は O(log n) でも、挿入でずらす） |

`dict` と `set` の「最悪 O(n)」は、ハッシュ値が衝突した場合です。冒頭の hash flooding は、まさにこの最悪ケースを外部から引き起こす攻撃でした。

**比較によるソートの下限**: 要素の大小比較だけで並べ替えるアルゴリズムは、最悪の場合に少なくとも log₂(n!) ≈ n log₂ n − 1.44n 回の比較が必要です。n 個の並べ方は n! 通りあり、1 回の比較で可能性を高々半分にしか絞れないからです。したがって比較ソートは Ω(n log n) より速くなれず、マージソートやヒープソートは最適です。計数ソートや基数ソートのように、比較以外の情報（値の範囲や桁）を使えばこの下限を回避できます（[2.6 アルゴリズム設計技法](../06-algorithm-design/README.md)）。

## よくある落とし穴

1. **「O(1) だから速い」「O(n log n) だから遅い」と思い込む**。O は定数倍を隠します。ハッシュの計算が重い O(1) より、キャッシュに乗る O(log n) の方が速いこともあります。候補を絞ったら計測で決めましょう。
2. **平均計算量だけを見て最悪ケースを放置する**。外部からの入力で最悪ケースを起こせるなら（ハッシュの衝突、正規表現のバックトラッキング、ソート済み入力のクイックソート）、それは攻撃面です。入力サイズの上限、タイムアウト、線形時間が保証された手法（RE2 型の正規表現エンジンなど）で守りましょう。
3. **ループの中の隠れた O(n)** を見逃す。`in list`、`pop(0)`、`insert(0, ...)`、`remove`、文字列の連結、ORM の遅延読み込みは、1 行でも O(n) です。レビューでは「このループは何回回り、その中で何回回るか」を問いましょう。
4. **小さなデータの計測から本番の性能を推測する**。二乗のアルゴリズムは、1,000 件で 0.1 秒でも 100 万件で 1 日かかります。倍増実験で増え方を確かめ、本番の最大サイズで見積もりましょう。
5. **ならし O(1) を「毎回 O(1)」と思う**。拡張や再ハッシュの瞬間は O(n) で、テールレイテンシに現れます。レイテンシが重要なら、事前に容量を確保する（`reserve`）、段階的に処理する設計を検討しましょう。
6. **空間計算量を無視する**。メモ化の表、再帰の深さ、全件をメモリに読み込む処理は、データが増えるとメモリ不足やスワップで一気に遅くなります。ストリーム処理やバッチ分割を検討しましょう。
7. **推測で最適化する**。時間の大半はごく一部で使われます。プロファイラで最大の箇所を特定してから直しましょう。逆に、計測なしの「なんとなくの高速化」で可読性を犠牲にしないことです。
8. **二分探索の境界を雑に書く**。`lo = mid`（+1 忘れ）による無限ループ、`<=` と `<` の取り違え、固定長整数での `(lo + hi) / 2` のオーバーフローは古典的なバグです。不変条件を書いてから実装しましょう。

## CTOの視点

1. **設計レビューで「n はいくつまで増えるか」を必ず問う**。計算量の問題は、データが増えてから一気に顕在化し、そのときには利用者に見える障害になっています。「今の件数、1 年後の件数、10 倍になったら何が起きるか」「このループは何件のデータを回るか」を定型の質問にしましょう。特に、ユーザー数・テナント数・履歴件数に比例して増えるデータを、アプリケーションのメモリに全件読み込む設計は要注意です。
2. **最悪計算量を可用性とセキュリティの要件として扱う**。ユーザー入力が計算量を決める箇所（検索条件、正規表現、アップロードされたファイルの解析、ハッシュテーブルのキー）を洗い出し、入力サイズの上限、タイムアウト、最悪計算量が保証された手法を要件にしましょう。Cloudflare の事例のように、1 つのルールの計算量が全サービスを止めることがあります。
3. **性能改善への投資は計測で判断する**。「遅い」という報告に対しては、まずプロファイルと計測のデータを求め、改善の効果を事前に見積もってから工数を割り当てます（全体の 5% しか占めない部分を 10 倍速くしても、全体は 5% も速くならない。[9.5 スケーラビリティとパフォーマンス](../../09-architecture/05-scalability-and-performance/README.md) のアムダールの法則）。性能のリグレッションを検出するベンチマークを CI に組み込むことも検討しましょう。
4. **ハードウェアで解決できる問題と、できない問題を区別する**。定数倍の問題はサーバーを増やせば解決できることがありますが、二乗の問題は、データが 10 倍になればサーバーが 100 倍必要です。「スケールアウトで乗り切る」判断の前に、計算量が線形か（またはそれ以下か）を確認しましょう。これはクラウドのコスト（[10.6 クラウドコスト管理（FinOps）](../../10-cloud-and-sre/06-finops/README.md)）に直結します。
5. **採用では「計算量を道具として使えるか」を見る**。アルゴリズムの暗記問題より、「このコードは 100 万件で何秒かかりそうか」「どこがボトルネックで、どう直すか」「どう計測して確かめるか」を議論させる方が、実務の能力をよく測れます。

### 演習 6（記述）: 夜間バッチの計算量レビュー

あるサービスの夜間バッチが、年々遅くなって朝までに終わらなくなってきました。処理の中心は次のコードです。現在、キャンペーン C = 50 件、ユーザー U = 200 万人、購入履歴 P = 3,000 万件で、いずれも毎年 2 倍程度に増えています。

```python
def nightly_campaign_targets(campaigns, users, purchases):
    """各キャンペーンについて、その対象商品を過去に購入したユーザーを列挙する"""
    results = []
    for c in campaigns:
        for u in users:
            bought = [p for p in purchases if p.user_id == u.id]
            if c.product_id in [p.product_id for p in bought]:
                results.append((c.id, u.id))
    return results
```

1. このコードの時間計算量を C, U, P で表し、現在の規模で CPython がおよそ 1 秒に 10⁷ 回の基本操作をこなすとして、実行時間を桁で見積もってください。
2. 計算量を下げた書き直しを示し、その計算量を答えてください。
3. コードの書き直し以外に、設計レビューで確認・提案すべきことを挙げてください。

<details>
<summary>解答例</summary>

**1. 計算量と見積もり**

キャンペーンごと・ユーザーごとに購入履歴を全件走査するので、Θ(C·U·P) です。現在の規模では 50 × (2 × 10⁶) × (3 × 10⁷) = 3 × 10¹⁵ 回の操作で、10⁷ 回/秒なら 3 × 10⁸ 秒、つまり **約 10 年** かかります（実際にはもっと小さい規模のときに書かれ、規模の増加とともに破綻したと考えられます）。さらに、C・U・P がそれぞれ毎年 2 倍になると、実行時間は毎年 8 倍になります。

**2. 書き直し**

購入履歴を 1 回だけ走査して「商品 → 購入したユーザーの集合」の索引を作り、キャンペーンごとに引きます。

```python
from collections import defaultdict

def nightly_campaign_targets(campaigns, users, purchases):
    buyers = defaultdict(set)                  # 商品 ID → 購入したユーザー ID の集合: O(P)
    for p in purchases:
        buyers[p.product_id].add(p.user_id)
    active = {u.id for u in users}             # 対象ユーザーの集合: O(U)
    return [(c.id, uid)                        # O(C + 出力の大きさ)
            for c in campaigns
            for uid in buyers.get(c.product_id, ()) if uid in active]
```

計算量は Θ(P + U + C + 出力件数) の線形で、3,000 万件の走査なら数十秒程度の見込みです（結果の順序が元のコードと変わる点は、仕様として問題ないか確認します）。

**3. 確認・提案すべきこと**

- **データベースに任せる**: 購入履歴が DB にあるなら、全件をアプリケーションに読み込むより、`JOIN`（DB のハッシュ結合など）と適切なインデックスで DB 側で計算する方が、メモリも転送量も小さくて済みます。
- **メモリ**: 3,000 万件の購入履歴を Python のオブジェクトとして全件読み込むと、数 GB のメモリを使う可能性があります。必要な列だけを読む、ストリームで処理する、を検討します。
- **差分処理**: 毎晩全期間を計算し直す必要があるか。前回からの新しい購入だけを反映する増分処理にすれば、処理量は増え方そのものが変わります。
- **規模の前提を文書化し、監視する**: バッチの実行時間と入力件数を毎日記録し、増え方（線形か超線形か）を監視して、締め切りに間に合わなくなる時期を事前に予測できるようにします。

採点の観点:

- Θ(C·U·P) と「年単位」の桁の見積もりができ、索引（dict / set）を使った線形の書き直しが示せていれば合格です。
- データの増加率から実行時間の増え方（毎年 8 倍）を導けているか、DB・メモリ・増分処理・監視まで視野に入っているかで、設計レビューをリードできる水準かを判断します。

</details>

## 理解度チェック

**Q1. f(n) = 5n log₂ n + 20n が O(n²) であることは正しいですか。Θ(n log n) であることはどうですか。「f(n) = O(n²) だから遅いアルゴリズムだ」という主張の問題点も説明してください。**

<details>
<summary>解答</summary>

どちらも正しい主張です。n ≥ 1 で log₂ n ≤ n なので、5n log₂ n + 20n ≤ 25n² となり O(n²) です。また、n ≥ 2 では 5n log₂ n ≤ f(n) ≤ 25n log₂ n（20n ≤ 20n log₂ n より）なので Θ(n log n) です。

O は上界を表すだけなので、「O(n²)」は「n² より速く増えることはない」としか言っていません。実際の増え方は n log n で、O(n²) という表現は正しいが情報の少ない上界です。遅いかどうかを議論するには、Θ で正確な増え方を示すか、最悪ケースの下界（Ω）を示す必要があります。

</details>

**Q2. 次のコードの時間計算量を答えてください。**

```python
def f(n):
    total = 0
    i = n
    while i > 0:
        for j in range(i):
            total += 1
        i //= 2
    return total
```

<details>
<summary>解答</summary>

**Θ(n)** です。内側のループは i 回回り、i は n, n/2, n/4, … と半分になるので、合計は n + n/2 + n/4 + … < 2n です。外側のループが log n 回あるからといって Θ(n log n) にはなりません。内側の回数が毎回半分になる等比数列の和なので、最初の項が支配的になります（マスター定理の場合 3 と同じ構造）。

</details>

**Q3. 漸化式 T(n) = 4T(n/2) + n² と T(n) = 8T(n/2) + n² を、マスター定理で解いてください。**

<details>
<summary>解答</summary>

- T(n) = 4T(n/2) + n²: a = 4、b = 2、d = 2 で、bᵈ = 4 = a なので場合 2。**Θ(n² log n)** です。
- T(n) = 8T(n/2) + n²: a = 8 > bᵈ = 4 なので場合 1。**Θ(n^log₂8) = Θ(n³)** です（素朴な分割統治による行列の積がこの形で、7 回の掛け算で済ませるシュトラッセン法は Θ(n^2.807)）。

</details>

**Q4. 動的配列の容量を「足りなくなったら 2 倍」ではなく「足りなくなったら 1,000 要素分だけ増やす」にすると、n 回の append の合計コストはどうなりますか。**

<details>
<summary>解答</summary>

拡張は 1,000 回の append ごとに起き、k 回目の拡張では約 1,000k 個の要素をコピーします。n 回の append で拡張は n/1,000 回起きるので、コピーの合計は 1,000 × (1 + 2 + … + n/1,000) ≈ n²/2,000 で、**Θ(n²)** です（4.1 節の計測では、100 万回の append で約 5 億回のコピー）。1 回あたりのならしコストは Θ(n) になり、O(1) ではなくなります。定数倍（幾何級数的）に広げることが、ならし O(1) の条件です。

</details>

**Q5. 「ならし O(1)」と「平均 O(1)」の違いを説明してください。ハッシュテーブルの検索と、動的配列の append は、それぞれどちらですか。**

<details>
<summary>解答</summary>

ならし解析は、**どんな操作列に対しても** 合計コストを操作回数で割った値が抑えられるという、確率を使わない最悪の保証です。平均計算量は、入力やハッシュ関数などの **確率的な分布を仮定した期待値** で、運が悪い（または攻撃者が選んだ）入力では悪化しえます。

動的配列の append は **ならし O(1)** です（個々の append は最悪 O(n) だが、n 回の合計は必ず O(n)）。ハッシュテーブルの検索は **平均 O(1)** で、全キーが衝突すれば O(n) になります（hash flooding）。なお、ハッシュテーブルへの挿入は、拡張のコストについてはならし解析、衝突については平均の議論が必要で、両方が組み合わさっています。

</details>

**Q6. ある API のレスポンスが、ページあたりの件数を 20 件から 100 件に増やしたら 5 倍どころか 25 倍遅くなりました。どのような原因が考えられ、どう調査しますか。**

<details>
<summary>解答</summary>

件数が 5 倍で時間が 25 倍なので、件数に対して二乗で増える処理（うっかり二乗）が疑われます。例えば、各項目について全項目を走査する処理（`in list` やリストの突き合わせ）、項目ごとに関連データを取り直す処理が項目数に比例するデータを返すもの、などです。単純な N+1 クエリなら時間は件数に比例（5 倍程度）するはずなので、N+1 に加えて各クエリの結果も件数に比例して大きくなっている、などの組み合わせも考えられます。

調査は、20・40・80・100 件のように件数を変えて倍増実験を行い、時間の増え方（指数）を確認したうえで、プロファイラ（cProfile など）や DB のクエリログ・APM のトレースで、時間の大半を使っている箇所と発行されているクエリの数を特定します。

</details>

**Q7. 二分探索のループで、範囲の更新を `lo = mid`（+1 なし）と書くと、何が起きる可能性がありますか。ループ不変条件と変量の観点から説明してください。**

<details>
<summary>解答</summary>

hi − lo = 1 のとき mid = (lo + hi) // 2 = lo なので、`lo = mid` では lo が変わらず、範囲が狭まりません。変量 hi − lo が減らないので、停止性の議論が破綻し、**無限ループ** になります。

`a[mid] < x` のとき、mid 自身も答えの候補から外れる（不変条件「a[:lo] はすべて x 未満」は lo = mid + 1 でも保たれる）ので、`lo = mid + 1` と書くのが正しく、これで変量は毎回必ず減ります。「どちらの更新でも不変条件が保たれ、かつ変量が必ず減る」ことを確かめるのが、二分探索を正しく書くコツです。

</details>

**Q8. 同じ Θ(n²) の処理なのに、2 次元配列を行ごとに走査すると列ごとより 16 倍速かったのはなぜですか。計算量の議論はこの差を説明できますか。**

<details>
<summary>解答</summary>

メモリはキャッシュライン（多くの CPU で 64 バイト）単位で読み込まれ、行優先で並んだ配列を行ごとに走査すると、1 回読み込んだキャッシュラインの残りの要素をすぐ使えます。列ごとの走査では、毎回 16 KB（4096 要素 × 4 バイト）離れた位置を読むため、ほぼ毎回キャッシュミスが起き、メインメモリへのアクセスを待つことになります。

計算量（RAM モデル）は「基本操作 1 回のコストは一定」と仮定するので、この差は説明できません。計算量はアルゴリズムの増え方を比べる道具で、メモリ階層による定数倍の差は、[1.3 メモリ階層とキャッシュ](../../01-computer-systems/03-memory-hierarchy/README.md) の知識と計測で扱います。

</details>

## まとめ

- アルゴリズムの正しさは **ループ不変条件（初期化・維持・終了）と変量（停止性）** で示す。二分探索は半開区間と不変条件で書く。
- 計算量は基本操作の回数の **増え方** で比べる。O は上界、Ω は下界、Θ は同じ増え方。O は「最悪計算量」の意味ではない。
- 入力が攻撃者に選ばれうるなら **最悪計算量** を重視する（hash flooding、正規表現のバックトラッキング）。
- 1 秒で扱える n は、O(n²) で数千〜数万、O(2ⁿ) で数十。**10 倍のデータで 100 倍遅くなる処理** を本番に出さない。
- 分割統治の漸化式は、再帰木と **マスター定理**（a と bᵈ の比較）で解ける。部分問題を 1 つ減らすだけで指数が変わる（カラツバ法）。
- 動的配列は **定数倍で広げればならし O(1)**、縮小は 1/4 で半分にして振動を防ぐ。ならしは最悪の保証だが、個々の操作はたまに遅い。
- 性能は **計測してから直す**。timeit・倍増実験・cProfile で理論と実測をつなぎ、定数倍（キャッシュ・組み込み関数）は計測で判断する。
- **うっかり二乗**（`pop(0)`、ループ内の `in list`、連結、N+1 クエリ）は、`deque`・`set`/`dict`・`join`・JOIN で線形に直せる。
