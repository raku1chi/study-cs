# 14.9 CTOの自己管理とキャリア

> CTO は、会社の技術に最終的な責任を負いながら、社内に同じ立場の相談相手がいない役割です。長く良い仕事を続けるには、システムや組織と同じように、自分自身の時間・エネルギー・判断力・学び・キャリアを意図的に設計する必要があります。この章では、支援のネットワーク、時間の使い方、技術力の保ち方、意思決定の疲労と燃え尽きへの備え、自己認識、次のキャリアと後継者計画、倫理と責任、そして個人の学習計画を扱います。

## なぜ学ぶのか

CTO の仕事の成果は、判断の質で決まります。そして判断の質は、疲労、孤立、偏った情報、古くなった知識によって、本人が気づかないうちに落ちていきます。

- **構造的な孤独**: 部下には弱みを見せにくく、CEO は上司であり同僚でもあり、M&A や組織の再編のように誰にも話せない情報を抱えます。社内に、同じ責任を負う相談相手はいません。
- **燃え尽きは個人の弱さではない**: 世界保健機関（WHO）は 2019 年、国際疾病分類の第 11 版（ICD-11）で燃え尽き（burn-out）を「うまく管理されなかった慢性的な職場のストレスから生じる」職業上の現象と位置づけ、①エネルギーの枯渇や消耗感、②仕事からの心理的な距離の増大（否定的・冷笑的な感情）、③職業上の効力感の低下、の 3 つの次元で特徴づけました。原因は個人の気合ではなく、仕事の構造にあるということです。
- **法律が守ってくれない立場**: 取締役などの役員の CTO は、一般に労働基準法上の労働者には当たらないため、労働時間の上限規制などの保護の外にいます。自分の働き方の上限は、自分で決めて守るしかありません（執行役員など、雇用契約のもとで働く場合は扱いが異なります）。
- **役割が変わる**: [14.1 CTOの役割](../01-role-of-cto/README.md) で見たように、会社の成長につれて CTO に求められることは変わります。10 人の会社で最適だった CTO が、300 人の会社でも最適とは限りません。キャリアを意識的に設計しなければ、役割と自分のずれに苦しむことになります。

この章は、ここまでの章のように「会社の仕組み」を扱うのではなく、その仕組みを動かす **自分自身の仕組み** を扱います。

## 1. 孤独と支援のネットワーク

### 1.1 なぜ CTO は孤独なのか

| 構造 | 何が起きるか |
|---|---|
| 同じ立場の人が社内にいない | 判断の相談相手がいない。自分の判断が偏っていても気づけない |
| 弱みを見せにくい | 部下の不安を招くことを恐れ、迷いを一人で抱える |
| 話せない情報がある | 資金調達、M&A、組織の再編、人事の問題を誰とも共有できない |
| 評価が遅く曖昧 | 技術の判断の結果が出るのは数か月〜数年後。うまくいっているのか分からない |

孤独そのものは避けられません。大切なのは、**社外に、目的の違う複数の支えを持つ** ことです。

### 1.2 支援の種類と使い分け

| 種類 | してくれること | 見つけ方 | 注意点 |
|---|---|---|---|
| ピア（他社の CTO や VPoE） | 同じ悩みの共有、他社の実例 | コミュニティ、勉強会、紹介 | 守秘を守る。社名や個人を特定できる話はしない |
| メンター | 経験に基づく助言、キャリアの相談 | 数年先を歩む人に、具体的な問いを持って依頼する | 相手の時間を尊重し、相談の目的を明確にする |
| エグゼクティブ・コーチ | 問いを通じて考えと行動を整理し、行動の変化を支える | 専門のコーチ（会社の費用で契約する例もある） | 助言者ではない。相性が重要 |
| アドバイザー・社外取締役 | 取締役会や投資家との関係、ガバナンスの助言 | 投資家や取締役会の紹介 | 利害関係を意識する |
| 専門家 | 法務・会計・心身の健康の専門的な判断 | 会社の契約先、産業医、従業員支援プログラム（EAP）、医療機関 | 困ってからではなく、早めに相談する |
| 家族・友人 | 仕事の外での支え | — | 仕事の外の関係を犠牲にしない |

日本では、2019 年に設立された一般社団法人日本 CTO 協会のように、技術の経営者が集まるコミュニティがあります（同協会は 2019 年に、企業の DX の自己診断の基準「DX Criteria」を公開しています）。ほかにも CTO や VPoE、エンジニアリングマネージャーが集まる勉強会は数多くあります。まずは参加して、話せる相手を 2〜3 人見つけることから始めましょう。

### 1.3 「自分の取締役会」を持つ

目的の違う 4〜6 人を選び、自分の **パーソナル・ボード**（個人の取締役会）と考えて、四半期に 1 回程度、個別に話す時間を取ります。例えば、ピアの CTO 2 人、メンター 1 人、コーチ 1 人、技術の相談相手 1 人です。重要なのは、**危機のときではなく平時に関係を作っておく** ことです。重大な障害や組織の危機の最中に、初めて相談相手を探しても間に合いません。演習 4 で、自分の支援のネットワークの地図を描きます。

## 2. 時間の使い方

### 2.1 メイカーとマネージャーのスケジュール

Paul Graham は 2009 年のエッセイ "Maker's Schedule, Manager's Schedule" で、2 種類の時間の使い方を区別しました。マネージャーのスケジュールは 1 日を 1 時間単位に区切り、予定を入れていきます。一方、プログラマーや作家のような「作る人（メイカー）」は、少なくとも半日単位のまとまった時間を必要とします。**1 つの会議が午後全体を台無しにする** ことがあるのは、午後が 2 つに分断され、どちらも難しいことをするには短すぎる時間になるからです。

CTO は、両方のスケジュールを抱えています。会議の多い日々の中で、考える時間・設計を読む時間・技術を試す時間を守るには、仕組みが要ります。

- **考える時間を先に予約する**: 例えば週に 2 回、午前中を会議禁止にしてカレンダーで押さえる
- **会議をまとめる**: Graham は、出資先の創業者と会う時間を、作業日の終わりのまとまった枠に集める方法を紹介しています。1on1 や相談を特定の曜日や時間帯に寄せると、残りの時間がまとまって空きます
- **チームのメイカーの時間も守る**: CTO が思いつきでエンジニアを会議に呼ぶことは、エンジニアの半日を奪うことがある

### 2.2 カレンダー監査

自分が何に時間を使っているかは、思っているより分かっていないものです。2〜4 週間分のカレンダーを書き出し、予定ごとにカテゴリを付けて集計し、「こうありたい」という配分と比べます。

[14.1](../01-role-of-cto/README.md) の演習 3 では、同じような記録を CTO の責務の分類（14.1 の 3.8 節）で集計し、今のステージに合った責務に時間を使えているかを確かめました。この節では、分類を時間の使い方に合わせて細かくし（考える時間、割り込み、雑務など）、時間を取り戻すための仕組みを考えます。

```python
import csv
import io
from collections import defaultdict

# カレンダーから 2 週間分の予定を書き出し、予定ごとにカテゴリを付けた CSV（例）
data = """category,hours
経営会議・社内調整,14.0
1on1・育成,11.0
採用,9.5
顧客・営業支援,6.0
障害・割り込み,5.0
雑務・移動,5.0
技術（設計レビュー・コード）,4.5
投資家・取締役会,3.0
戦略・考える時間,2.0
"""
# 自分で決めた目標の配分（%。例であり、会社のステージによって変わる）
target = {"戦略・考える時間": 15, "技術（設計レビュー・コード）": 15, "採用": 15, "1on1・育成": 15,
          "経営会議・社内調整": 15, "顧客・営業支援": 10, "投資家・取締役会": 5, "障害・割り込み": 5, "雑務・移動": 5}

hours = defaultdict(float)
for row in csv.DictReader(io.StringIO(data)):
    hours[row["category"]] += float(row["hours"])
total = sum(hours.values())
print(f"合計 {total:.1f} 時間（2 週間）")
for cat, h in sorted(hours.items(), key=lambda kv: -kv[1]):
    actual = 100 * h / total
    gap = actual - target[cat]
    mark = "▲多い" if gap > 5 else "▼少ない" if gap < -5 else ""
    print(f"{actual:5.1f}%（目標 {target[cat]:2d}%）{mark:4s} {cat}")
```

```text
合計 60.0 時間（2 週間）
 23.3%（目標 15%）▲多い  経営会議・社内調整
 18.3%（目標 15%）     1on1・育成
 15.8%（目標 15%）     採用
 10.0%（目標 10%）     顧客・営業支援
  8.3%（目標  5%）     障害・割り込み
  8.3%（目標  5%）     雑務・移動
  7.5%（目標 15%）▼少ない 技術（設計レビュー・コード）
  5.0%（目標  5%）     投資家・取締役会
  3.3%（目標 15%）▼少ない 戦略・考える時間
```

この例では、社内調整の会議が膨らみ、考える時間と技術に触れる時間が押しつぶされています。よくある姿です。集計したら、次の問いで予定を 1 つずつ見直します。

- この会議で、自分がいなければ決まらないことはあったか（なければ、議事録を読むだけにする、または代理を立てる）
- 定例の会議は、毎回何かを決めているか（決めていないなら、非同期の報告に置き換える）
- 自分の代わりにやることで、誰かが成長できる仕事はないか（2.3 節）
- 目標の配分自体は、今の会社のステージに合っているか（[14.1](../01-role-of-cto/README.md)）

演習 3 で、自分のカレンダーを実際に監査します。

### 2.3 委任

CTO の時間の問題の多くは、委任の問題です。Andy Grove は『HIGH OUTPUT MANAGEMENT』で、部下の **タスク習熟度**（その仕事に対する経験と成熟度）に応じて関わり方を変えるべきだと述べています。習熟度が低ければ具体的に指示し、中程度なら対話と支援を重ね、高ければ目標を合意して結果を確認するだけにします。委任とは「丸投げ」でも「全部を見張る」ことでもなく、**相手の習熟度に合った関わり方を選ぶ** ことです。

委任の度合いを、段階として明示するのも有効です。

| 段階 | 意味 | 例 |
|---|---|---|
| 1. 私が決めて伝える | 決定済みのことを伝える | 全社のセキュリティ方針 |
| 2. 意見を聞いてから私が決める | 相談は受けるが決定は CTO | 来期の技術予算の配分 |
| 3. 一緒に決める | 合意で決める | 組織の再編の方針 |
| 4. あなたが決めて、私に知らせる | 決定は委任し、結果を共有してもらう | チームの技術スタックの選定 |
| 5. あなたが決める | 報告も不要 | チーム内の開発プロセス |

（Jurgen Appelo が Management 3.0 で示した「委任の 7 段階」を、ここでは 5 段階に簡略化しています。）

自分がボトルネックになっている決定を洗い出しましょう。「すべての採用の最終面接」「すべての設計の承認」「本番環境への特権アクセスの承認」などを自分が握っているなら、基準を文書にして、段階 4 か 5 に移せないかを検討します。

### 2.4 断る

時間は増やせないので、何かを引き受けるたびに何かを断っています。断るかどうかは、次の問いで判断します。

- 今期の自分の最重要事項（3 つまで）に貢献するか
- 自分でなければできないことか。自分より適任の人、それで成長できる人はいないか
- 自分が出席しないと、決まらないことがあるか

断るときは、理由と代わりの案を添えると角が立ちません。「今期は採用基盤の立て直しに集中するため、今回の登壇は見送ります。技術的な内容なら、○○さんが適任だと思います。」

### 2.5 エネルギーの管理

時間と同じくらい大切なのが、エネルギーです。同じ 1 時間でも、疲れ切った夜の 1 時間と、よく眠った朝の 1 時間では、判断の質がまったく違います（睡眠不足が判断力に与える影響は [14.6 危機管理](../06-crisis-management/README.md) の 6.5 節を参照）。

- 重い判断や考える仕事は、自分の調子が最も良い時間帯に置く
- 会議を連続させず、間に 5〜10 分の余白を置く
- 睡眠・運動・食事を「空いた時間にやること」ではなく、予定として扱う
- 休暇を実際に取る。休暇中に連絡が来ないチームを作ることは、それ自体が組織の強さの証明になる

## 3. 技術力と学びを保つ

### 3.1 CTO に必要な「技術力」とは

CTO に求められる技術力は、コードを書く速さではありません。**設計の良し悪しを見分け、正しい問いを立て、もっともらしい誤りに気づき、技術の選択のコストとリスクを見積もる判断力** です。この判断力は、現場の実態に触れ続けないと、少しずつ現実からずれていきます。

避けるべき両極端があります。

- **完全に離れる**: 10 年前の知識と経験で判断し、現場から「分かっていない」と見なされる
- **コードを書き続けて、重要な作業の流れ（クリティカルパス）に入る**: CTO のレビュー待ちや実装待ちで、チームが止まる。会議が多い CTO の書くコードは、たいてい遅れる

### 3.2 技術に触れ続ける習慣

| 習慣 | 頻度の例 | 目的 |
|---|---|---|
| 重要な設計文書と、主要なプルリクエストを読む | 週 1〜2 時間 | システムの実態と、チームの判断の質を知る |
| 重要な設計レビューに参加する（すべてではない） | 月に数回 | 大きな判断の質を担保する |
| 捨てる前提のプロトタイプを作る | 月に 1 日 | 新しい技術を自分の手で評価する |
| 論文や技術文書を原典で読む | 週 1 本 | 流行の要約ではなく、元の主張と限界を知る |
| ポストモーテムを読み、ときにオンコールを見学する | 毎回・四半期に 1 回 | 本番の現実を知る |
| 社外で話す・書く | 四半期に 1 回 | 教えることで理解を深め、採用にもつなげる |

原則は、**自分をクリティカルパスに置かないこと** です。プロトタイプは捨てる前提で作り、学んだことは文書にしてチームに共有します。

### 3.3 技術の流行を批判的に評価する

新しい技術が話題になったとき、CTO が投げるべき問いは次のとおりです。

1. **どんな問題を、誰のために解くのか**。自社はその問題を持っているか
2. **証拠は何か**。自社と同じ規模・条件で、本番で使われた実績はあるか。デモやベンチマークだけではないか
3. **コストは何か**。運用の負担、必要なスキル、ロックイン、移行の費用
4. **やめるときの道はあるか**。後戻りできない判断（一方通行のドア）か
5. **待つとどうなるか**。1 年待って困ることは何か。成熟を待つ方が安くならないか

技術を「採用する・試す・評価する・保留する」の段階で整理した、社内の技術レーダーを作っておくと、流行の議論が組織の判断に変わります（[14.2 技術戦略の立て方](../02-technology-strategy/README.md)）。

### 3.5 年間の学習計画

CTO の学びは、時間があるときに自然に起きるものではありません。予算と時間を確保した、年間の計画として扱います。

| 原則 | 内容 |
|---|---|
| テーマを絞る | 1 年に 3〜4 テーマ。会社の今後 12 か月の課題と、自分の長期のキャリアの両方から選ぶ |
| 入力と出力を組み合わせる | 読む・受講する（入力）だけでなく、作る・書く・教える（出力）を必ず含める |
| 時間を先に予約する | 例えば毎週 4 時間を学習の枠としてカレンダーに入れる |
| 誰かと約束する | ピアやコーチと目標を共有し、四半期ごとに振り返る |
| 成果で測る | 読んだ冊数ではなく、作ったプロトタイプ、書いた文書、変えた判断で測る |

このカリキュラムは、学習計画の材料として使えます。四半期ごとにテーマを決め、関係する部の章を読み返し、演習を解き直し、学んだことを社内に還元します。演習 2 で、自分の年間の計画を作ります。

## 4. 意思決定の疲労

### 4.1 研究の知見と、その限界

「判断を重ねるほど判断の質が落ちる」という **意思決定の疲労** は、よく語られる概念です。有名な例として、Danziger らが 2011 年に PNAS に発表した、イスラエルの仮釈放の審査の研究があります。審査の各セッションの最初には約 65% だった仮釈放を認める判断の割合が、セッションの終わりにはほぼ 0% まで下がり、食事の休憩の後に再び約 65% に戻っていたと報告されました。

ただし、この研究には批判があります。審理の順番が無作為ではなかった（同じ刑務所の案件をまとめて審理し、各セッションの中では弁護人のいない受刑者が最後に回ることが多かった、など）という指摘（Weinshall-Margel と Shapard、2011 年）や、許可の判断の方が時間がかかるために休憩の直前に長い案件を始めないという時間の管理だけで、同じような形のデータが生じうるというシミュレーションによる指摘（Glöckner、2016 年）です。また、「意志の力は使うと減る」という自我消耗（ego depletion）の効果について、23 の研究室による事前登録の追試（Hagger ら、2016 年）では、効果の大きさはほぼゼロでした。

つまり、「判断の回数そのものが脳の資源を減らす」という強い主張は、確かな科学的事実とは言えません。一方で、疲労・睡眠不足・空腹・時間の切迫が判断の質を下げうることは、多くの人が経験から知っています。CTO としては、**研究の強い主張に頼らず、判断の負荷を下げる仕組みを作る** のが賢明です。

### 4.2 判断の負荷を下げる仕組み

- **判断を方針に変える**: 同じ種類の判断を何度もしているなら、基準を文書にして、繰り返しの判断を不要にする（例: 「この条件を満たす技術はチームで選んでよい」）
- **判断の種類を見分ける**: Jeff Bezos は 2015 年の株主への手紙で、後戻りできない「タイプ 1」の決定（一方通行のドア）と、後戻りできる「タイプ 2」の決定（両方向のドア）を区別し、タイプ 2 は判断力のある個人や小さなグループが素早く決めるべきだと述べています。CTO が慎重に考えるのはタイプ 1 だけでよく、タイプ 2 は委任します
- **重い判断の時間を選ぶ**: 後戻りできない判断は、よく休んだ状態で行う。深夜の障害対応の最中に、必要のない大きな決定をしない
- **判断を記録して振り返る**: 決定の内容、期待した結果、理由、確信度を記録し、数か月後に結果と照らし合わせる。自分の判断の癖（楽観的すぎる、など）が見えてくる。組織の技術的な判断は ADR として残す（[13.2 技術的意思決定と設計レビュー](../../13-technical-leadership/02-technical-decisions/README.md)）

## 5. メンタルヘルスと燃え尽きの予防

### 5.1 燃え尽きの兆候

WHO の定義にある 3 つの次元（消耗感、仕事への否定的な感情、効力感の低下）は、日常の兆候としては次のように現れます。自分について、ときどき点検しましょう。

- 休んでも疲れが取れない。眠れない、または眠りすぎる
- チームや顧客に対して、冷笑的な気持ちや苛立ちが増えた
- 以前は楽しかった仕事や趣味に、喜びを感じなくなった
- 判断を先延ばしにする。小さなことが決められない
- 「すべてが緊急」に感じられ、休暇を取れない
- 飲酒の量が増えた、体の不調が続く

WHO は燃え尽きを病気ではなく職業上の現象として分類していますが、兆候が続くときや、気分の落ち込みが強いときは、うつ病など治療が必要な状態との区別も含めて、医療機関に相談してください。**専門家に早く相談することは、弱さではなく判断力の表れ** です。

### 5.2 予防のための仕組み

| 層 | 取り組み |
|---|---|
| 仕組み | 持続可能な仕事のペース。委任。自分がいなくても回る体制（後継者と代行者。8 節）。2 週間、連絡なしで休暇を取れるかが実際の試金石 |
| 個人 | 睡眠、運動、仕事の外の人間関係と趣味。仕事の連絡を見ない時間を決める |
| 専門家 | 産業医、従業員支援プログラム（EAP）、医療機関、カウンセラー、コーチ |

日本では、常時 50 人以上の労働者を使用する事業場に、産業医の選任とストレスチェックの実施が義務づけられています（2025 年の法改正で、ストレスチェックの義務は 50 人未満の事業場にも広がり、2028 年 4 月に施行される予定とされます）。ただし、これらは主に労働者を守るための仕組みです。役員の CTO は対象外になりうるので、会社として役員の健康を支える仕組み（役員も使える EAP、定期的な健康診断、休暇の取得の奨励）を整えることも CTO の仕事の一部です。

### 5.3 リーダーの振る舞いは伝染する

CTO が深夜 2 時にメッセージを送れば、受け取ったエンジニアは「すぐ返すべきか」と悩みます。CTO が休暇を取らなければ、チームも休みにくくなります。

- 夜間や休日のメッセージは、送信予約を使って業務時間に届くようにする
- 休暇を取り、そのことを公にする。休暇中は本当に連絡しない
- メンタルヘルスについて、リーダー自身が普通の話題として話す
- オンコールの負荷を指標として追い、特定の人に偏らないようにする（[10.5](../../10-cloud-and-sre/05-incident-management/README.md)、[13.3](../../13-technical-leadership/03-engineering-management/README.md)）

### 5.4 危機の後の自分の回復

重大な障害、組織の縮小、キーパーソンの退職のような出来事の後、CTO はチームの回復を支えることに集中しがちで、自分の回復を後回しにします。危機の後にはまとまった休息を取り、支援のネットワーク（1 節）で出来事を言葉にする時間を持ちましょう。感情を整理しないまま次の危機を迎えると、判断が硬直します。

## 6. 自己認識

### 6.1 強みと盲点

心理学者の Luft と Ingham が 1955 年に示した「ジョハリの窓」は、自分についての情報を、自分が知っているか・他者が知っているかの 2 軸で 4 つに分けます。

| | 自分が知っている | 自分は知らない |
|---|---|---|
| **他者が知っている** | 開放の窓 | **盲点の窓** |
| **他者は知らない** | 秘密の窓 | 未知の窓 |

立場が上がるほど、周囲は率直なフィードバックをしなくなり、**盲点の窓は大きくなります**。CTO の言葉は、本人が思う以上に重く受け取られ、何気ない一言が「CTO がそう言った」として組織に広まります。盲点を小さくするには、意図的にフィードバックを求める仕組みが必要です。

### 6.2 360 度フィードバック

| 手順 | 内容 |
|---|---|
| 回答者を選ぶ | CEO、他の役員、直属の部下、その下のメンバー、主要な協力者から 8〜12 名 |
| 匿名性を確保する | 第三者（コーチ、人事、外部のサービス）を通して集める |
| 問いを行動に絞る | 「続けてほしいこと」「やめてほしいこと」「始めてほしいこと」と、具体的な場面 |
| 傾向を読む | 1 人の極端な意見より、複数の人に共通する指摘に注目する |
| 結果を共有する | 学んだことと、これから変えることを、チームに自分の言葉で伝える |
| 繰り返す | 年に 1 回程度。変化を確かめる |

最後の「結果を共有する」ことは勇気が要りますが、効果が大きい手順です。リーダーが自分の弱点を認めて改善を約束すると、チームにとって「フィードバックしてよい」という強い合図になります。

市販の性格診断や強みの診断ツールは、自分を言葉にするきっかけとしては役立ちますが、科学的な妥当性には差があるので、採用や評価の判断には使わず、対話の出発点にとどめましょう。

### 6.3 自分の取扱説明書

**自分の取扱説明書**（パーソナル・オペレーティング・マニュアル、「README for me」とも呼ばれる）は、自分の働き方、コミュニケーションの好み、大切にしていること、苦手なこと、既知の盲点、フィードバックのもらい方を書いた短い文書です。新しいチームに加わるときや、新しい部下を迎えるときに共有すると、互いを理解する時間を短縮できます。

注意点は、これを「私はこういう人間なので、合わせてください」という宣言にしないことです。取扱説明書は、**互いに合わせるための出発点** であり、フィードバックを受けて更新していく文書です。演習 1 で書きます。

### 7.1 CTO の次の選択肢

| 選択肢 | 内容 | 活きる経験 | 新たに必要になるもの | 試し方 |
|---|---|---|---|---|
| 連続して CTO を務める | 別の会社で再び CTO になる | 組織の立ち上げ、技術戦略 | 新しい事業領域の知識 | 技術顧問として関わってから |
| CEO・起業 | 事業全体の責任を負う | 技術、組織、プロダクト | 営業、資金調達、財務 | 事業部門の責任者を経験する |

個人の貢献者に戻ることは、失敗ではありません。マネジメントと技術の間を行き来できる人は、どちらの役割でも強くなります（[13.1 テックリードとStaffエンジニア](../../13-technical-leadership/01-tech-lead-and-staff/README.md)）。

日本では、複数の会社の技術顧問を務める働き方も広く見られます。副業として行う場合は、本業の就業規則や役員としての義務（競業や利益相反）との関係を確認しましょう。

## 8. 後継者計画と「会社が別のCTOを必要とするとき」

### 8.1 会社のステージと、必要な CTO

会社の成長に伴い、CTO に求められる中心的な仕事は変わります（[14.1](../01-role-of-cto/README.md)）。自分で作る段階、組織を作って拡大する段階、上場に向けて統制と信頼性を整える段階、大組織を率いる段階。すべての段階で最適な人は多くありません。

会社が別の種類の CTO を必要としている兆候は、次のようなものです。

- 取締役会や CEO から求められることに、自分が興味を持てない、または力を発揮できない
- 組織の規模が、自分のマネジメントの力量を超えている
- 自分が避けている仕事がある（採用、予算、取締役会への説明など）
- 優秀なメンバーが、リーダーシップを理由に辞めていく
- 自分が意思決定のボトルネックになっている
- CEO との信頼関係が、繰り返し揺らいでいる

兆候に気づいたときの選択肢は、辞めることだけではありません。

- **役割を分ける**: 組織の運営を VPoE に任せ、自分は技術の方向性とアーキテクチャに集中する
- **役割を移る**: 新しい CTO を迎え、自分は別の役割（技術のフェロー、特定の事業の責任者、アドバイザーなど）に移る
- **計画的に退く**: 後任を育て、または迎え、引き継ぎの期間を設けて退任する

いずれの場合も、**CEO と早く、正直に話す** ことが最も重要です。自分の後継者の計画を自分から提案できる CTO は、会社にとって最も信頼できる CTO です。

### 8.2 後継者計画を作る

後継者計画には、二つの目的があります。一つは、CTO が突然いなくなった場合（急病、事故、危機の最中の離脱）に会社が止まらないようにすること。もう一つは、計画的な交代や組織の成長に備えて、次の世代のリーダーを育てることです。

| 要素 | 内容 |
|---|---|
| 重要な責任の一覧 | CTO が担っている責任（技術の方向性、組織の運営、セキュリティ、主要なベンダーとの関係、取締役会への報告など） |
| 緊急時の代行者 | 責任ごとに、今日から代わりを務められる人 |
| 後継者の候補 | 「今すぐ」「1〜2 年後」「3 年以上後」の準備度ごとの候補 |
| 育成の計画 | 候補者ごとに、足りない経験と、それを得る機会（任せる仕事、研修、メンター） |
| 知識と関係の移転 | 設計の判断の記録、アクセス権の管理（緊急時に使える特権アクセスの手順）、ベンダーや取締役会との関係の紹介 |
| 共有の範囲 | CEO と取締役会（機密として扱う） |

演習 5 で、後継者計画の草案を書きます。

## 9. 倫理と責任

### 9.1 ACM の倫理綱領

計算機科学の国際的な学会である ACM は、2018 年に「ACM Code of Ethics and Professional Conduct」を改訂しました。一般的な倫理の原則（第 1 節）、専門家としての責任（第 2 節）、専門家としてのリーダーシップの原則（第 3 節）、綱領の遵守（第 4 節）から構成されます。第 3 節は、組織を率いる立場の人に向けた原則で、CTO にとって特に重要です（以下の日本語は筆者の訳）。

| 原則 | 内容 |
|---|---|
| 3.1 | 専門的なコンピューティングのすべての仕事において、公共の利益を中心的な関心事とする |
| 3.2 | 組織やグループのメンバーによる社会的責任の遂行を、明確にし、受け入れを促し、評価する |
| 3.3 | 働く生活の質を高めるように、人と資源を管理する |
| 3.4 | 綱領の原則を反映した方針と手続きを明確にし、適用し、支援する |
| 3.5 | 組織やグループのメンバーが専門家として成長する機会を作る |
| 3.6 | システムを変更したり廃止したりするときには、注意を払う |
| 3.7 | 社会の基盤に組み込まれたシステムを認識し、特別な注意を払う |

また、第 1 節の「1.2 害を避ける」では、害をもたらしうるシステムのリスクの兆候を報告する責任に触れ、リーダーがリスクを抑える行動をとらない場合には「内部告発」が必要になることもありうる一方で、軽率な、あるいは誤った報告もそれ自体が害になりうるため、報告の前に状況を慎重に評価すべきだと述べています。

### 9.2 非倫理的な要請に向き合う

CTO は、倫理的に問題のある要請を受ける立場にあります。例えば、解約を意図的に難しくする画面の設計、法令の期限を過ぎてまでの情報漏えいの公表の先送り、投資家や監査への数字の粉飾、同意の範囲を超えたデータの収集や販売、既知の安全上の欠陥を抱えたままの出荷、内部で問題を指摘した人への報復、などです。

こうした要請に向き合う手順を、平時に決めておきます。

1. **事実を確かめる**: 要請の意図を誤解していないか。何が問題なのかを、法令・契約・倫理のどれに照らして問題なのかまで整理する
2. **代わりの案を示す**: 要請の背後にある事業の目的を、倫理的な方法で達成する案を出す（例: 解約の防止ではなく、解約理由の分析と改善）
3. **記録を残す**: 要請の内容、日時、自分の回答を記録する
4. **エスカレーションする**: CEO と話し、解決しなければ取締役会、監査役（または監査等委員会）、社外の弁護士に相談する
5. **通報の窓口を使う**: 社内の内部通報の窓口、必要に応じて行政機関などへの通報
6. **最後の手段として辞任する**: 自分が加担することを拒む

**自分が越えない一線（レッドライン）は、平静なときに書いておく** ことを勧めます。圧力がかかった状況では、少しずつ妥協を重ねて、気づけば一線を越えていることがあるからです。

### 9.3 公益通報者保護法

日本の公益通報者保護法は、事業者の一定の法令違反の事実を、社内の窓口・行政機関・報道機関などに通報した人を、解雇などの不利益な取扱いから保護する法律です（以下は一般的な説明です。具体的な判断は弁護士に確認してください）。

- 2022 年 6 月に施行された改正で、退職後 1 年以内の人と役員も保護の対象に加わりました。役員が行政機関や報道機関などの外部に通報する場合は、原則として、まず社内で調査や是正の措置をとるよう努めたことなどが保護の要件になります。
- 同じ改正で、常時使用する労働者が 300 人を超える事業者には、内部通報に適切に対応する体制の整備が義務づけられ、通報への対応業務に従事する人には守秘義務が課されました。
- 2025 年にも改正法が成立し、通報を理由とする解雇や懲戒への刑事罰の導入、通報後 1 年以内の解雇や懲戒を通報を理由とするものと推定する規定、一定のフリーランスへの保護の拡大などが盛り込まれました。2026 年 12 月 1 日に施行される予定とされています。

CTO は、自分が通報する可能性がある立場であると同時に、**内部通報の仕組みを作り、通報した人を守る立場** でもあります。技術組織で「言いにくいことを言える」文化は、[14.6](../06-crisis-management/README.md) で見たように、危機を防ぐ仕組みでもあります。

## よくある落とし穴

1. **すべての会議に出る**。CTO が出席しないと決まらない組織は、CTO の時間で成長が止まります。基準を文書にして委任し、自分は議事録を読む側に回ります。
2. **技術から完全に離れる、または書き続けてクリティカルパスに入る**。判断力を保つために技術に触れ続けつつ、チームの作業の流れを自分で止めない距離を保ちます。
3. **燃え尽きを気合で乗り切ろうとする**。燃え尽きは職場の構造から生じる現象です。仕組み（委任、代行者、休暇）と専門家の助けで対処します。
4. **フィードバックを求めない**。立場が上がるほど、周囲は率直に言わなくなります。360 度フィードバックなど、意図的な仕組みが必要です。
5. **支援のネットワークを、危機になってから作ろうとする**。相談相手との信頼関係は、平時にしか作れません。
6. **自分がいなくても回る仕組みを作らない**。休暇が取れず、突然の離脱に会社が耐えられず、後継者も育ちません。
7. **倫理の一線を事前に決めていない**。圧力の中では、小さな妥協が積み重なります。平静なときに書いておきます。
8. **役割が会社に合わなくなっても、しがみつく**。会社のステージと自分の強みのずれに早く気づき、CEO と正直に話して、役割の分担・移動・計画的な交代を選びます。

### 演習 1（記述）: 自分の取扱説明書

次の項目を含む、A4 で 1 ページ程度の自分の取扱説明書を書いてください。①私の役割と今期の優先事項 ②働き方（時間帯、連絡の手段と返信の目安） ③コミュニケーションの好み ④大切にしていること ⑤苦手なこと・既知の盲点 ⑥フィードバックのもらい方 ⑦私に助けを求めてほしいとき。

<details>
<summary>解答例</summary>

```text
山田（CTO）の取扱説明書  ― 2026年10月版（半年ごとに更新）

① 役割と今期の優先事項
  技術の方向性と技術組織全体に責任を持ちます。今期の優先は
  (1) 決済基盤の信頼性（SLO 99.95% の達成） (2) EM の採用 2 名 (3) AI 活用の方針づくり。

② 働き方
  平日 9:30〜18:30。火・木の午前は考える時間としてブロックしています（緊急時を除き会議なし）。
  連絡は Slack で。24 時間以内に返信します。緊急時（障害・セキュリティ）は電話で構いません。
  夜間・休日に私からメッセージが届いても、翌営業日の返信で大丈夫です。

③ コミュニケーションの好み
  結論を先に、その後に理由と選択肢を。相談は「決めてほしいこと」を最初に書いてもらえると助かります。
  長い議論は、事前に 1 ページの文書があると質が上がります。

④ 大切にしていること
  顧客への誠実さ、率直さ、仕組みで問題を解決すること。失敗の報告が早いことを高く評価します。

⑤ 苦手なこと・既知の盲点
  興味のある技術の話になると、議論を深掘りしすぎることがあります。止めてください。
  360 度フィードバックで「決定の背景の説明が足りない」と指摘されました。改善中です。

⑥ フィードバックのもらい方
  1on1 で直接言ってもらうのが一番ありがたいです。言いにくいことは、匿名のフォームも使えます。
  私の判断に反対のときは、会議の場で遠慮なく言ってください。反対意見を歓迎します。

⑦ 助けを求めてほしいとき
  他部署との調整で行き詰まったとき、予算や人が足りないとき、倫理的に迷うことがあるとき。
  「こんなことで CTO に」と思うことでも、早めに相談してもらう方が助かります。
```

**よくできている取扱説明書の観点**

- 具体的で、読んだ人の行動が変わる（「返信は 24 時間以内」「火・木の午前はブロック」）
- 盲点を正直に書き、それを指摘してよいと明言している
- 「合わせてほしい」だけでなく、自分が相手に何を提供するか（助けを求めてほしいとき）がある
- 更新の日付と周期がある

</details>

### 演習 2（記述）: このカリキュラムを使った年間の学習計画

今後 12 か月の学習計画を、四半期ごとのテーマ、読み返す章、出力（作る・書く・教える）、時間の予算、振り返りの方法を含めて作ってください。テーマは、自社の今後の課題と自分のキャリアの両方から選びます。

<details>
<summary>解答例</summary>

前提: シリーズ C の B2B SaaS の CTO（技術組織 80 名）。来期に大企業向けの販売を強化し、2 年後の上場を目指す。自分の課題は、財務と取締役会への説明、AI の活用の方針。

| 四半期 | テーマ | 読み返す章 | 出力 | 時間 |
|---|---|---|---|---|
| Q1 | 大企業向けの信頼性とセキュリティ | 10.3、10.5、11.5、14.6 | SLO と危機管理計画を改訂し、経営陣を含む机上演習を 1 回実施 | 週 4 時間 |
| Q2 | 上場準備のガバナンスと財務 | 14.3、14.4、14.5 | IT 全般統制の現状の評価を 1 枚にまとめ、取締役会で説明 | 週 4 時間 |
| Q3 | AI の活用の方針 | 12.4、12.5、14.8 | 社内の AI 利用規程を策定。捨てる前提のプロトタイプを 2 つ作り、社内で発表 | 週 4 時間 ＋ 月 1 日 |
| Q4 | 組織の次の段階と自分のキャリア | 13.6、13.5、14.1、14.9 | 組織の 2 年後の姿の案と、自分の後継者計画の草案 | 週 4 時間 |

- **振り返り**: 四半期の終わりに、ピアの CTO 1 人と 1 時間、目標と実績を確認する。年度の終わりに、翌年のテーマを決める。
- **予算**: 書籍と研修で年間 20 万円程度、外部のカンファレンス 2 回（会社の制度を利用）。

**採点の観点**

- 合格ライン: テーマが会社の課題と結びついている。読むだけでなく、出力（文書、演習、発表、プロトタイプ）がある。時間が確保されている。
- よくできている: 出力が組織の成果物（計画、規程、演習）になっていて、学びがそのまま会社に還元される。振り返りの相手と周期が決まっている。技術（第 1〜12 部）と経営（第 13〜14 部）の両方をバランスよく含む。

</details>

### 演習 3（記述）: カレンダー監査

直近 2〜4 週間のカレンダーを書き出し、2.2 節の方法で集計してください（[14.1](../01-role-of-cto/README.md) の演習 3 で使った記録があれば、それを使ってかまいません。14.1 では責務の配分を、この演習では会議・委任・割り込みといった時間の使い方の仕組みを見直します）。そのうえで、①目標の配分とその理由 ②実際の配分とのずれ ③ずれの原因 ④来月から変えること 3 つ、を書いてください。

<details>
<summary>解答例</summary>

2.2 節の集計結果（2 週間で 60 時間）を例にします。

- **①目標の配分**: 組織が 80 名に拡大する段階なので、採用と育成（合わせて 30%）、技術の判断の質を保つための技術の時間（15%）、来年の技術戦略を考える時間（15%）を重視する。
- **②ずれ**: 経営会議・社内調整が 23% と目標より 8 ポイント多い。考える時間は 3% と 12 ポイント少なく、技術の時間も 8 ポイント少ない。
- **③原因**: 定例の会議のうち 3 つは報告だけで、何も決めていなかった。部署間の調整の多くが CTO まで上がってきており、判断の基準がないことが原因だった。障害の割り込みの多くは、オンコールのエスカレーションの基準が曖昧だったため。
- **④来月から変えること**:
  1. 報告だけの定例会議 3 つを、週 1 回の文書での報告に置き換える（週 3 時間を回収）
  2. 部署間の調整の判断の基準を文書にし、VPoE と EM に段階 4（決めて知らせる）で委任する
  3. 火・木の午前を考える時間として固定し、そのうち 1 回を設計文書とプルリクエストを読む時間に充てる
- **1 か月後に再度集計** して、変化を確かめる。

**採点の観点**

- 合格ライン: 目標の配分に理由があり、ずれが数値で示されている。変えることが具体的で、測定できる。
- よくできている: ずれの原因を、個々の予定ではなく仕組み（委任の不足、基準の欠如）として捉えている。再集計の予定がある。

</details>

### 演習 4（記述）: 支援のネットワークの地図

1.2 節の種類（ピア、メンター、コーチ、アドバイザー、専門家、家族・友人）ごとに、今の自分の支えになっている人（名前ではなく関係性で可）、相談できるテーマ、最後に話した時期を書き出してください。そのうえで、欠けている支えと、今後 3 か月で作る行動を書いてください。

<details>
<summary>解答例</summary>

| 種類 | 現在の支え | 相談できるテーマ | 最後に話した時期 |
|---|---|---|---|
| ピア | 前職の同僚で、今は別の会社の CTO（1 人） | 組織の拡大、採用 | 4 か月前 |
| メンター | なし | — | — |
| コーチ | なし | — | — |
| アドバイザー | 社外取締役（投資家） | 取締役会への説明 | 1 か月前（取締役会の場のみ） |
| 専門家 | 会社の顧問弁護士、産業医 | 法務の相談（健康の相談はしたことがない） | 必要なときのみ |
| 家族・友人 | 配偶者、大学時代の友人 | 仕事以外のこと | 継続的 |

**欠けている支えと、3 か月の行動**

- ピアが 1 人だけで、しかも疎遠になっている → 技術の経営者のコミュニティの勉強会に 2 回参加し、定期的に話せるピアを 2 人増やす。前職の同僚とは月 1 回の食事を予定に入れる。
- メンターがいない → 上場を経験した元 CTO に、「上場準備の技術面で何を優先すべきか」という具体的な問いを持って、四半期に 1 回の相談を依頼する。
- 社外取締役とは取締役会以外で話していない → 四半期に 1 回、30 分の 1on1 を依頼する。
- コーチは、来年度の予算で検討する（360 度フィードバックと組み合わせる）。

**採点の観点**

- 合格ライン: 種類ごとに現状を正直に書き、空白を特定している。行動が具体的で、期限がある。
- よくできている: 「最後に話した時期」から、関係が形だけになっていないかを点検している。相談のテーマが偏っていないか（技術だけ、など）を確認している。

</details>

### 演習 5（記述）: 後継者計画の草案

自分（または想定する CTO の立場）の後継者計画の草案を、8.2 節の要素に沿って書いてください。

<details>
<summary>解答例</summary>

前提: 技術組織 80 名の CTO。直下に VPoE 1 名、EM 6 名、プリンシパルエンジニア 1 名、セキュリティ責任者 1 名。

**重要な責任と緊急時の代行者**

| 責任 | 緊急時の代行者 | 備考 |
|---|---|---|
| 技術組織の運営（採用・評価・予算の執行） | VPoE | 予算の承認権限の代行を、職務権限規程に明記済み |
| 技術の方向性・重要な設計の判断 | プリンシパルエンジニア | 重要な判断は ADR として記録済み |
| セキュリティとインシデントの指揮 | セキュリティ責任者 | 危機管理計画の代行順位に記載 |
| 主要なベンダー（クラウド、決済）との関係 | VPoE | 年 1 回、先方の担当者に紹介する |
| 取締役会への技術の報告 | CEO ＋ VPoE | 四半期の報告資料の型を共有済み |

**後継者の候補**

| 候補 | 準備度 | 足りない経験 | 育成の計画 |
|---|---|---|---|
| VPoE | 1〜2 年 | 技術戦略の策定、取締役会・投資家への説明 | 来期の技術戦略の草案を任せる。取締役会に四半期に 1 回同席 |
| プリンシパルエンジニア | 3 年以上 | 組織のマネジメント、予算 | 1 チームの EM を半年間兼務する。社外のメンターを紹介 |
| 社外からの採用 | — | 自社の文脈 | 候補が社内に育たない場合の選択肢として、CEO と合意しておく |

**知識と関係の移転**: 設計の判断は ADR に、運用の手順は手順書に残す。緊急時に使う特権アクセスの手順（誰が、どう承認するか）を文書にし、半年ごとに試す。

**共有の範囲と見直し**: CEO と取締役会に共有し、年 1 回見直す。候補者本人への伝え方は、CEO と相談して決める。

**採点の観点**

- 合格ライン: 「緊急時の代行者」と「長期の後継者」を分けている。責任ごとに代行者がいて、権限や手順の裏付けがある。
- よくできている: 候補者ごとの足りない経験と、それを埋める具体的な機会がある。特権アクセスや外部との関係など、見落としやすい移転の対象を含む。社外からの採用という選択肢も排除していない。

</details>

## 理解度チェック

**Q1. Paul Graham の「メイカーのスケジュール」と「マネージャーのスケジュール」の違いを説明し、両方を抱える CTO が時間を設計するための工夫を 2 つ挙げてください。**

<details>
<summary>解答</summary>

マネージャーのスケジュールは、1 日を 1 時間単位に区切って予定を入れていく使い方です。メイカーのスケジュールは、作る仕事のために少なくとも半日単位のまとまった時間を必要とします。1 つの会議が時間を分断し、どちらの断片も難しい仕事には短すぎる状態にしてしまうため、メイカーにとって会議のコストは見かけより大きくなります。

工夫の例: ①考える時間・技術に触れる時間を先にカレンダーで予約し、その時間は会議を入れない。②会議や 1on1 を特定の曜日や時間帯にまとめる（Graham は面談を作業日の終わりのまとまった枠に集める方法を紹介しています）。ほかに、チームのエンジニアの時間を分断しないよう、思いつきで会議に呼ばないことも大切です。

</details>

**Q2. カレンダー監査で「経営会議・社内調整」の時間が目標の 1.5 倍、「考える時間」が目標の 5 分の 1 でした。どのように原因を分析し、改善しますか。**

<details>
<summary>解答</summary>

個々の予定の多さではなく、仕組みの問題として原因を探ります。例えば、報告だけで何も決めない定例会議はないか、判断の基準がないために調整が CTO まで上がってきていないか、委任の段階が低すぎないか、を見ます。

改善としては、何も決めない定例会議を文書での報告に置き換える、判断の基準を文書にして委任の段階を上げる（「決めて知らせる」など）、考える時間を先に予約して守る、といった手を打ちます。そして 1 か月後に再び集計し、変化を確かめます。

</details>

**Q3. 「意思決定の疲労」の研究について、どのような注意が必要ですか。それを踏まえて、CTO が判断の質を保つためにとるべき実践を挙げてください。**

<details>
<summary>解答</summary>

仮釈放の審査の研究（Danziger ら、2011 年）は有名ですが、審理の順番が無作為でなかったという指摘や、時間の管理だけで同様のデータが生じうるというシミュレーション（Glöckner、2016 年）による批判があります。また、自我消耗の効果は大規模な事前登録の追試（Hagger ら、2016 年）でほぼ確認されませんでした。「判断の回数そのものが資源を減らす」という強い主張を、確かな事実として扱うべきではありません。

それでも、疲労や睡眠不足が判断を損なうことを前提に、判断の負荷を下げる仕組みを作るのが賢明です。繰り返しの判断を方針に変える、後戻りできる判断（タイプ 2）は委任して素早く決め、後戻りできない判断（タイプ 1）に集中する、重い判断はよく休んだ状態で行う、判断を記録して振り返り自分の癖を知る、などです。

</details>

**Q4. WHO による燃え尽きの特徴づけの 3 つの次元を挙げ、燃え尽きを個人の問題ではなく仕組みの問題として扱うべき理由と、予防策を説明してください。**

<details>
<summary>解答</summary>

3 つの次元は、①エネルギーの枯渇や消耗感、②仕事からの心理的な距離の増大（否定的・冷笑的な感情）、③職業上の効力感の低下です。WHO は燃え尽きを、うまく管理されなかった慢性的な職場のストレスから生じる職業上の現象と位置づけています。原因が職場の構造にある以上、個人の気合や我慢では解決しません。

予防策は、仕組み（持続可能なペース、委任、自分がいなくても回る体制、実際に休暇を取れる状態）、個人の習慣（睡眠、運動、仕事の外の関係）、専門家（産業医、EAP、医療機関、コーチ）の 3 層で考えます。役員の CTO は労働法上の保護の外にいることがあるため、自分で上限を決め、会社として役員の健康を支える仕組みも整えます。兆候が続くときは、治療が必要な状態との区別も含めて医療機関に相談します。

</details>

**Q5. 会社が「別の種類の CTO」を必要としている兆候を 3 つ挙げ、それに気づいたときの選択肢を説明してください。**

<details>
<summary>解答</summary>

兆候の例: 取締役会や CEO から求められる仕事に興味を持てない、または力を発揮できない。組織の規模が自分のマネジメントの力量を超えている。採用や予算など、自分が避けている仕事がある。優秀なメンバーがリーダーシップを理由に辞めていく。自分が意思決定のボトルネックになっている。

選択肢は、辞めることだけではありません。組織の運営を VPoE に任せて技術の方向性に集中する（役割を分ける）、新しい CTO を迎えて別の役割に移る、後任を育てるか迎えて計画的に退任する、などがあります。いずれの場合も、CEO と早く正直に話し、自分から後継の計画を提案することが、会社にとっても自分にとっても最善の道になります。

</details>

**Q6. CEO から、公表の期限が迫っている情報漏えいについて「四半期の決算発表が終わるまで公表を遅らせてほしい」と求められました。どう行動しますか。ACM の倫理綱領と日本の制度を踏まえて説明してください。**

<details>
<summary>解答</summary>

まず事実を確かめます。個人情報保護委員会への報告や本人への通知の期限、契約上の通知義務、上場企業としての開示のルールに照らして、遅らせることが法令や契約に反するかを、法務・社外の弁護士と確認します。そのうえで、要請の背後にある目的（株価や決算への影響の懸念）を、期限内の公表と両立させる案を示します（例: 事実と対応を正確にまとめた公表文と、投資家向けの説明を準備する）。要請と自分の回答は記録に残します。

それでも法令に反する先送りを求められるなら、取締役会、監査役（または監査等委員会）、社外の弁護士にエスカレーションします。ACM の倫理綱領の 1.2 は、害をもたらしうるリスクを報告する責任に触れ、リーダーが対処しない場合には内部告発が必要になることもありうるとしています。日本の公益通報者保護法は、一定の法令違反の通報者を保護しており、役員も保護の対象ですが、外部への通報では、原則として先に社内で調査・是正の措置をとるよう努めたことなどが要件になります。具体的な判断は弁護士に確認します。最後の手段として、加担を拒んで辞任することもありえます。

</details>

**Q7. CTO の後継者計画に、長期の後継者の候補だけでなく「緊急時の代行者」を含めるべき理由を説明してください。**

<details>
<summary>解答</summary>

CTO が突然いなくなる事態（急病、事故、危機の最中の離脱）は、長期の後継者が育つのを待ってはくれないからです。代行者が決まっていなければ、予算の執行、重要な設計の判断、セキュリティ事故の指揮、ベンダーや取締役会との連絡が止まり、会社の業務やリスク対応に穴が開きます。責任ごとに「今日から代われる人」を決め、権限（職務権限規程への明記）、手順（特権アクセスの緊急手順）、関係（ベンダーへの紹介）の裏付けを用意しておくことで、CTO 自身も安心して休暇を取れるようになります。

</details>

## さらに学ぶために

- Paul Graham "Maker's Schedule, Manager's Schedule"（2009 年）— 短いエッセイだが、時間の設計を考えるときの基本の枠組み。自分とチームの時間の両方に効く。
- Andrew S. Grove『HIGH OUTPUT MANAGEMENT』（日経BP）— タスク習熟度に応じた関わり方、会議、委任など、マネージャーの時間の使い方の古典。
- Camille Fournier『エンジニアのためのマネジメントキャリアパス』（オライリー・ジャパン）— テックリードから CTO までの各段階の役割と悩みを、現場の視点で整理している。自分の役割の変化を理解するために。
- Ben Horowitz『HARD THINGS』（日経BP）— 経営者の孤独と、正解のない困難な判断の実態を率直に描いた本。支えのない状況で判断を下す心構えが得られる。
- ACM "Code of Ethics and Professional Conduct"（2018 年）— 計算機の専門家としての倫理の原則。特にリーダーシップの原則（第 3 節）は、CTO が組織で果たすべき責任の指針になる。
- 消費者庁の公益通報者保護制度の解説 — 法律の概要、事業者の体制整備の指針、改正の内容を一次情報で確認できる。
- WHO の ICD-11 における燃え尽き（burn-out）の説明（2019 年）— 燃え尽きの定義と、それが職場の現象であることの根拠。

## まとめ

- CTO の孤独は役割の構造から生まれる。ピア・メンター・コーチ・アドバイザー・専門家・家族からなる支援のネットワークを、危機の前に作っておく。
- 時間は、メイカーとマネージャーの両方のスケジュールを意識して設計する。カレンダー監査で実態を測り、委任・断ること・会議のまとめ方・エネルギーの管理で改善する。
- 技術力とは判断力である。技術に触れ続ける習慣を持ちつつ、自分をクリティカルパスに置かない。流行は問題・証拠・コスト・出口の問いで評価し、このカリキュラムを螺旋のように読み返す。
- 意思決定の疲労の研究は強い主張には注意が必要だが、判断の負荷を下げる仕組み（方針化、タイプ 1 とタイプ 2 の区別、記録と振り返り）は有効である。
- 燃え尽きは職場の構造から生じる現象であり、仕組み・個人・専門家の 3 層で予防する。リーダーの働き方はチームに伝染する。
- フィードバックの仕組みで盲点を小さくし、自分の取扱説明書を互いに合わせるための出発点として使う。
- キャリアの選択肢は多様であり、会社が別の種類の CTO を必要とする兆候に早く気づいて、CEO と正直に話す。緊急時の代行者と長期の後継者の両方を含む後継者計画を作る。
- 倫理の一線は平静なときに決めておく。非倫理的な要請には、確認・代替案・記録・エスカレーション・通報の手順で向き合い、内部通報の仕組みを作り守る立場でもあることを忘れない。
